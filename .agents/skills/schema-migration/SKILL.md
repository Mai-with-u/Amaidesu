# 配置与存储迁移

本仓库的配置与存储变更遵循"Schema 即真相"（配置文件的结构由代码里的 Pydantic Schema 唯一定义，文件是它的落盘快照）。规则法条在仓库根 `AGENTS.md` 的"配置与存储变更"一节——本 skill 不复制法条，只给可执行的操作流程。该区自认的最高频事故形态是"只改 Schema 不升版本、不验证迁移"，本 skill 的全部设计都为堵住这两步。

## 决策入口四问（动 Schema 前逐条回答）

1. **纯新增还是数据变换？** 只加新字段/新段（带默认值）= 纯新增，零成本；其余都算数据变换——改默认值且需要存量配置跟随、字段重命名、删字段/段、段跨文件搬移、值的类型或语义转换。判断标准：一个**已落盘**的旧配置文件，加载后磁盘上的内容需不需要被改写？需要 = 数据变换。
2. **动的是配置文件还是存储表？** 配置文件走 `src/modules/config/` 的每文件版本 + 升级钩子（工作流见 [references/config-workflow.md](references/config-workflow.md)）；存储表走 `src/modules/storage/` 的 `SCHEMA_VERSION` + 一版本一文件迁移（工作流见 [references/storage-workflow.md](references/storage-workflow.md)）。两者机制独立、版本流互不相干。
3. **版本推进到哪？** 配置：只升目标文件的 `[meta].version` 到新钩子的 target（各文件版本独立，一个文件升版本绝不带动其他文件）。存储：`SCHEMA_VERSION` 恰好 +1，并为该版本补注册表条目（严格 +1，缺条目会被守护测试拦下）。
4. **怎么证明迁移生效？** 不是"迁移测试绿了"就算——证据是**写回落盘**或**加载日志**：配置跑 `tests/config/` 对应用例，看加载后文件里的新版本号、新值与"第二次加载零变更"；存储看启动日志的 schema 版本推进行。迁移必须幂等（对已迁移的数据重复执行不再产生变更），第二次加载/重启零变更是验证的一部分。

## 红线（每条都出过事故）

- **存储迁移的测试库绝不指向真实库 `data/amaidesu.db`**——测试一律用 `tests/conftest.py` 的 `db_path` fixture（`tmp_path/test.db`）或 `sqlite3.connect(":memory:")`。历史事故：测试污染过真实库。
- **`SCHEMA_VERSION` 与 pyproject 发布版本号无关**——它是存储表结构的数据迁移版本，不参与发布、不随发布 bump。
- **迁移必须幂等**——幂等指：对已经迁移过的数据再执行一次，结果不变、不再产生变更。新旧钩子都以"列/键存在性检查"实现，重复执行安全是注册表与调度器的硬性契约。
- **键改名/退役不写钩子的后果是启动硬错**——加载管线对程序不认识的条目一律报错而非静默跳过，所以"忘了钩子"不会被悄悄放过，但会把启动砸了；宁多做一次核对验证，不赌用户目录形状。
- 修改既有字段的默认值**只影响新生成的配置文件**——存量文件保留现值；需要存量跟随的按数据变换档处理，且钩子里区分"用户显式设置的值"（不动）与"等于旧默认的落盘值"（改写）。

## 操作分流

四问回答完，按第 2 问分流：

- 配置文件 → [references/config-workflow.md](references/config-workflow.md)（含纯新增零成本路径、钩子写法、迁移测试模板、验证写回的具体操作）
- 存储表 → [references/storage-workflow.md](references/storage-workflow.md)（含版本推进、迁移实现、测试写法、启动验证）

配置结构变更后连带要更新组件的 schema 测试（改哪个组件就同步改哪个组件的 schema 测试）；这些都是普通代码改动，随迁移工作流一并完成。

## 自我改进（每次迁移收尾时执行）

迁移实践中发现的新坑（钩子次序、幂等反例、验证盲区）要回灌本 skill 与 references，收编有硬性守卫，**防止对着答案出题**（把一次迁移的特殊情况当成普遍规律写进清单）：

1. 收编候选 = 本次迁移新发现、且既有清单未覆盖的坑；已覆盖的不动。
2. 收编三问，全过才写：**去掉本次变更的具体事实还能执行吗**（不引用本次改的字段名、版本号、文件名）；**是既有条目的换皮吗**（重复就合并）；**下一次迁移能直接照做吗**（能落成明确的检查动作，不是一句感想）。
3. 具体案例（本次的版本号、字段路径、报错原文）留在提交信息与代码注释里当证据，不进正文清单。
4. 单次收编不超过三条；想收更多说明该重组清单而不是继续加长。
5. 变更走仓库版本管理，正文不写变更记录。
