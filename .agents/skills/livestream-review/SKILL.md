# 直播复盘

对一场已发生的直播（或任意 Agent 运行会话）做事后分析：先用数据量化"发生了什么"，再对疑点逐层深挖、拿到确凿证据，最后沉淀成可领取修复的问题清单，并把本场的新经验回灌给本 skill 自身（见第九步）。纪律只有一条：**每条结论都要有原始证据（日志行、代码位置、统计数字），不确定就标注存疑，不猜。**

## 输入与数据源

分析的全部原料是运行时产物（场次记录表、事件日志、LLM 请求全文、应用日志），它们不入版本管理、只存在于实际运行过的机器上。本仓库的具体路径约定见 [references/data-sources.md](references/data-sources.md)；移植到其他项目时，按"场次记录库 / 事件日志 / 请求全文 / 进程日志"四类结构探测对应位置，流程不变。

场次边界：从会话开始事件到结束事件；缺结束事件时用进程关闭事件确定结束边界，并在报告里注明统计所用的数据来源与查询时刻——结束信息可能由下次启动的兜底补写，**查记录前先确认进程状态与查询时点**（见第四步检查点）。

## 第一步：定位会话 + 概览统计（先量后质）

1. 查数据库里的场次记录表（live_sessions）定位场次号与时间窗；列出当日的日志文件（注意按小时/大小轮转，一场可能跨多个文件）。顺手盘点覆盖缺口：表中已结束、但复盘分析目录没有对应文档的场次，在汇报里列出（只提示，不主动扩工）；时长不足 5 分钟且无观众互动的场次按测试场登记，不展开复盘。
2. 事件类型分布计数——异常量级一眼可见（某类失败事件、求助事件突增）。
3. 生命周期时间线：进程启动/关闭、场次开/结、环节切换、全部警告与错误。记录：进程重启几次、哪些退出没有关闭记录、开播前折腾了多久。
4. 本场数据：发言条数与频率、决策轮数及触发来源分布、发言/沉默比、观众弹幕量与进房数、游戏任务成功/失败计数、礼物/SC/舰长条数。
5. LLM 用量按用途分组（请求记录里的 profile 字段，区分决策、游戏、台词等）：调用量、输入/输出 token、缓存命中率、单笔 prompt 上限、**费用**（`overview_stats.py --config config/model.toml` 按仓库价格表现算，口径与 `observation.calculate_cost` 一致；注明统计窗口是进程启动起还是开播起）。历史单调爬升且全程无回落 = 整理/压缩从未触发——**先读代码确认触发阈值与设计意图再定性**。对照相邻场次时先按 profile+模型名分组核对两场各自实际用的模型——两场之间的一次进程重启就可能伴随模型配置变更，节奏/成本差异先归因模型再谈代码。

第 2、3、4、5 步的机械统计可直接跑 [scripts/overview_stats.py](scripts/overview_stats.py)。

## 第二步：梳理全场内容时间线（游戏事件 ⊕ 发言统一对齐）

以开播到下播为窗，把游戏侧事件（任务变化、里程碑、身体事件、死亡）与全部发言按时间合并成一张时间线，标注三类行：游戏事件、发言、二者矛盾处。时间线是后面所有内容判断的事实底座，先梳理再分析：

1. 逐条发言对照"开口时游戏里刚发生了什么"，对不上处（发言断言 X、游戏记录为 Y）单独标注——叙述与游戏记录的矛盾是虚构断言的直接证据。**矛盾判定的事实源是世界记录**（感知载荷、事件、对端日志），主播自述按"背包级/世界级"分级：背包级字面属实不等于世界级属实，后者才是观众听到的断言。
2. 同一模板句/同一玩笑结构全场出现几次（如"给某物起名"类桥段）：间隔多远、共多少次、对象是否始终存在——**对象是否存在要逐轮查感知实体列表**，实体离场在感知里是静默（只报在场不报离场），主播继续对已离场/已死亡实体说话是时间线矛盾行。
3. 涉及其他进程/对端（如游戏 Mod 服务端）时，把对端日志纳入时间线互证：agent 叙述的事实主张不能只用 agent 侧转述链自证——转述可能在任何一环升格或失真（"范围内没有能睡的床"被转述成"没床"即此类）。
4. 时间线成品随复盘文档归档（阶段划分 + 关键事件 + 关键发言引用 + 矛盾标注），供人工复核与后续场次对照。**完成判定以文档结构为准：复盘文档里必须存在"时间线"章节且矛盾逐条标注（全程确无矛盾也要写明一句）——分析过程中对齐过不等于已归档，归档时降级成散文纪要是本条被连续多场跳过的真实形态，交付前先查文档结构，缺该章节 = 第二步未完成。**

## 第三步：内容分析（发言质量，两轴分离，子代理并行）

发言质量审计分两轴，**分开分析、分开报告，一轴不替另一轴背书**：

- **轴 A：客观内容审计**（判据见 [references/speech-audit-criteria.md](references/speech-audit-criteria.md)）——只依赖发言文本与运行记录，不依赖互动数据。判据分五组：事实与状态（与事实偏离 / 前后矛盾 / 实体同一性 / 时空与状态自洽）、承诺与因果（宣布-兑现闭环 / 悬念闭合 / 因果归因）、社交与情感（不合时宜的玩梗 / 情绪-事件极性 / 对象指向）、信息与重复（话题重复 / 信息新鲜度 / 造梗前提）、机制与跨场（递话消化率 / 历史密度 vs 新鲜感知 / 备忘录事实错误率——备忘录错误会带进下场，优先级高于单条发言）。判"属实/偏离"以**世界记录**为事实源，主播自述与其状态块不构成事实源；修辞豁免（明显不可能为真的夸张）须显式写明理由。
- **轴 B：互动行为**（进房响应率与时延 / 弹幕回应对齐 / 付费致谢完整性）——核对的是行为有没有做，不是效果好不好。
- **效果判断（"好看/节奏好/有节目效果"）不属于任何一轴**：零观众反馈数据（0 弹幕）时禁止写任何效果结论，只允许写"结构存在"（某结构可回查地发生了）并注明效果未验证。

**子代理并行审计**（做法参考通用 code-review skill 的双轴分离：隔离上下文、具体 brief、汇总时绝不合并重排）：轴 A、轴 B、基础设施专项各派一个子代理，每个只带自己的 brief（数据源路径 + 判据清单 + 产出上限），不带入主会话的任何中间结论——主会话积累的叙事印象（"这场不错"）是审计偏置的源头，子代理没有这个包袱。主会话汇总时按轴分报，**两轴发现冲突时不折衷、并排呈现**。子代理的产出同样是待验证主张，进文档前照走第四步的三级证据链，不因"子代理说的"免检。

机械统计落地（脚本见 [scripts/](scripts/)）：

1. 每条发言与开口前窗口内新事件对齐，纯状态重述占比——**必须全量分类，抽样只能标"下限估计"**。
2. 近邻复读组与模板句轮转保留时间戳与原文对照。
3. 用 `gate_replay.py` 把台词序列与 planner 指导语序列各过一遍线上同款重合度闸：指导语层重合率高于台词层即复读源头在决策环节；指导语句式模板占比（如"对 X 自嘲……不提 Y"）单独统计——模板占比直接解释情绪分布偏置。
4. 情绪字段分布与负面事件后首轮情绪抽样（死亡/他人死亡/重伤各抽一轮），对照人设口径判断是否越界。
5. 决策时延（中位/p90/最大）入概览——秒级世界变化被"说晚"属机制性延迟，审计时从"偏离"里剔出单列。
6. 收尾核对：结束边界前后到达的受理类事件（递话、委派、收尾任务）逐一核对消费输出——受理成功不等于被消化。
7. **好样本也要记，但只记结构事实**（某结构可回查地发生了），效果判语（节奏好/收束完整）禁写；写之前对每条正面结论**先找反证**（它的结尾是否其实是事故的可见症状）。

## 第四步：疑点深挖（每条必须拿到确凿证据）

对概览发现的每个异常，先按形态关键词检索复盘分析目录的既往文档：命中同形态记录的，标注"与场次N同构"并继承其结论链，只复核增补、不重复深挖；未命中的，沿"事件日志给线索 → 进程日志找原因原文（含堆栈）→ 读代码定机制与阈值"三层逐层查证。以下四条检查点是硬性的，每条结论过一遍：

1. **先假设"可能是有意设计"**：读代码与配置确认语义后再定性。看似缺陷的形态常是文档化行为（终态标记、预算线未到、兜底延迟）——未读代码就报缺陷，是复盘最高频的误报来源。
2. **读机制代码前先锚定当晚实际运行的版本**：工作区当前代码不等于当晚行为——修复可能在场次之后才并入，或已并入但实例没重启。先从提交历史确认当时在跑的版本，再对着那个版本读代码。同日多进程（中途重启）按时段分段锚定；若场内有提交落在进程启动之后，运行代码可能是该提交的**未提交形态**——提交时间晚于进程启动不等于改动没在跑，以日志里的实际行为反推版本，不迷信单一 commit hash。
3. **查数据库/日志前先确认时点**：进程还在运行或刚重启时，看到的是中间态——结束时间可能由下次启动的兜底补写、计数可能尚未 flush。结论引用的必须是最终状态。
4. **判"失败"要看重试后的最终状态**：首试失败 ≠ 最终失败，先确认重连/重试循环是否自愈，再谈"人工解围"或"依赖缺陷"。
5. **存疑的出口只有三个**：①**当场查掉**——知道哪块没查就先查，"未复核/待深挖"不构成交付状态；②**数据不存在**——日志里根本没有的（只有直播时能看到的现象、无记录的人工决策），转"问用户"清单；③**已调查至数据边界**——写明"已查到什么、边界在哪"（如"日志未记录该次交互的坐标"），这三种之外不存在第四种状态。把调查义务写成"待查"挂在报告里，是把义务转给读者，且旁边的判断可能已被它带偏。
6. **三级证据链齐了才定级**："主播没理会某信息"类疑点，行为层（发言/行动里无引用）只是线索，必须再下钻两层：**注入层**——请求全文检索这条信息进没进模型、进了多少笔、存续多久（两条同类递话一条注入几十笔一条只注入一笔，本身就是缺陷）；**感知层**——观察/速览原始载荷里这个事实在不在（关键物体从未进感知与"看了没理"是两种事故，归属不同）。缺一级就定级，严重度只会被系统性低估。基础设施专项同理：告警计数层不算分析完成，要下钻到"哪一句/哪一帧"。

另外四条：任何频率/量级主张先跑统计再写，不为叙事凑数字；判定问题归属（本仓库 / 外部依赖 / 第三方服务）必须给证据（如"传输层全程正常完成 → 断点在对端会话层"），涉及对端仓库（如游戏 Mod）的结论要注明对端的版本或时点——对端在自己演进，两天前的归属判断今天可能已反转；**基础设施专项核对**——语音合成（失败/断流/冷启动吞句）、画面采集（断流/长期未更新）、弹幕与游戏链路（中断/重连风暴），这类问题在发言层可能没有症状、只有事件与告警层有痕迹，只看发言就会漏；**任务完成度核对**——游戏任务的成功/失败计数与失败原因分布，连续失败或大面积失败要给归因。

## 第五步：对照既往修复验收

调出上一场的复盘文档：既往修复逐条核对是否复发、是否真生效（要生效证据，如"场内此类告警 0 条"）；历史问题清单（口癖、关键事件叙述缺失、音频断流、启动失败风暴……）逐项标注状态：已修复 / 未复发 / 复发 / 暂缓观察。同时核对上一场文档的"待拍板"区与移交清单的现状：已处置的销项，仍悬置的带原日期在本次报告待拍板区重列——拍板项静默蒸发与误报同样损害复盘的信用。**修复效果的下播验收就以这一步为准。**

## 第六步：写入复盘文档（markdown 初稿）→ 与用户讨论定稿

**产出顺序**：markdown 初稿 → 客观性自查 → 向用户汇报并讨论 → **缺陷全部定稿后**才进入第七步做可视化页。HTML 是最终渲染产物，不是讨论稿——讨论轮次不做网页（教训：边讨论边做页，页面会落后文档数代，返工且失同步）。

每场一份分析文档，写进项目的复盘分析目录（gitignored，属内部事务），固定结构见 [references/report-template.md](references/report-template.md)。要点：

- 只写事实与归因；修复完成后在原条目下追加"修复记录"行（含提交标识），不另开文档、不在文末堆变更记录；
- 结论涉及本地编号、内部事件的内容不进提交信息与被跟踪代码——远端读者无从知晓；
- 分析用的临时脚本与中间文件用完即删；**承重计算（写进结论的数字）的查询方法随结论记录**（脚本化或注明查询口径），保证他人可复算。

**客观性自查是交付硬门**：初稿写完、汇报之前，对整份复盘逐项过 [references/objectivity-selfcheck.md](references/objectivity-selfcheck.md)（A 断言 / B 证据链 / C 统计方法 / D 立场 / E 交付卫生五组，每条是可对着成品验证的问句）。产出要求：在复盘文档"复盘自查"节**写出实际查出的项与改动**——只写"已逐项自查通过"不构成自查。**红队盲审（建议，非强制）**：派一个不带本会话上下文的子代理，只给判据清单 + 自查清单 + 文档路径，独立找问题；与主分析对比，差集即主分析的盲区，逐条处置（采纳或驳回并说明理由）——自查清单由分析者本人编写，只覆盖已知失效模式，盲审补未知的未知。

**向用户汇报必带三件事**（汇报正文分节：【一句话总结（说人话）】【修复/改动清单】【新发现】【待拍板】）：

1. **"问用户"清单**——只有直播时才能确认、或日志里根本没有的现象，列出来问，不写"建议复核"了事：音频听感（断流/尾音那句到底卡没卡）、画面与语音/形象动作的同步、观众端所见、操作员当时的观察（当时有没有察觉某事）、日志无记录的人工决策（测试场为什么关、什么时候手动接管了游戏）。
2. **存疑推断清单**——所有标了"存疑/不定式"的点集中列出，请用户确认或提供只有用户知道的信息。
3. **待拍板事项**——等用户圈选，不静默开工。

## 第七步：产出可视化复盘页（缺陷定稿后，一次成页）

**前置条件：第六步的讨论已结束、所有缺陷已定稿。** 本页是最终渲染，一次成页，不再随讨论返工。写到 `logs/reviews/session-{场次id}-{YYYY-MM-DD}.html`（目录不存在先创建；场次 id 以 `live_sessions` 表为准）。页面只写 HTML 结构与内容——样式与脚本外置，以相对路径引用同目录的 `report.css` / `report.js`：

- 写页面前先确认 `logs/reviews/` 下有这两个文件：缺则从 [assets/](assets/report-template.html)（report.css / report.js / report-template.html 三件套）原样拷贝过去；已存在则直接引用，不覆盖、不改动（模板本身更新不影响已落盘副本）；
- 结构按 [assets/report-template.html](assets/report-template.html) 的九个章节槽位填**定稿后**的本场数据，文件头注释写明各槽位填法（形状条/发言刻度的百分比算法等）；
- 文件名前缀 `session-{id}-` 是 WebUI 查找键，不得改动；
- 页面内容与 markdown 定稿同源同序（同一分析，两种载体），矛盾行必须用 `.conflict` 样式并编号；
- 填完自查"占位词零残留"，并对本页独立过一遍 [references/objectivity-selfcheck.md](references/objectivity-selfcheck.md) 的 E3（两个载体各自独立核对，"照着 md 改"不算核对）；全场无某章节（如测试场无游戏表现表）就整节删除，不留空壳。

## 第八步：修复派工与并入主线（用户拍板后）

1. 方案已定的事项派后台子代理到空闲工作树实施：派工单里写明"开工前先调研确认问题真实存在再动手"（防误报流入实施）；开工前先查工作树登记与 reflog（防双会话并发）、登记占用、做目标文件与在途改动的交集预检；每件修复一笔提交，遵循仓库提交规范。
2. 审阅：逐笔 diff + 提交信息（本地语境、过程标记、署名是重点）→ 全量测试 → 快进并入主线 → 更新工作树登记。推送需用户单独授权。
3. 归属不在本仓库的问题单列移交，不重复派工；跨域归属拿不准先与并行任务对齐再动手。

## 第九步：改进本 skill（每场完整复盘收尾时执行）

本场的新经验要回灌到本文件与 references，让 skill 越用越准；但收编有硬性守卫，**防止"对着答案出题"**（把一场的特殊发现当成普遍规律写进清单）：

1. 收编候选 = 本场新发现、且既有清单未覆盖的失效模式 / 统计维度 / 误报教训；既有清单已覆盖的不动。
2. 收编三问，全过才写进正文：**去掉本场事实还能执行吗**（不引用场次、时间戳、具体物品与事件名）；**是既有条目的换皮吗**（重复就合并，不加新条目）；**对下一场可直接执行吗**（能落成明确的检查动作，而不是一句感想）。
3. 抽象层级基准：正文写"检查某类失真"，本场的具体案例（时间戳、台词、数字）只留在复盘文档里当证据。
4. 单场收编不超过三条；想收的更多，说明该重组清单而不是继续加长——清单越长，每条被真正执行的概率越低。
5. 反向修剪：复盘文档会记录本场命中了哪些检查点（见报告模板）；发现某条连续两场都没有命中线索时，考虑合并、移入 references 或删除。
6. 收编与修剪的变更走仓库版本管理，正文不写变更记录。
7. 跨场次元复盘：每累计 3–5 场，或用户指派时，做一次跨场次元复盘——覆盖矩阵（哪些场次复盘了/没复盘）、跨场共性问题模式、本 skill 各检查点的实际命中情况——产物落复盘分析目录并更新索引。跨场模式（如"复读是游戏侧零进展的下游症状"）单场复盘看不到，只有拉通多场才浮现。

## 汇报规范

- **开头先有一段说人话的总结**：三五句话、不用问题编号、不用机制术语，讲给"没看这场直播也没读过文档的人"听——这场出了什么事、最重的问题是什么、要修什么。编号与细节从第二层开始。
- **汇报是"结构配方"不是"形容词要求"**：难懂不是靠禁令（"别用黑话"）治的——禁令只管词汇，真正的失败形态是**形状不对**（压缩过度、机制先行、电报体）。硬性配方如下（每条可对着自己的稿子查）：
  1. **"发生了什么"必须是场景叙述**——几点、谁、做了什么、结果如何，带时间戳；机制名、代码路径、字段名只许出现在第二段"说明什么"；
  2. **先给背景，再说变化**——先交代"之前是什么状态"，再说"现在变成什么"，不直接抛机制；
  3. **具体陈述优于抽象标签**——写"把发言里的每个断言逐条对照游戏记录"，不写"完成断言凭据检查"；
  4. **宁用两句长的，不用五句短的**——一个意思不许拆成一串电报式短句；
  5. **机制链按步骤分句**，一句最多两个从句，不许一句串到底；
  6. **自造名词首次出现必带具体例子**；
  7. **不用比喻**（项目既有教训：对该用户不用黑话比喻是记忆里的七犯之一）。
- **"没看懂"的兜底条款**：用户说"没看懂/说人话/解释一下"时，**禁止同义压缩重讲**（"be concise"式删词会产出更短更含糊的残句）。正确动作是**退回去补缺失的前提，从一个具体场景从头讲**（如"讲清这张委托单的一生"），并描述听者状态而非描述输出要求。
- 汇报正文分节：【一句话总结】【修复/改动清单（文件与位置）】【新发现】【待拍板】——修复与新发现不混排，便于用户只核修复。
- **报告里禁出现"未复核 / 未深入调查 / 待查 / 暂不定案（因未调查）"**：交付前对全文扫一遍这些词，每个命中按第四步"存疑三出口"处置——查掉、转问用户、或改写为"已调查至数据边界"。挂着"待查"交付，等于承认报告不完整却仍在下判断。
- 平实语言：不用项目自造词与工程缩语，术语首次出现就地用一句直白话解释；判定标准是"没有前置知识的人能否看懂"，不以"对方也用过这个词"为豁免。
- 修正自己此前的结论时明说"之前说错了，实际是……"。
- 待拍板事项集中列出等用户圈选，不静默开工。

## 踩坑清单（每场复盘收尾前过一遍）

按根源分三族。**复盘者的立场坑是最高频的一族**——复盘者会不自觉替主播辩护、给这场直播写影评；事故调查的立场是：每条正面结论先找反证，每条"属实"核口径归属。

**一、立场坑（替被审计方辩护）**

| 坑 | 教训 |
|----|------|
| 效果判断无据 | 零观众反馈数据下禁写"好看/节奏好/有节目效果"；只写"结构存在"并注明效果未验证 |
| 采用被审计方口径 | "属实"以世界记录为事实源；主播自述与其状态块不是事实源（背包级属实 ≠ 世界级属实） |
| 择优解读 | 证据两可（致谢对象、物体同一性、角色线结局）时写不定式；凡对主播/故事有利的解读都要先找反证 |
| 0 信号反向解读 | 0 弹幕/0 告警是"未验证"的中性信号，不是"无问题"证据，也不是任何审计的免检条件 |
| 既往裁定当免检 | 引用用户既往裁定前核其适用边界（针对矫枉的裁定不是通用法则）；裁定的前提条件（如"要言之有物"）要单独核 |
| 结构事实升格 | 跨场呼应/叙事结构/角色线只能记为"可回查地发生了"，不能记为好样本效果 |

**二、证据层坑（在第一层停手）**

| 坑 | 教训 |
|----|------|
| 行为层即定级 | "没理会某信息"必须下钻注入层（请求全文）与感知层（观察载荷）才定级，见第四步第 5 条 |
| 告警层当分析完成 | 基础设施专项要到句子/帧级定位，告警计数不算结论 |
| 中间态误判 | 查记录前确认进程状态与查询时点，引用最终状态 |
| 历史结论复核 | 引用既往复盘或机制自称的"零告警/已验收"前，用原始日志按条数复核 |
| 设计误报 | 疑点先读代码定性，"看似缺陷"常是文档化行为 |
| 重试误判 | 首试失败不等于最终失败，看重试循环的最终结果 |
| 对端过时 | 引用对端仓库状态前先拉最新；归属结论注明对端版本或时点 |
| 物体同一性无据 | "睡的就是那张床""这就是那个实体"必须有位置/时间/ID 佐证，叙事需要不构成证据 |

**三、计数坑（数字怎么错的）**

| 坑 | 教训 |
|----|------|
| 截断输出当全量 | `head` 砍掉的尾部必须补查；聚类输出先看总数再看首屏 |
| 首个匹配当目标 | 文本抽取先校准匹配落在哪个区块（历史清单 / 实时状态 / 对话历史），再下结论 |
| 抽样当普查 | "N/N 全成"类断言核到每条的 status 字段；抽样只能写"下限估计" |
| 单文件当全场 | 按小时轮转的日志跨文件合并后再计数 |
| 量级编造 | 频率/成本主张先跑统计再写进报告 |
| 检测脚本盲扫 | 自写脚本先拿已知正样本校准（正例能检出、负例不误报）再跑全量；两场数字完全相同、计数与原始文件对不上，先疑脚本 |
| 同名字段双形态 | 感知载荷里同名 key 可能有两种结构（如实体在场条目 vs 实体"没看到"状态跟踪条目）：解析前先采样两种形态各一条再写匹配，只按一种写条件会把另一种漏检或误读 |

**四、流程坑**

| 坑 | 教训 |
|----|------|
| 复述判据不扩展 | 用户给了判据只审那几条是等指令；现成可机核的维度（情绪字段、指导语、时延）要主动跑完 |
| 记忆索引不同步 | 主题记忆更新后索引行同步刷新——索引才是下次会话加载的那一层 |
| 难懂汇报（三形态） | ①**黑话词**：自造词/工程缩语未就地解释；②**抽象标签压缩**：用机制名代替可执行描述（"完成断言凭据检查"）；③**电报体**：一个意思拆成一串短句。治法是结构配方（汇报规范七条），不是禁令。 |
| "没看懂"后的错误反应 | 同义压缩重讲（越讲越短越含糊）。正解：从具体场景从头讲 + 补缺失前提；描述听者状态而非输出要求。 |
| 工作树并发 | 开工前先查登记与 reflog、登记占用、禁同树双会话 |
| 对着答案出题 | 收编新经验过三问（去本场事实 / 非换皮 / 可执行），具体案例只进复盘文档；单场想收超过三条就重组清单而不是加长 |
