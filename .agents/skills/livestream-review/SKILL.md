# 直播复盘

对一场已发生的直播（或任意 Agent 运行会话）做事后分析：先用数据量化"发生了什么"，再对疑点逐层深挖、拿到确凿证据，最后沉淀成可领取修复的问题清单，并把本场的新经验回灌给本 skill 自身（见第八步）。纪律只有一条：**每条结论都要有原始证据（日志行、代码位置、统计数字），不确定就标注存疑，不猜。**

## 输入与数据源

分析的全部原料是运行时产物（场次记录表、事件日志、LLM 请求全文、应用日志），它们不入版本管理、只存在于实际运行过的机器上。本仓库的具体路径约定见 [references/data-sources.md](references/data-sources.md)；移植到其他项目时，按"场次记录库 / 事件日志 / 请求全文 / 进程日志"四类结构探测对应位置，流程不变。

场次边界：从会话开始事件到结束事件；缺结束事件时用进程关闭事件确定结束边界，并在报告里注明统计所用的数据来源与查询时刻——结束信息可能由下次启动的兜底补写，**查记录前先确认进程状态与查询时点**（见第四步检查点）。

## 第一步：定位会话 + 概览统计（先量后质）

1. 查数据库里的场次记录表（live_sessions）定位场次号与时间窗；列出当日的日志文件（注意按小时/大小轮转，一场可能跨多个文件）。顺手盘点覆盖缺口：表中已结束、但复盘分析目录没有对应文档的场次，在汇报里列出（只提示，不主动扩工）；时长不足 5 分钟且无观众互动的场次按测试场登记，不展开复盘。
2. 事件类型分布计数——异常量级一眼可见（某类失败事件、求助事件突增）。
3. 生命周期时间线：进程启动/关闭、场次开/结、环节切换、全部警告与错误。记录：进程重启几次、哪些退出没有关闭记录、开播前折腾了多久。
4. 本场数据：发言条数与频率、决策轮数及触发来源分布、发言/沉默比、观众弹幕量与进房数、游戏任务成功/失败计数、礼物/SC/舰长条数。
5. LLM 用量按用途分组（请求记录里的 profile 字段，区分决策、游戏、台词等）：调用量、输入/输出 token、缓存命中率、单笔 prompt 上限。历史单调爬升且全程无回落 = 整理/压缩从未触发——**先读代码确认触发阈值与设计意图再定性**。对照相邻场次时先按 profile+模型名分组核对两场各自实际用的模型——两场之间的一次进程重启就可能伴随模型配置变更，节奏/成本差异先归因模型再谈代码。

第 2、3、4、5 步的机械统计可直接跑 [scripts/overview_stats.py](scripts/overview_stats.py)。

## 第二步：梳理全场内容时间线（游戏事件 ⊕ 发言统一对齐）

以开播到下播为窗，把游戏侧事件（任务变化、里程碑、身体事件、死亡）与全部发言按时间合并成一张时间线，标注三类行：游戏事件、发言、二者矛盾处。时间线是后面所有内容判断的事实底座，先梳理再分析：

1. 逐条发言对照"开口时游戏里刚发生了什么"，对不上处（发言断言 X、游戏记录为 Y）单独标注——叙述与游戏记录的矛盾是虚构断言的直接证据。
2. 同一模板句/同一玩笑结构全场出现几次（如"给某物起名"类桥段）：间隔多远、共多少次、对象是否始终存在。模板句轮转（每次只换几个字）是近邻复读比对抓不到的重复形态，单独计数。
3. 涉及其他进程/对端（如游戏 Mod 服务端）时，把对端日志纳入时间线互证：agent 叙述的事实主张不能只用 agent 侧转述链自证——转述可能在任何一环升格或失真（"范围内没有能睡的床"被转述成"没床"即此类）。
4. 时间线成品随复盘文档归档（阶段划分 + 关键事件 + 关键发言引用 + 矛盾标注），供人工复核与后续场次对照。**完成判定以文档结构为准：复盘文档里必须存在"时间线"章节且矛盾逐条标注（全程确无矛盾也要写明一句）——分析过程中对齐过不等于已归档，归档时降级成散文纪要是本条被连续多场跳过的真实形态，交付前先查文档结构，缺该章节 = 第二步未完成。**

## 第三步：内容分析（发言质量）

发言质量从三个本质角度审视：**信息增量**（说了没说过的东西吗）、**开口时机**（该说不说、不该说却说）、**观众互动**（进房/弹幕/付费被理睬了吗）。下面的清单是既往复盘沉淀的已知失效模式示例——照查，但不限于：

1. 把每条发言与"这条开口之前窗口内到达的新事件"对齐——没有任何新事件支撑的发言就是状态重述，统计占比。
2. 近邻复读：按时间顺序找"十几秒内同一件事说两三遍"的组，保留时间戳与原文对照。
3. 话题聚类：全场发言归到几个话题、各占多少条；找出反复出现的万能填充句。
4. 回放查重机制：如果项目有重复话题检测，用真实发言序列过一遍它，量化"按规则本应拦截多少轮 / 实际拦截多少轮"——这套机制是否生效，用数字说话，工具见 [scripts/gate_replay.py](scripts/gate_replay.py)。
5. 抽查决策环节写给台词生成环节的指导语：它本身是否在复读、是否带了防重复约束。
6. 口癖（同款开头词连发）、数值读数频率。
7. 观众互动核对：进房与弹幕是否被理睬；礼物/SC/舰长是否每笔都有致谢、有无漏谢或重复谢。
8. **好样本也要记**：铺垫回收、跨场呼应、自嘲梗——后续修复不能把好的叙事习惯改没。
9. 收尾核对：直播结束边界前后到达的受理类事件（递话、委派、收尾任务）逐一核对其是否有对应消费输出（发言、任务启动）——受理成功不等于被消化。

## 第四步：疑点深挖（每条必须拿到确凿证据）

对概览发现的每个异常，先按形态关键词检索复盘分析目录的既往文档：命中同形态记录的，标注"与场次N同构"并继承其结论链，只复核增补、不重复深挖；未命中的，沿"事件日志给线索 → 进程日志找原因原文（含堆栈）→ 读代码定机制与阈值"三层逐层查证。以下四条检查点是硬性的，每条结论过一遍：

1. **先假设"可能是有意设计"**：读代码与配置确认语义后再定性。看似缺陷的形态常是文档化行为（终态标记、预算线未到、兜底延迟）——未读代码就报缺陷，是复盘最高频的误报来源。
2. **读机制代码前先锚定当晚实际运行的版本**：工作区当前代码不等于当晚行为——修复可能在场次之后才并入，或已并入但实例没重启。先从提交历史确认当时在跑的版本，再对着那个版本读代码。同日多进程（中途重启）按时段分段锚定；若场内有提交落在进程启动之后，运行代码可能是该提交的**未提交形态**——提交时间晚于进程启动不等于改动没在跑，以日志里的实际行为反推版本，不迷信单一 commit hash。
3. **查数据库/日志前先确认时点**：进程还在运行或刚重启时，看到的是中间态——结束时间可能由下次启动的兜底补写、计数可能尚未 flush。结论引用的必须是最终状态。
4. **判"失败"要看重试后的最终状态**：首试失败 ≠ 最终失败，先确认重连/重试循环是否自愈，再谈"人工解围"或"依赖缺陷"。

另外四条：任何频率/量级主张先跑统计再写，不为叙事凑数字；判定问题归属（本仓库 / 外部依赖 / 第三方服务）必须给证据（如"传输层全程正常完成 → 断点在对端会话层"），涉及对端仓库（如游戏 Mod）的结论要注明对端的版本或时点——对端在自己演进，两天前的归属判断今天可能已反转；**基础设施专项核对**——语音合成（失败/断流/冷启动吞句）、画面采集（断流/长期未更新）、弹幕与游戏链路（中断/重连风暴），这类问题在发言层可能没有症状、只有事件与告警层有痕迹，只看发言就会漏；**任务完成度核对**——游戏任务的成功/失败计数与失败原因分布，连续失败或大面积失败要给归因。

## 第五步：对照既往修复验收

调出上一场的复盘文档：既往修复逐条核对是否复发、是否真生效（要生效证据，如"场内此类告警 0 条"）；历史问题清单（口癖、关键事件叙述缺失、音频断流、启动失败风暴……）逐项标注状态：已修复 / 未复发 / 复发 / 暂缓观察。同时核对上一场文档的"待拍板"区与移交清单的现状：已处置的销项，仍悬置的带原日期在本次报告待拍板区重列——拍板项静默蒸发与误报同样损害复盘的信用。**修复效果的下播验收就以这一步为准。**

## 第六步：写入复盘文档

每场一份分析文档，写进项目的复盘分析目录（gitignored，属内部事务），固定结构见 [references/report-template.md](references/report-template.md)。要点：

- 只写事实与归因；修复完成后在原条目下追加"修复记录"行（含提交标识），不另开文档、不在文末堆变更记录；
- 结论涉及本地编号、内部事件的内容不进提交信息与被跟踪代码——远端读者无从知晓；
- 分析用的临时脚本与中间文件用完即删。

**同时产出可视化复盘页**（WebUI 场次复盘页按此约定读取展示）：写到 `logs/reviews/session-{场次id}-{YYYY-MM-DD}.html`（目录不存在先创建；场次 id 以 `live_sessions` 表为准）。页面只写 HTML 结构与内容——样式与脚本外置，以相对路径引用同目录的 `report.css` / `report.js`：

- 写页面前先确认 `logs/reviews/` 下有这两个文件：缺则从 [assets/](assets/report-template.html)（report.css / report.js / report-template.html 三件套）原样拷贝过去；已存在则直接引用，不覆盖、不改动（模板本身更新不影响已落盘副本）；
- 结构按 [assets/report-template.html](assets/report-template.html) 的九个章节槽位填本场数据，文件头注释写明各槽位填法（形状条/发言刻度的百分比算法等）；
- 文件名前缀 `session-{id}-` 是 WebUI 查找键，不得改动；
- 页面内容与 markdown 文档同源同序（同一分析，两种载体），矛盾行必须用 `.conflict` 样式并编号；
- 填完自查"占位词零残留"；全场无某章节（如测试场无游戏表现表）就整节删除，不留空壳。

## 第七步：修复派工与并入主线（用户拍板后）

1. 方案已定的事项派后台子代理到空闲工作树实施：派工单里写明"开工前先调研确认问题真实存在再动手"（防误报流入实施）；开工前先查工作树登记与 reflog（防双会话并发）、登记占用、做目标文件与在途改动的交集预检；每件修复一笔提交，遵循仓库提交规范。
2. 审阅：逐笔 diff + 提交信息（本地语境、过程标记、署名是重点）→ 全量测试 → 快进并入主线 → 更新工作树登记。推送需用户单独授权。
3. 归属不在本仓库的问题单列移交，不重复派工；跨域归属拿不准先与并行任务对齐再动手。

## 第八步：改进本 skill（每场完整复盘收尾时执行）

本场的新经验要回灌到本文件与 references，让 skill 越用越准；但收编有硬性守卫，**防止"对着答案出题"**（把一场的特殊发现当成普遍规律写进清单）：

1. 收编候选 = 本场新发现、且既有清单未覆盖的失效模式 / 统计维度 / 误报教训；既有清单已覆盖的不动。
2. 收编三问，全过才写进正文：**去掉本场事实还能执行吗**（不引用场次、时间戳、具体物品与事件名）；**是既有条目的换皮吗**（重复就合并，不加新条目）；**对下一场可直接执行吗**（能落成明确的检查动作，而不是一句感想）。
3. 抽象层级基准：正文写"检查某类失真"，本场的具体案例（时间戳、台词、数字）只留在复盘文档里当证据。
4. 单场收编不超过三条；想收的更多，说明该重组清单而不是继续加长——清单越长，每条被真正执行的概率越低。
5. 反向修剪：复盘文档会记录本场命中了哪些检查点（见报告模板）；发现某条连续两场都没有命中线索时，考虑合并、移入 references 或删除。
6. 收编与修剪的变更走仓库版本管理，正文不写变更记录。
7. 跨场次元复盘：每累计 3–5 场，或用户指派时，做一次跨场次元复盘——覆盖矩阵（哪些场次复盘了/没复盘）、跨场共性问题模式、本 skill 各检查点的实际命中情况——产物落复盘分析目录并更新索引。跨场模式（如"复读是游戏侧零进展的下游症状"）单场复盘看不到，只有拉通多场才浮现。

## 汇报规范

- 先结论后细节；每个问题按"发生了什么（现象 + 时间戳）→ 说明什么 → 修什么"三段写。
- 平实语言：不用项目自造词与工程缩语，术语首次出现就地用一句直白话解释；判定标准是"没有前置知识的人能否看懂"，不以"对方也用过这个词"为豁免。
- 修正自己此前的结论时明说"之前说错了，实际是……"。
- 待拍板事项集中列出等用户圈选，不静默开工。

## 踩坑清单（每场复盘收尾前过一遍）

| 坑 | 教训 |
|----|------|
| 中间态误判 | 查记录前确认进程状态与查询时点，引用最终状态 |
| 历史结论复核 | 对照验收引用既往复盘或机制自称的"零告警/已降级/已验收"结论前，用原始日志按条数复核（文档可能漏查，机制的降级/去重承诺可能未生效） |
| 设计误报 | 疑点先读代码定性，"看似缺陷"常是文档化行为 |
| 重试误判 | 首试失败不等于最终失败，看重试循环的最终结果 |
| 量级编造 | 频率/成本主张先跑统计再写进报告 |
| 检测脚本盲扫 | 自写检测/统计脚本先拿已知正样本校准（正例能检出、负例不误报）再跑全量；输出可疑（如两场数字完全相同、计数与原始文件对不上）先疑脚本再疑数据 |
| 对端过时 | 引用对端仓库（如游戏 Mod）的状态、能力或约束前先拉对端最新；归属结论注明对端版本或时点 |
| 黑话汇报 | 含未解释的项目黑话的汇报会被打回 |
| 工作树并发 | 开工前先查登记与 reflog、登记占用、禁同树双会话 |
| 对着答案出题 | 收编新经验过三问（去本场事实 / 非换皮 / 可执行），具体案例只进复盘文档 |
