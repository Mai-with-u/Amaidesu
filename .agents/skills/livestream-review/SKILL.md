# 直播复盘

对一场已发生的直播（或任意 Agent 运行会话）做事后分析：先用数据量化"发生了什么"，再对疑点逐层深挖、拿到确凿证据，最后沉淀成可领取修复的问题清单，并把本场的新经验回灌给本 skill 自身。纪律只有一条：**每条结论都要有原始证据（日志行、代码位置、统计数字），不确定就标注存疑，不猜。**

复盘要看的是结果，不是步骤走没走全：结论判得对不对、问题找得全不全、上次修的生效没有。下面的步骤都服务于这三件事。

## 输入与数据源

分析的全部原料是运行时产物（场次记录表、事件日志、LLM 请求全文、应用日志），它们不入版本管理、只存在于实际运行过的机器上。本仓库的具体路径约定见 [references/data-sources.md](references/data-sources.md)；移植到其他项目时，按"场次记录库 / 事件日志 / 请求全文 / 进程日志"四类结构探测对应位置，流程不变。

- **场次边界**：从会话开始事件到结束事件；缺结束事件时用进程关闭事件确定结束边界，并在报告里注明统计所用的数据来源与查询时刻——结束信息可能由下次启动的兜底补写，**查记录前先确认进程状态与查询时点**。
- **三个角色**：发言里的第一人称属于主播。运营者（用户）与对端开发者是另外两个角色，常以玩家身份出现在游戏里；谁是谁以本地角色表为准，不把主播的话当成用户的话。
- **说话的链路**（游戏主控期间）：游戏 Agent 写下解说要点 → 主播侧把它拼进状态块 → 回复器润色成正式发言 → 语音出声。每一步都有事件可查；主播说的和游戏里做的不一致时，先定位错在哪一步。

## 第一步：导出素材与概览

1. **先导出，再取数**：`uv run python .agents/skills/livestream-review/scripts/session_export.py --session <场次号>` 按场次记录表的边界，把一场的运行记录整理成标准文件，写进 `.omo/livestream-analysis/tmp/s<场次号>/`（文件清单见脚本文件头的说明）。先读 `summary.md`（数据范围、运行锚点、固定指标、基础设施表、覆盖缺口），再按它"下一步"里给出的命令跑 [scripts/overview_stats.py](scripts/overview_stats.py)（事件类型分布、生命周期、本场数据、模型用量与费用）。写进结论的数字，这两个来源有的就从这里取；需要另算的，先拿一条已经知道对的结果校准自己的查询，再跑全量。
2. **读出概况**：生命周期——进程重启几次、哪些退出没有关闭记录、开播前折腾了多久；本场数据——发言条数与频率、决策轮数及触发来源、观众弹幕量与进房数、目标的成功/失败/取消数、礼物/超级留言/舰长条数；模型用量按用途——调用量、输入与输出 token、缓存命中率、单笔 prompt 上限、费用（注明统计窗口是进程启动起还是开播起）。用量里历史单调爬升且全程无回落 = 整理/压缩从未触发——**先读代码确认触发阈值与设计意图再定性**。
3. **锚定当晚实际运行的环境**：工作区当前代码不等于当晚行为——修复可能在场次之后才并入，或已并入但实例没重启。跑这一场的是开播前**最后一次**进程启动，不是当晚第一次；以 `summary.md` 给出的启动时刻为起点，对着那个时刻读代码。同日多进程按时段分段锚定；提交时间晚于进程启动不等于改动没在跑，以日志里的实际行为反推版本。**运行配置（引擎、模型、开关）与版本同源同刻锚定**：取该次启动行里的装配信息，不从早前实例的日志行或配置文件现值推断。
4. **覆盖缺口**：`summary.md` 列出的"已结束但复盘目录里没有文档"的场次，在汇报里提一句（只提示，不主动扩工）；时长不足 5 分钟且无观众互动的场次按测试场登记，不展开复盘。
5. **对照相邻场次先核配置**：按用途与模型名分组核对两场各自实际用的模型——两场之间的一次进程重启就可能伴随模型或提示词/行为参数的配置变更，节奏/成本差异先归因配置变更再谈代码。

导出目录可以随时重新生成，复盘结束后删除；承重数字在文档里注明来自哪个导出文件或哪条查询，保证他人可复算。

## 第二步：梳理全场内容时间线

以导出目录的 `timeline.txt` 为底，把游戏侧事件（目标受理与终态、里程碑、身体事件、死亡）与全部发言按时间对齐，标注三类行：游戏事件、发言、二者矛盾处。时间线是后面所有内容判断的事实底座，先梳理再分析：

1. 逐条发言对照"开口时游戏里刚发生了什么"，对不上处（发言断言 X、游戏记录为 Y）单独标注——叙述与游戏记录的矛盾是虚构断言的直接证据。**矛盾判定的事实源是世界记录**（感知载荷、事件、对端日志），主播自述按"背包级/世界级"分级：背包级字面属实不等于世界级属实，后者才是观众听到的断言。
2. 同一模板句/同一玩笑结构全场出现几次（如"给某物起名"类桥段）：间隔多远、共多少次、对象是否始终存在——**对象是否存在要逐轮查感知实体列表**，实体离场在感知里是静默（只报在场不报离场），主播继续对已离场/已死亡实体说话是时间线矛盾行。
3. 涉及其他进程/对端（如游戏 Mod 服务端）时，把对端日志纳入时间线互证：agent 叙述的事实主张不能只用 agent 侧转述链自证——转述可能在任何一环升格或失真（"范围内没有能睡的床"被转述成"没床"即此类）。
4. 时间线成品随复盘文档归档（阶段划分 + 关键事件 + 关键发言引用 + 矛盾标注），供人工复核与后续场次对照。**完成判定以文档结构为准：复盘文档里必须存在"时间线"章节且矛盾逐条标注（全程确无矛盾也要写明一句）——分析过程中对齐过不等于已归档，归档时降级成散文纪要是本条被连续多场跳过的真实形态，交付前先查文档结构，缺该章节 = 第二步未完成。**

## 第三步：内容分析（先言行一致，再两轴审计，子代理并行）

### 言行一致：游戏里的行动和主播说的话对不对得上

以**游戏行动**为主键，不从发言出发。`alignment.txt` 已经列出两类要核对的情形——目标已以失败或取消结束、解说紧随其后；解说出口时目标还没有结果——逐条读原文定性。五种形态（内容不符 / 时序错位 / 该说的没说 / 说了没做 / 状态不同步）的认法与取证处见 [references/speech-audit-criteria.md](references/speech-audit-criteria.md) 第零组。

四段时延每场从 `summary.md` 抄数进文档：目标提交到解说出口、解说到正式发言、发言到出声、宣告到行动（提前量，人工量）。**"说晚"既不并进"与事实偏离"，也不剔除不报**——它是独立的一类，量出来交用户判断。

定性时写明不一致出在哪一步：解说要点与它自己的行动回执不符（游戏 Agent），还是正式发言把解说要点说反了（回复器润色）。时刻先后只是框架层的事实——模型写解说时有没有看到终态回执，要回请求全文核对。

### 两轴审计

发言质量审计分两轴，**分开分析、分开报告，一轴不替另一轴背书**：

- **轴 A：客观内容审计**（判据见 [references/speech-audit-criteria.md](references/speech-audit-criteria.md)）——只依赖发言文本与运行记录，不依赖互动数据。判据分五组：事实与状态（与事实偏离 / 前后矛盾 / 实体同一性 / 时空与状态自洽）、承诺与因果（宣布-兑现闭环 / 悬念闭合 / 因果归因）、社交与情感（不合时宜的玩梗 / 情绪-事件极性 / 对象指向）、信息与重复（话题重复 / 信息新鲜度 / 造梗前提）、机制与跨场（递话消化率 / 历史密度 vs 新鲜感知 / 备忘录事实错误率——备忘录错误会带进下场，优先级高于单条发言）。判"属实/偏离"以**世界记录**为事实源，主播自述与其状态块不构成事实源；修辞豁免（明显不可能为真的夸张）须显式写明理由。
- **轴 B：互动行为**——B 站侧：进房响应率与时延、弹幕回应对齐、付费致谢完整性；游戏内真人侧：游戏公屏消息的回应与对象、肢体互动（扔东西、蹲起、挥手）的接收与致谢、他人死亡与进退服的表态。核对的是行为有没有做，不是效果好不好。
- **效果判断**（"好看/节奏好/有节目效果"）不属于任何一轴：零观众反馈数据（0 弹幕）时禁止写任何效果结论，只允许写"结构存在"（某结构可回查地发生了）并注明效果未验证。

### 子代理并行审计

- **派工单只写四样**：任务一句话、导出目录里的数据文件路径、判据表路径、产出上限。不写数字，不写判断；需要背景就给原始文件的路径。数据文件给整场导出，不按时间截取——截过的窗口会变成子代理的盲区。
- 轴 A、轴 B、基础设施专项各派一个子代理，每个只带自己的派工单，不带入主会话的任何中间结论——主会话积累的叙事印象（"这场不错"）是审计偏置的源头，子代理没有这个包袱。
- **子代理失败、超时或迟迟不回时**：重派，或在汇报里写明"这一项没有完成"。主会话不顶替，不默认已覆盖。
- 主会话汇总时按轴分报，**两轴发现冲突时不折衷、并排呈现**。子代理的产出同样是待验证主张，进文档前照走第四步的三级证据链，不因"子代理说的"免检；其中**涉时刻的结论（"早于/晚于某事件"）一律用精确时戳复核**——用时间窗口近似定位回执时，回执常被归入下一个发言的窗口，产生系统性滞后误判。

机械统计从 `summary.md` 的固定指标取（发言与解说条数、情绪分布、长静默、出声时延、负面事件后的表态、逐字重复），只量不判。逐字重复测不出换词的模板句，模板句与话题重复仍按判据表人工判。另做两项：**收尾核对**——结束边界前后到达的受理类事件（递话、委派、收尾任务）逐一核对消费输出，受理成功不等于被消化；**好样本只记结构事实**，写之前对每条正面结论先找反证（它的结尾是否其实是事故的可见症状）。

## 第四步：疑点深挖（每条必须拿到确凿证据）

对概览发现的每个异常，先按形态关键词检索复盘分析目录的既往文档：命中同形态记录的，标注"与场次N同构"并继承其结论链，只复核增补、不重复深挖；未命中的，沿"事件日志给线索 → 进程日志找原因原文（含堆栈）→ 读代码定机制与阈值"三层逐层查证。以下检查点是硬性的，每条结论过一遍：

1. **先假设"可能是有意设计"**：读代码与配置确认语义后再定性。看似缺陷的形态常是文档化行为（终态标记、预算线未到、兜底延迟）——未读代码就报缺陷，是复盘最高频的误报来源。
2. **读机制代码前先锚定当晚实际运行的版本**（按第一步的锚点）：提交时间晚于进程启动不等于改动没在跑，不迷信单一 commit hash。
3. **查数据库/日志前先确认时点**：进程还在运行或刚重启时，看到的是中间态——结束时间可能由下次启动的兜底补写、计数可能尚未 flush。结论引用的必须是最终状态。
4. **判"失败"要看重试后的最终状态**：首试失败 ≠ 最终失败，先确认重连/重试循环是否自愈，再谈"人工解围"或"依赖缺陷"。"按 X 建了一部分/失败"类回执之后可能紧跟一个新目标把同一件事做完——判"虚报完成"前必须把失败回执到发言时刻之间的全部新目标终态查完；判"宣告无据"同理向后看——宣告时点之后到统计截止之间的回执也要查完再定性。
5. **存疑的出口只有三个**：①**当场查掉**——知道哪块没查就先查，"未复核/待深挖"不构成交付状态；②**数据不存在**——日志里根本没有的（只有直播时能看到的现象、无记录的人工决策），转"问用户"清单；③**已调查至数据边界**——写明查到了什么、为什么再查不下去（如"日志未记录该次交互的坐标"）；"没回溯""没读代码"不算数据边界。这三种之外不存在第四种状态。把调查义务写成"待查"挂在报告里，是把义务转给读者，且旁边的判断可能已被它带偏。
6. **三级证据链齐了才定级**："主播没理会某信息"类疑点，行为层（发言/行动里无引用）只是线索，必须再下钻两层：**注入层**——请求全文检索这条信息进没进模型、进了多少笔、存续多久（两条同类递话一条注入几十笔一条只注入一笔，本身就是缺陷）；**感知层**——观察/速览原始载荷里这个事实在不在（关键物体从未进感知与"看了没理"是两种事故，归属不同）。缺一级就定级，严重度只会被系统性低估。基础设施专项同理：告警计数层不算分析完成，要下钻到"哪一句/哪一帧"。
7. **归因到代码或数据层的第一因，才写修复方向**。"模型说错了""它没理会"停在行为层时，先读模型当时拿到的输入——工具报错原文、流程单环节的任务描述、提示词条款、对端回执——回答"它为什么会这么写"；用模型当时的感知载荷还原它看到的世界，再和人在现场看到的对照，两边对不上就是根因候选（现场只有用户能看到时，先自己还原一遍再请用户核对）。发言形态在流程单环节切换点突变时，先读该环节的任务描述。归因没到这一层时，"修复方向"栏写"归因未到位"，不出方案——建在半路归因上的方向会连带把对的方向否掉。

另外四条：任何频率/量级主张先跑统计再写，不为叙事凑数字；**判定问题归属前先问"是谁的动作顺序造成的"**——本仓库 / 外部依赖 / 第三方服务的归属必须给证据（如"传输层全程正常完成 → 断点在对端会话层"），对端行为符合它的设计时不向对端提底层改动，涉及对端仓库（如游戏 Mod）的结论要注明对端的版本或时点——对端在自己演进，两天前的归属判断今天可能已反转；**基础设施专项核对**——语音合成（失败/断流/冷启动吞句）、画面采集（断流/长期未更新）、弹幕与游戏链路（中断/重连风暴），这类问题在发言层可能没有症状、只有事件与告警层有痕迹，只看发言就会漏；**任务完成度核对**——游戏任务的成功/失败计数与失败原因分布，连续失败或大面积失败要给归因。

## 第五步：对照既往（修复验收、未决项、远端已修）

调出上一场的复盘文档，做三件事：

- **修复验收**：既往修复逐条核对是否复发、是否真生效（要生效证据，如"场内此类告警 0 条"）；历史问题清单（口癖、关键事件叙述缺失、音频断流、启动失败风暴……）逐项标注状态：已修复 / 未复发 / 复发 / 暂缓观察。**修复效果的下播验收就以这一步为准。**
- **未决项带首次提出的场次**：上一场文档"待拍板"区与移交清单逐条核对现状——已处置的销项，仍悬置的带首次提出的场次原样重列（"自场次N起"）。拍板项静默蒸发与误报同样损害复盘的信用。对端移交项写三态：对端已修 / 已部署 / 场内验收。
- **对照远端与对端已修**：写待拍板之前先拉本仓库与对端仓库的最新状态，给每条候选问题标注"远端已修 / 部分修 / 未修"及是否已部署——两位开发者的修复在两场之间落地是常态，已修的不再列为待拍板。仓库里有提交不等于运行实例已部署。

## 第六步：写复盘文档、独立核对、汇报

**产出顺序**：markdown 初稿 → 独立核对 → 客观性自查 → 向用户汇报。讨论轮次不做网页等附加产物。

每场一份分析文档，写进项目的复盘分析目录（gitignored，属内部事务），固定结构见 [references/report-template.md](references/report-template.md)。要点：

- 只写事实与归因；修复并入后把提交号写回对应条目（见第七步），不另开文档、不在文末堆变更记录；
- 结论涉及本地编号、内部事件的内容不进提交信息与被跟踪代码——远端读者无从知晓；
- 分析用的临时脚本与中间文件用完即删。

**红队盲审是条件必做**：文档里有 P1 或 P2 条目，首次汇报之前必须派一个不带本会话上下文的子代理，只给判据清单、自查清单与文档路径，独立找问题；与主分析对比，差集即主分析的盲区，逐条处置（采纳或驳回并说明理由）——自查清单由分析者本人编写，只覆盖已知失效模式，盲审补未知的未知。只有 P3 的场可以不做。

**客观性自查是交付硬门**：初稿写完、汇报之前，对整份复盘逐项过 [references/objectivity-selfcheck.md](references/objectivity-selfcheck.md)（A 断言 / B 证据链 / C 统计方法 / D 立场 / E 交付卫生五组，每条是可对着成品验证的问句）。在复盘文档"复盘自查"节**写出实际查出的项与改动**——只写"已逐项自查通过"不构成自查。自查与主分析出自同一个模型，所以自查节末尾固定写三行计数：审计子代理改掉几条初判、红队改掉几条、用户改掉几条——这三行是复盘自身质量的趋势指标。

**向用户汇报必带三件事**（分节：【一句话总结（说人话）】【修复/改动清单】【新发现】【待拍板】）：

1. **"问用户"清单**——只有直播时才能确认、或日志里根本没有的现象，列出来问，不写"建议复核"了事。每条定稿前过**三闸**，任一不过即删：①**决策价值闸**——先写一行"答案改变哪个结论/哪个决定"，写不出就不问；日志已定案的事实不问感知路径（"你怎么知道的/是看到的还是猜的"），涉及用户主管的系统（账户、服务器、配置）不设"你是猜的吗"式设问。②**听感闸**——TTS/音频听感、画面观感类永不主动问（用户有问题自己会说），只有日志里出现明显异常时才在报告中提该异常本身。③**主动意图闸**——用户主动做的操作（改配置、开关、开播设置）不问"是不是有意的"。合法问句剩四类：日志验证不了的客观实态（先自己机核过才可问）、只有用户知道的事实（物品去向、无记录的人工决策）、**关键场景的现场核对**（日志能还原模型看到的世界，人当时看到的现场只有用户能提供；先自己还原一遍，再请用户对照）、归属移交前需用户确认的结局。
2. **存疑推断清单**——所有标了"存疑/不定式"的点集中列出，请用户确认或提供只有用户知道的信息。
3. **待拍板事项**——等用户圈选，不静默开工。

**可选产出**（可视化复盘页等）默认不做，汇报里不提。用户认为有必要时会提出，做法见 [references/report-page.md](references/report-page.md)；AI 可以建议一次，不索要授权。

## 第七步：修复派工与并入主线（用户拍板后）

1. 方案已定的事项派后台子代理到空闲工作树实施：派工单里写明"开工前先调研确认问题真实存在再动手"（防误报流入实施）；开工前先查工作树登记与 reflog（防双会话并发）、登记占用、做目标文件与在途改动的交集预检；每件修复一笔提交，遵循仓库提交规范。
2. 审阅：逐笔 diff + 提交信息（本地语境、过程标记、署名是重点）→ 全量测试 → 快进并入主线 → 更新工作树登记 → **把提交号写回复盘文档里对应的问题条目**。推送需用户单独授权。跨会话完成的修复，由下一场复盘在修复验收时补写。
3. 归属不在本仓库的问题单列移交，不重复派工，移交清单每条都要有证据；跨域归属拿不准先与并行任务对齐再动手。

## 第八步：改进本 skill

本场的新经验要回灌到本文件与 references，让 skill 越用越准；**在首次汇报之前执行，不等会话收尾**——会话通常在汇报后转入设计讨论，不再回来；用户纠正后出现的新失效模式当场补收编。收编有硬性守卫，**防止"对着答案出题"**（把一场的特殊发现当成普遍规律写进清单）：

1. 候选有三处：本场新出现、既有清单没覆盖的失效模式或统计维度；本场被用户或独立核对（审计子代理、红队）纠正的结论，逐条问"当初为什么错"；独立核对抓到而主分析漏掉的问题。既有清单已覆盖的不动。
2. 收编三问，全过才写进正文：**去掉本场事实还能执行吗**（不引用场次、时间戳、具体物品与事件名）；**是既有条目的换皮吗**（重复就合并，不加新条目）；**对下一场可直接执行吗**（能落成明确的检查动作，而不是一句感想）。
3. 抽象层级基准：正文写"检查某类失真"，本场的具体案例（时间戳、台词、数字）只留在复盘文档里当证据。
4. 单场收编不超过三条；想收的更多，说明该重组清单而不是继续加长——清单越长，每条被真正执行的概率越低。
5. 收编与修剪的变更走仓库版本管理，正文不写变更记录。
6. 反向修剪不在单场做（单场缺跨场的命中记录）。合并、移走、删除条目放在跨场次元复盘里，按"近几场有没有靠它抓住过真问题"决定。
7. 跨场次元复盘：每累计 3–5 场，或用户指派时做一次——覆盖矩阵（哪些场次复盘了/没复盘）、跨场共性问题模式、各检查点与踩坑条目的实际命中情况、未决项挂了几场、每个问题条目的去向（定案、修复、验收、蒸发）。**元复盘的产物是待执行的 skill 改动清单**，下一次元复盘先核对上一次清单的执行情况。产物落复盘分析目录并更新索引。跨场模式（如"复读是游戏侧零进展的下游症状"）单场复盘看不到，只有拉通多场才浮现。

## 汇报规范

- **开头先有一段说人话的总结**：三五句话、不用问题编号、不用机制术语，讲给"没看这场直播也没读过文档的人"听——这场出了什么事、最重的问题是什么、要修什么。编号与细节从第二层开始。
- **汇报是"结构配方"不是"形容词要求"**：难懂不是靠禁令（"别用黑话"）治的——禁令只管词汇，真正的失败形态是**形状不对**（压缩过度、机制先行、电报体）。硬性配方如下（每条可对着自己的稿子查）：
  1. **"发生了什么"必须是场景叙述**——几点、谁、做了什么、结果如何，带时间戳；机制名、代码路径、字段名只许出现在第二段"说明什么"；
  2. **先给背景，再说变化**——先交代"之前是什么状态"，再说"现在变成什么"，不直接抛机制；
  3. **具体陈述优于抽象标签**——写"把发言里的每个断言逐条对照游戏记录"，不写"完成断言凭据检查"；
  4. **宁用两句长的，不用五句短的**——一个意思不许拆成一串电报式短句；
  5. **机制链按步骤分句**，一句最多两个从句，不许一句串到底；
  6. **自造名词首次出现必带具体例子**；
  7. **不用比喻**（项目既有教训：对该用户不用黑话比喻是记忆里的七犯之一）。
- **"没看懂"的兜底条款**：用户说"没看懂/说人话/解释一下"时，**禁止同义压缩重讲**（"be concise"式删词会产出更短更含糊的残句）。正确动作是**退回去补缺失的前提，从一个具体场景从头讲**（如"讲清这张委托单的一生"），并描述听者状态而非描述输出要求。
- 汇报正文分节：【一句话总结】【修复/改动清单（文件与位置）】【新发现】【待拍板】——修复与新发现不混排，便于用户只核修复。
- **报告里禁出现"未复核 / 未深入调查 / 待查 / 暂不定案（因未调查）"**：交付前对全文扫一遍这些词，每个命中按第四步"存疑三出口"处置——查掉、转问用户、或改写为"已调查至数据边界"。挂着"待查"交付，等于承认报告不完整却仍在下判断。
- 平实语言：不用项目自造词与工程缩语，术语首次出现就地用一句直白话解释；判定标准是"没有前置知识的人能否看懂"，不以"对方也用过这个词"为豁免。
- 修正自己此前的结论时明说"之前说错了，实际是……"。
- 待拍板事项集中列出等用户圈选，不静默开工。

## 踩坑清单（每场复盘收尾前过一遍）

按根源分四族。只收别处没有的条目：与自查清单、汇报规范、AGENTS.md 重复的，以及已经改进脚本解决的，不在这里重复。**复盘者的立场坑是最高频的一族**——复盘者会不自觉替主播辩护、给这场直播写影评；事故调查的立场是：每条正面结论先找反证，每条"属实"核口径归属。

**一、立场坑（替被审计方辩护）**

| 坑 | 教训 |
|----|------|
| 采用被审计方口径 | "属实"以世界记录为事实源；主播自述与其状态块不是事实源（背包级属实 ≠ 世界级属实） |
| 择优解读 | 证据两可（致谢对象、物体同一性、角色线结局）时写不定式；凡对主播/故事有利的解读都要先找反证 |
| 0 信号反向解读 | 0 弹幕/0 告警是"未验证"的中性信号，不是"无问题"证据，也不是任何审计的免检条件 |
| 既往裁定当免检 | 引用用户既往裁定前核其适用边界（针对矫枉的裁定不是通用法则）；裁定的前提条件（如"要言之有物"）要单独核 |

**二、证据层坑（在第一层停手）**

| 坑 | 教训 |
|----|------|
| 告警层当分析完成 | 基础设施专项要到句子/帧级定位，告警计数不算结论 |
| 告警淹没 | 同一句错误逐轮重复几十上百次，是"每轮都在发生的静默缺陷"的唯一痕迹（兜底吞异常类缺陷尤其如此）：WARNING 先按归并文本计数，高频同文的单独立查，不当背景噪声放过 |
| 中间态误判 | 查记录前确认进程状态与查询时点，引用最终状态 |
| 历史结论复核 | 引用既往复盘或机制自称的"零告警/已验收"前，用原始日志按条数复核 |
| 设计误报 | 疑点先读代码定性，"看似缺陷"常是文档化行为 |
| 重试误判 | 首试失败不等于最终失败，看重试循环的最终结果——"按 X 建了一部分/失败"类回执之后可能紧跟一个新目标把同一件事做完，判"虚报完成"前必须把失败回执到发言时刻之间的全部新目标终态查完；判"宣告无据"同理向后看——宣告时点之后到统计截止之间的回执也要查完再定性 |
| 对端过时 | 引用对端仓库状态前先拉最新；仓库有提交 ≠ 运行实例已部署（jar/服务类尤其如此），"已生效/未生效"一律以场内回执行为反推；归属结论注明对端版本或时点 |
| 回执源单一 | 判"宣告无回执"前把互动事件层一并查完——玩家投掷类互动是实物转移的世界记录，而走位拾取常不产生任务回执；只对齐任务/里程碑表会漏掉实物证据，把属实断言误判成无据 |
| 物体同一性无据 | "睡的就是那张床""这就是那个实体"必须有位置/时间/ID 佐证，叙事需要不构成证据 |
| 感知条目当实时状态 | 感知载荷里的设施/地标条目可能是注册表缓存而非实时扫描——实体早已移除，条目仍"查询成功"全程在列；用它裁断"某物在不在"前，先与玩家口述/对端语义互证，冲突时勿单边采信 |
| 账本"已执行"当现行一致 | 迁移/升级类账本只证明"登记过"，不证明登记时的内容与现行文件一致（同版本号可能被半成品先占）——用版本记录下结论前，与独立物证交叉验证（如迁移前备份的文件名时间戳、备份库内的列状态） |
| 能力缺口 vs 没用上 | 判"某能力缺失/损坏"前先数该能力的实际调用次数：零调用说明可能只是没人用过（不会用/不知道），修的方向从"修能力"变成"教用法"，归属判定完全不同 |
| 功能落地时序未核 | 下"未生效/未触发"结论前先核功能落地时点与本场数据产生时点的先后：功能后到 = 无数据可验，写"未达可验证状态"而非缺陷（结算类产物尤其要核它跑在功能并入之前还是之后） |
| 长时活动零回执当矛盾 | 发言声称持续了一段时间的活动（找了很久/跑了半天）但窗内零回执时，先确认该活动类型是否属不产出回执的后台目标（漫游/巡逻/长时移动类），再在"矛盾"与"回执缺失"之间定性；后者只能记存疑，不定性矛盾 |
| 转述定矛盾 | 判"前后矛盾"前引原句全文对照，不以子代理转述或摘句为判定依据——一句话可同时含两个并存陈述（整体在运转 + 局部卡住），拆开读会制造假矛盾 |

**三、计数坑（数字怎么错的）**

| 坑 | 教训 |
|----|------|
| 同名字段双形态 | 感知载荷里同名 key 可能有两种结构（如实体在场条目 vs 实体"没看到"状态跟踪条目）：解析前先采样两种形态各一条再写匹配，只按一种写条件会把另一种漏检或误读 |
| 重复事件当重放或缺陷 | 诊断同刻同载荷的重复事件先排合法并发（并发的相同调用会回相同结果），再查双进程混写（进程重启后旧进程残留时新旧日志写同一文件，同游标成对出现的日志行是实证），最后才怀疑对端重放 |
| 两源对账口径未对齐 | 两个数据源对账前先对齐拆行口径（连发批次一侧按累计行、一侧按单包行很常见），口径对齐后逻辑总量一致即判定对上，逐条时刻差 1 秒不算对不上 |

**四、流程坑**

| 坑 | 教训 |
|----|------|
| 流程规则只进记忆不进 skill | 直接约束复盘产出形态的裁定（如问用户清单的编制纪律），正确位置是本 skill 正文——skill 每场必然加载，记忆召回是概率性的 |
| 归因停在模型行为层 | 发言模板化/复读的根因排查要下探到提示词措辞本身：举例式并列（"A 还是 B，从这里推"）会被模型读成封闭菜单收窄行为空间，扫描"两种/只有/必须换一个"等排他语；修复方向是开放语（"常见的有…不限于此"），不是加禁令 |
| 跨 agent 归属想当然 | 归因"主播为什么没做 X"前先核对动作归哪个组件执行：委派出去的游戏操作属游戏 Agent，主播 Agent 没在忙——"正埋头干活所以没顾上"这类解释先验证架构归属再写进报告 |
