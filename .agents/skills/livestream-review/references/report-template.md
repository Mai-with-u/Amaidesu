# 复盘文档模板

> 保存位置：项目的复盘分析目录（gitignored，属内部事务；本仓库为 `.omo/livestream-analysis/`）。命名 `YYYY-MM-DD-场次N.md`（日期为开播日，N 为场次记录表里的场次号）。每场一份，更新同目录 README 索引表。

```markdown
# 场次N（YYYY-MM-DD HH:MM – HH:MM）直播复盘分析

> 数据来源与统计标准：`data/amaidesu.db`（场次记录表）、`logs/events/…`（事件日志）、
> `logs/llm_requests/…`（LLM 请求全文）、`logs/app/…`（应用日志）。
> 时间已换算本地 UTC+8。查询时间 <时刻>。
> 场次边界说明：<如缺下播事件，注明结束边界如何确定>。

## 一、场次概况

- 场次登记信息、时长、热度/观看数据说明。
- 观众：弹幕、进房、礼物/超级留言/舰长的条数。
- 开播前折腾时长与进程重启情况：跑这一场的进程是哪次启动、当晚启动过几次。
- 运行版本与配置锚点：代码版本、语音服务等装配信息，取自哪一次启动。
- 固定指标（从导出摘要抄录）：发言条数与频率、解说条数、静默、出声时延、目标成败与受理到终态时延、言行对齐两类、负面事件后的发言、逐字重复。
- LLM 用量：各用途（profile）调用量 / 输入（缓存命中率）/ 输出（思考占比）；失败数；单笔 prompt 上限；费用（价格表现算，注明口径与窗口）。
- 对照相邻场次的配置变更（模型、提示词、行为参数）。
- **命中的检查点与新增发现类型**（必填）：本场的哪些问题是被哪条检查点或踩坑条目抓住的，供跨场次元复盘决定条目的去留。

## 二、内容时间线（阶段划分）

> 游戏事件与发言按时间对齐。三类行——游戏 / 发言 / **矛盾**；矛盾一条不漏。
> 交付前自查：本章节存在、矛盾行逐条可回查（全程确无矛盾也要写明"全程未发现矛盾"）——缺本章节 = 时间线步骤未完成。

### 阶段一：<名称>（HH:MM–HH:MM）

- `[HH:MM:SS]` 游戏：<事件原文摘要>
- `[HH:MM:SS]` 发言："<发言摘要>"
- `[HH:MM:SS]` **矛盾**：发言断言 X，游戏记录为 Y（<证据指针：日志行/事件类型>）

### 阶段二：<名称>（HH:MM–HH:MM）

- …

## 三、言行一致

> 以游戏行动为主键。导出摘要列出的两类核对情形逐条读过之后的结论。
> 先写一句总数（核对多少条、成立多少条），再列成立的；四段时延跟在表后。

| 时刻 | 目标（编号、终态） | 解说或发言原文 | 形态 | 出在哪一步 | 证据 |
|---|---|---|---|---|---|
| HH:MM:SS | #N，失败 | "<原文>" | 内容不符 / 时序错位 / 该说的没说 / 说了没做 / 状态不同步 | 游戏 Agent 的解说要点 / 回复器润色 | 日志行或请求全文位置 |

- 四段时延：目标提交到解说出口 <数>、解说到正式发言 <数>、发言到出声 <数>、宣告到行动 <数>。

## 四…N、问题条目（P0/P1/P2/P3 分级，从最重开始）

## N、发言内容审计（两轴分开：轴 A 客观内容按 speech-audit-criteria 逐条过；轴 B 互动行为，B 站侧与游戏内真人侧分列）

> 每条发现带时间戳与原文；"属实"注明口径归属（世界记录）；无观众反馈数据时本节不写效果判语。

## N、基础设施专项

> 导出摘要里的基础设施表（语音配对、工具回执与错误码、告警归并、连接类事件）加上下钻到句子级的结论；告警计数本身不是结论。

## N、验证为健康（对照既往问题清单）

| 既往问题 | 本场状态 |
|---------|---------|

## N、未决项与远端已修对照

| 事项 | 首次提出 | 现状 | 本场处置 |
|---|---|---|---|
| <待拍板或移交的事项> | 场次M | 远端已修 / 部分修 / 未修；是否已部署；对端已修 / 已部署 / 场内验收 | 销项 / 重列 / 升级为单独议题 |

## N、P3 杂项（不分级的小问题，一条一行）

## N、复盘自查（误报史留档）

> 三部分：①**交付前自查结果**——按 objectivity-selfcheck.md 五组清单逐项过，**列出实际查出的项与改动**（不写"已逐项通过"）；②**误报史**——被复核推翻的结论就地更正、不静默删除，对照 SKILL.md 踩坑清单四族归类；未被检验的区块同样可能有同类偏差，注明；③**三行计数**——审计子代理改掉几条初判、红队改掉几条、用户改掉几条。用户指正后重跑清单，漏检项回填清单修订。

## N、待拍板（按归属分列）

> 对端的问题单列移交，不重复派工，每条移交都要有证据。

**Amaidesu 侧候选修复项**

1. …

**维持不动 / 已核实非缺陷**

- …

**问用户清单**（每条过了三闸；含请用户核对的关键场景）

**存疑推断清单**（写明每条已调查到的边界）
```

## 问题条目写法

- 标题 = 一句话概括现象与根因，带严重度编号。
- 事实链：带时间戳的证据序列，每条都可回查（日志行/代码位置/统计数字）。
- 影响：说清观众视角与成本/时延的后果。
- 修复方向：归因到代码或数据层的第一因之后才写；没到位的写"归因未到位"，不出方案。给方案选项时标注"待拍板"，方案唯一时直接写。

## 数字口径备查

写进结论的承重数字，在文档里留一节各记一行：数值、来自哪个导出文件或哪条查询。导出目录用完即删，凭这一节能重算；固定指标直接写"见导出摘要的 <指标名>"，不另定口径。

## 追加修复记录

修复并入后，在对应条目末尾追加一行（不另开文档、不在文末堆变更记录）：

```markdown
> **修复记录（YYYY-MM-DD）**：<提交 hash>——<一句话说明>。验收：<下次直播的核对点>。
```

## 定性纪律

- 写进"问题条目"前过一遍 SKILL.md 第四步的检查点：设计意图查了吗、查询时点对吗、重试最终状态确认了吗、归因到第一因了吗。
- 被复核推翻的结论**就地更正**（条目内加"更正"注记），不静默删除——误报史本身就是防误报的教材。
- 本地编号、内部事件细节只写在本目录，不进提交信息与被跟踪代码。
