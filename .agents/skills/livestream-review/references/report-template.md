# 复盘文档模板

> 保存位置：项目的复盘分析目录（gitignored，属内部事务；本仓库为 `.omo/livestream-analysis/`）。命名 `YYYY-MM-DD-场次N.md`（日期为开播日，N 为场次记录表里的场次号）。每场一份，更新同目录 README 索引表。

```markdown
# 场次N（YYYY-MM-DD HH:MM – HH:MM）直播复盘分析

> 数据来源与统计标准：`data/amaidesu.db`（场次记录表）、`logs/events/…`（事件日志）、
> `logs/llm_requests/…`（LLM 请求全文）、`logs/app/…`（应用日志）。
> 时间已换算本地 UTC+8。查询时间 <时刻>。
> 场次边界说明：<如缺下播事件，注明结束边界如何确定>。

## 一、场次概况

- 场次登记信息、时长、热度/观看数据说明。
- 开播前折腾时长与进程重启情况。
- 场内发言 N 条 ≈ N 条/分钟；决策 N 轮（触发来源分布、发言/沉默比）；弹幕与进房。
- LLM 用量：各用途（profile）调用量 / 输入（缓存命中率）/ 输出（思考占比）；失败数；单笔 prompt 上限。
- 命中的检查点与新增发现类型：<供下次复盘修剪检查清单>。

## 二、内容时间线（阶段划分）

> 第二步的成品归档：游戏事件 ⊕ 发言按时间对齐。三类行——游戏 / 发言 / **矛盾**；矛盾一条不漏。
> 交付前自查：本章节存在、矛盾行逐条可回查（全程确无矛盾也要写明"全程未发现矛盾"）——缺本章节 = 时间线步骤未完成。

### 阶段一：<名称>（HH:MM–HH:MM）

- `[HH:MM:SS]` 游戏：<事件原文摘要>
- `[HH:MM:SS]` 发言："<发言摘要>"
- `[HH:MM:SS]` **矛盾**：发言断言 X，游戏记录为 Y（<证据指针：日志行/事件类型>）

### 阶段二：<名称>（HH:MM–HH:MM）

- …

## 三…N、问题条目（P0/P1/P2/P3 分级，从最重开始）

## N、P3 杂项（不分级的小问题，一条一行）

## N、验证为健康（对照既往问题清单）

| 既往问题 | 本场状态 |
|---------|---------|

## N、待拍板（按归属分列）

> Mod 侧 / 外部服务的问题单列移交，不重复派工。

**Amaidesu 侧候选修复项**

1. …

**维持不动 / 已核实非缺陷**

- …
```

## 问题条目写法

- 标题 = 一句话概括现象与根因，带严重度编号。
- 事实链：带时间戳的证据序列，每条都可回查（日志行/代码位置/统计数字）。
- 影响：说清观众视角与成本/时延的后果。
- 修复方向：给方案选项时标注"待拍板"，方案唯一时直接写。

## 追加修复记录

修复并入后，在对应条目末尾追加一行（不另开文档、不在文末堆变更记录）：

```markdown
> **修复记录（YYYY-MM-DD）**：<提交 hash>——<一句话说明>。验收：<下次直播的核对点>。
```

## 定性纪律

- 写进"问题条目"前过一遍误报防范三则（见 SKILL.md 第三步）：设计意图查了吗、查询时点对吗、重试最终状态确认了吗。
- 被复核推翻的结论**就地更正**（条目内加"更正"注记），不静默删除——误报史本身就是防误报的教材。
- 本地编号、内部事件细节只写在本目录，不进提交信息与被跟踪代码。
