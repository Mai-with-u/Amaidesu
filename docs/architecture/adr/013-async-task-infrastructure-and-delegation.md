# ADR-013：异步任务基建与 Agent 委派原语

- 状态：已接受（§3 异步 2026-09-10 定案、§4 委派 2026-09-11 定案；随工具系统重设计实现）
- 日期：2026-09-10 / 2026-09-11（定案）；2026-09-12（落盘）
- 实现提交：待收口回填

## 背景（Context）

四个问题同源：连接和工具**住在哪**（归属）、一个 Agent**能看见什么**（可见性，
ADR-012）、跨轮次的工作**谁在跟**（异步任务）、工作怎么在 Agent 之间**交接**
（委派）。现状四件事各有一半答案且相互打架：异步受理-跟踪只有 minecraft 一家
手工实现（约 160 行 handoff）；委派三通道（命令/结果/查询）缺任务身份——发出去
不知道受理/进行/完成，只能等事件或隔阵查状态。

用户裁决（增强版 B）：受理-跟踪-通知是所有"回执型工具调用"的通用问题，与游戏
无关，提取为工具系统基础设施（先例：ToolHealthMonitor = 框架循环 + provider 适配
器钩子 + 注册表记账 + 事件）。

## 决策（Decision）

核心一句：**任务归执行者（事实源），框架承载跨 Agent 契约（回执 / 查询路由 /
完成事件）；LLM 永不轮询——通知是提示、查询才是事实源。**

### 1. 异步任务基建（六件套，落 `src/modules/tools/`）

- **受理约定**：回执型工具返回结构化结果 `accepted=true + task_id`（回合不阻塞）。
- **任务记录表**：内存 dict（任务号 → 提供者/工具/发起方/执行者/状态/快照/时间）；
  终态移除条目。
- **单写者规则**（按事实源定）：provider 型（真相在外部系统，如 maicraft）由跟踪
  循环唯一写入；agent 型（委派，真相 = 执行 Agent 的状态）由执行 Agent 唯一写入、
  循环查询仅作对账兜底。状态**单调不回退**（终态粘滞）；同状态重复写入幂等、不
  重发事件。
- **跟踪循环**：照 ToolHealthMonitor 形态——后台循环 + 可测单步函数；通知触发 +
  周期兜底双通道；订阅起停归它。
- **适配器**：BaseToolProvider 两个可选钩子（查询适配器 / 通知适配器），默认不
  支持（同 `health_check` 套路）。
- **事件与唤醒**：`task.changed`（仅状态真变化时发；payload 带 task_id / 状态 /
  摘要 / 发起方 / 执行者）；BaseAgent 默认订阅并按 `payload.initiator == self.name`
  过滤唤醒（注入消息，含退订清理）。

### 2. 状态词表

受理 `accepted` → 进行中 `running` → 终态 `{成功 succeeded / 失败 failed /
取消 cancelled / 超时 timeout}`。

### 3. 委派原语（provider=`framework`，单一注册项承载）

- `framework_delegate(agent, 指令)`：名册校验；**禁自派**（受理失败）；受理成功
  回执 `accepted + task_id` 并登记进同一张任务记录表（发起方=调用方、执行者=目标）；
  **受理失败**（目标不存在/未启用/拒收）与**任务失败**（执行中失败）分开。
- `framework_task_status(task_id)`：返回状态 + 快照；未知任务号 → 失败结果。
- 指令只当自然语言（目标，不给步骤）；不加编排/条件分支/回调钩子。
- `BaseAgent` 增"接收委派"入口，**默认拒收**；各 Agent 按需实现（minecraft：
  入队 + 唤醒 + 队列项带任务号——承接原 `minecraft_send_prompt` 职能，该工具退役）。
- 嵌套委派（委派任务 ↔ 内层 maicraft 任务）在快照里带内层任务号。

## 替代方案（Alternatives)

- **各 Agent 手写跟踪**（维持 minecraft handoff 样本）：拒绝。第二个用户（委派）
  已在路上，N 套轮子换一套框架；handoff 的全部好行为（通知=提示/查询=事实、周期
  兜底、真变化才唤醒、订阅随任务起停）转为通用行为。
- **agent-as-tool（把目标 Agent 包装成工具直接调用）**：拒绝。Agent 不是函数——
  没有调用 Agent 这回事，只有把目标交给它；它忙不忙、怎么干是它的事。
- **读工具与派活不区分、全靠工具直调**：拒绝。读状态 = 普通工具（同步直返）；
  发任务 = 委派原语（回执 + 任务身份）——机制不同，不靠名单区分读写。

## 后果（Consequences）

**收益**：回执型工具接入零轮询（适配器声明即可）；跨 Agent 派活获得任务身份
（受理/进行/终态全程可查可通知）；minecraft 手写跟踪迁移后行为等价、代码归框架。

**代价与已知边界（有意取舍，债务清单 B 类维持）**：

- 任务记录表内存态：重启丢跟踪（与 minecraft 现状一致，接受）。
- 无发起方主动取消（执行者侧可用 maicraft task 的 cancel；跨 Agent 取消按需再加）。
- 排队无上限（积压无限流，将来再说）。
- 事件量 = 任务级（小），不构成压力。
- 只解决"跟踪/查询/通知"，不解决游戏执行本身慢。
