# ADR-012：工具可见名单机制（注册处生产侧声明）

- 状态：已接受（决策 2026-09-10 定案；随工具系统重设计实现）
- 日期：2026-09-10（定案）/ 2026-09-12（落盘）
- 实现提交：待收口回填

## 背景（Context）

需求：让某些 Agent 看不到某些工具，且机制可扩展。三条硬约束：禁止在配置或代码里
维护"某 Agent 能用哪些工具"的工具名清单；禁止依赖工具自报的注解；系统必需的信息
不进用户配置。三者共同指向——**可见性规则必须从代码结构里自动算出来，而不是被
列举出来**。

旧机制（ADR-009 的 `owner_agent`）只有"归属某 Agent / 全员共享"两档，表达不了
"读工具给主播+自己、执行工具仅自己"的逐工具受众；且当时已存在藏露颠倒——
minecraft 本地工具注册无归属而漏进主播工具面，streamer 内部工具声明了却永不注册。

MCP 注解复核：规范明示工具 annotations 不可信（除非来自可信 server）；MaiCraft
的 task 工具混合读/写动作却只有一套注解，无法表达动作级区分。读/执行分类只能由
我方代码声明。

## 决策（Decision）

核心一句：**每个工具在注册处声明自己可见给谁（生产侧、逐工具、代码事实）；每个
Agent 的工具列表由注册表按名单统一计算（`for_agent`），全体消费方只从这里拿。**

1. **名单形态**：`register_provider(provider, visible_to={工具全名: [Agent 注册名…]})`。
   值是 Agent 名或 `"*"`（单独出现，表示全员）；默认 `["*"]`（不写即全员，全局注册
   零负担）；空表非法；键必须命中该注册项声明的工具全名（拼错即注册报错）。
2. **生产侧而非消费侧**：工具的生产者最清楚它给谁用；本系统 Agent 与工具都是代码
   （无用户配置子代理场景），事实挂在快增长一侧（工具 55+）的出生点维护最省。
3. **判据与调用统一**：一切工具（含 Agent 自用）注册进全局注册表，调用统一经
   `registry.invoke`（观测/停用/熔断复用既有机制，不做第二路径）。
4. **调用不查身份**：名单只管"看不看得见"，不拦"编名字直调"（沿用 ADR-009 已知
   边界；封死需调用方身份治理，`source` 不是凭证）。
5. **有意取舍（非债务）**：默认 fail-open（未声明 = 全员可见）。理由：知道某工具
   敏感却不写名单是开发者自己的错误，且此类工具必然比全员可见的少；出现敏感工具
   类别时再保守化，成本最低的窗口就是现在。

## 替代方案（Alternatives）

- **消费侧清单**（每 Agent 列"我能用哪些工具"，Claude Code 子代理 / OpenAI
  Assistants 模式）：拒绝。那类产品里 Agent 是用户配置、存在"受限子代理"场景；
  本系统 Agent 只有一层、无子代理，且工具名清单已被约束禁止——消费侧还要求每个
  Agent 持有全局工具知识，增长轴上维护最贵。
- **注解路线**（server 自报 readOnly 等注解分类）：拒绝。注解不可信（规范明示），
  且无法表达动作级读写区分。
- **两档归属维持不动**（`owner_agent` 原样）：拒绝。"只给主播读"这一真实需求逼出
  第三档；开特例即承认需要逐工具名单。

## 后果（Consequences）

**收益**：新 Agent 零维护自动正确；藏露颠倒（minecraft 本地工具泄漏 / streamer
声明漂移）从机制上消除；工具面单一来源（各 Agent 手工拼列表的做法全部退役）。

**代价与已知边界**：

- "Agent X 能看到什么"分散在各注册处——由注册表计算接口与管理界面回答，人不汇总。
- 默认 fail-open 为有意取舍（见决策第 5 条）。
- 动态工具（如 rundown_control 按激活状态出现）名单静态，靠工具列表内条件追加，
  记录为已知例外。
- 停用/熔断/编名直调边界作用于全部工具（与 maicraft 现状一致，接受）；管理面对
  "停用会破坏宿主 Agent 运行"的关键内部件加警示标注（警示确认，非硬禁）。
