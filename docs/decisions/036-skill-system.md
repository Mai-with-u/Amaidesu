# ADR-036：Skill 系统——Agent 侧玩法经验文档（目录常驻 + 正文按需 + 环境门控）

- 状态：已采纳（2026-10-06 定案并实现）
- 日期：2026-10-06
- 实现提交：`d3e11b39b3777e7f6e16e28bbc1f793b73ba4f68`（feat(skills): 新增技能库基础设施）、`0978b397650cbbacbb36aefc153fd078943edbeb`（feat(minecraft): 新增生存/机械动力/Mek/通关种子技能）、`65cc0311a7e0406de4f8890c06801fbd659f3ed9`（feat(minecraft): 游戏 Agent 接入技能目录与读取；agent.py 部分被并发提交覆盖，由 `ad07f847ee7c221f8236299adce3b3fb09b981bc` fix(minecraft): 恢复并发提交互相覆盖的改动 恢复）；MaiCraft 仓库 `f5ddd008484044545d8659f5e3c27a7c971f1431`（feat(mcp): 新增已装模组清单只读资源 maicraft://environment）

## 背景（Context）

Minecraft Agent 能通过 MaiCraft 的 MCP 工具操作游戏，但"能调用"不等于"会玩"。Mod 侧已有两层信息：

- **能力契约**（`perceive(view="abilities")`）：某个能力怎么调、参数是什么、回执怎么读——单步操作的说明书。
- **知识库**（`maicraft://knowledge/*`）：这个世界与已装模组的事实——配方、Ponder 教程、机制常识、建筑风格。

缺的是第三层：**一类目标该怎么做成**——阶段顺序、决策点、常见坑、什么时候查哪份知识、哪些许可要先问主播。这层过去要么全靠模型临场悟，要么硬编码进常驻系统提示词（`_GAMEPLAY_RULES` 一类），后者每轮都占上下文，且与玩法无关的任务也在付费。

同时这层知识与已装模组强相关：没装机械动力（Create）时，动力网打法读了只是噪声。主播 Agent 与后续 Agent 也会有同类需求（例如"怎么主持一档游戏直播"），所以它应当是与 PromptManager 同级的基础设施，而不是 Minecraft 包的私有机制。

## 决策（Decision）

核心一句：**Skill 是消费 Agent 一侧沉淀的经验文档；目录常驻系统提示词，正文经 Agent 自有工具按需读取；受众由技能作者在文档里声明，适用环境由前提声明与已知环境事实共同决定。**

1. **定位三分**：契约（怎么调）与事实（是什么）随能力提供方发布；打法（怎么做成）随使用能力的 Agent 发布。Skill 引用知识库 URI 获取事实，不复制契约与数据。
2. **基础设施模块** `src/modules/skills/`：与 PromptManager 同构——约定扫描 `src/**/skills/**/*.md`，frontmatter `name` 是声明式注册键，元数据用 Pydantic 校验且禁止未知字段；坏文档、空正文、键冲突在加载期 fail-fast。全局单例由组合根（Agent 工厂）注入 Agent 构造器。
3. **两级按需加载**：目录（名字 + 一句话用途 + 分类）进系统提示词，常驻成本与技能正文长度无关；正文由模型判断需要时读取。第三级细节由正文引用的外部知识（如 Mod 知识库）承担。
4. **生产侧受众声明**：frontmatter `agents` 列出受众 Agent 注册名或单独的 `"*"`，与 ADR-012 工具可见名单同一思路——事实挂在技能出生点，消费方只按自己的注册名取用。
5. **读取工具每 Agent 一份**：`<provider>_skill`（如 `minecraft_skill`），按"LLM 可调内部工具 → 注册 + 名单隔离"红线只对自己可见。不做全局共享读取工具，因为工具注册表调用不携带可信的调用方身份，无法据此做受众筛选。
6. **环境门控三值**：`requires` 声明前提（类别由消费方定义，Minecraft 用 `mods`）。消费方提供已知环境事实：已知满足 → 进目录；已知不满足 → 移出目录、读取返回缺失项；该类事实未知 → 保留并标注"前提待确认"，由模型结合现场判断。未知与"没有"严格区分。
7. **Minecraft 的环境事实来源**：MaiCraft 新增只读资源 `maicraft://environment`（加载器、游戏版本、全部已装模组编号与版本，客户端启动时冻结，`mods_known` 区分未登记）。Agent 每次连接在任务批开始前读一次；连接恢复后重读（游戏可能换了整合包）；旧版 Mod 没有该资源时按未知处理。

## 替代方案（Alternatives）

- **继续写进系统提示词**：拒绝。常驻成本随玩法数量线性增长，且无法按模组裁剪；这正是本决策要解决的问题。
- **放在 Mod 侧作为知识库条目**：拒绝。知识库是 Mod 对世界事实的陈述，随 Mod 版本发布；打法属于 Agent 的决策经验，与 Agent 的提示词、工具面一起演进，且主播等非游戏 Agent 也需要同一机制。
- **全局共享 `skill_read` 工具 + 调用方自报身份**：拒绝。`source` 不是凭证（ADR-012 已记录调用不查身份的边界），受众筛选会被绕过或失效。
- **按目录位置决定受众**（`src/agents/minecraft/skills/` 即归 minecraft）：拒绝。位置是组织方式，不是语义；跨 Agent 共享的技能会被迫复制。声明式 `agents` 与 PromptManager 的声明式键一致。
- **配置文件手填已装模组**：拒绝作为主路径。换整合包要人工同步，漂移是必然；Mod 本就在启动时冻结了真实清单，读取即可。
- **把"前提未知"当作不满足而隐藏**：拒绝。旧版 Mod 或读取失败时会让所有模组技能消失，退化成"有技能也用不上"；标注待确认的代价只是目录里多几行。

## 后果（Consequences）

**收益**：加一项玩法经验 = 加一个 Markdown 文件，框架与 Agent 代码零改动；目录按受众与已装模组自动裁剪；主播或后续 Agent 接入只需一个 `<provider>_skill` 工具与目录注入。

**代价与已知边界**：

- 技能内容的正确性无法由代码校验，需要人工审阅；正文引用的能力名与知识 URI 随 Mod 演进可能过期，审阅时需对照当前 Mod。
- 目录在任务开始时随系统提示词固定，同一逻辑任务内已装模组变化不会刷新目录（模组清单本身只在游戏客户端重启时变化）。
- 读取工具不缓存"本任务已读"状态，避免重复读取靠工具描述约束模型；如出现反复读取，再在 Agent 侧加去重。
- `_GAMEPLAY_RULES` 中的机器建造、动力与重复加工规则暂未迁移为技能，迁移会改变常驻行为，另开任务评估。
