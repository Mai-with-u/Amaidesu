# ADR-031：组件间通信通道指派学说

- 状态：已采纳（2026-09-13 定案并实现）
- 日期：2026-09-13
- 实现提交：`a5c2f3977a862d06a31389c0129c2be92e8dfa91`（两阶段装配：simulator 启动移至 agent 订阅之后）；`51810cdccdbdeb416707e1b53ffcb29116b46297`（data-flow.md 对齐 ReAct 现状与两段装配，防腐修复）

## 背景（Context）

组件间"用什么通道说话"的学说原本散落且正在腐烂：`data-flow.md` 有通信机制选型表与 TTS 三分法（学说确实存在），但全景图仍以旧管道口吻描述已废除的 DecisionPlan 流程——ReAct 化后一周即失真，因为学说零强制、纯文档靠人肉同步。

更严重的是四个"未定案角落"，每个都有事故现场：

1. **Agent 调用自己的局部工具**——局部 Provider 算什么没规定，`rundown_control` 注册与直连双轨并存；
2. **组件间状态读取**——dashboard 直调 Agent 内部方法、Agent 私留 `_live_active` 状态副本、memory 直读 SQLite；
3. **运行时控制（管理面）**——dashboard 启停组件、直写 toml、注入消息，端点自我授权；
4. **观察旁路合法性**——思考流/日志/弹幕 widget 三条绕过事件总线的直推通道，无规则区分。

事故根因链（议题二深挖）：`main.py` 在 Agent 订阅接线**之前**调 `simulator_service.setup()`，后者回放模式开启场次并发出 `live.started`——观察者还没接线就改了运行态。Agent 只能启动后补读一次并私留 `_live_active` 副本。**私有副本是症状，不是选项**：状态（有当前值）用事件（瞬时通知）传播，迟到订阅者天然无法重建当前值。

## 决策（Decision）

核心一句：**通道选型按五维框架裁决；四个未定案角落补显式规则；装配期只构造接线、不触发运行态（两阶段装配）。**

### 五维框架

| 维度 | 取值 |
|------|------|
| 发起方向 | 推 / 拉 |
| 语义类别 | 事实通知 / 状态查询 / 动作命令 / 连续媒体 |
| 耦合预算 | 广播零耦合 / 经抽象 / 显式互识 |
| 时间耦合 | 无对齐 / 起止对齐 / 帧级同步 |
| 调用者智能 | LLM / 代码 |

四机制映射：事件总线 = 推 + 事实通知 + 零耦合 + 无时序 + 调用者无关；工具注册表 = 拉 + 动作命令 + 经注册表 + 同步 + 为 LLM；直连 Protocol = 拉 + 状态查询 + 显式互识 + 同步 + 为代码；装配期注入 = 连续媒体的局部解（TTS 三分法）。**判据：通道选错 = 把一个维度的负担转嫁给另一个机制。**

### 四个角落的裁决

1. **局部工具走 registry 统一**（方案 A）：所有工具（含 Agent 自用局部工具）统一经 `registry.invoke`，删除 `rundown_control` 的直连分支，回归 ADR-012 的单一路径——与 reply 的现状一致。
2. **状态读取**：状态有单一所有者；**装配期只构造与接线、不触发运行态；运行态变化只发生在装配完成后**。落地为两阶段装配：第①段全部构造 + 事件订阅接线，第②段才允许 `start()/setup()` 等运行态动作（simulator.setup 移到 `start_all()` 之后）；Agent 的启动补读与 `_live_active` 私有副本随之删除。
3. **管理面不加规则**（裁决时撤销）：WebUI 重启组件本身就是管理手段，配置一致性由重启兜底；控制操作白名单化 + 溯源属过度设计。
4. **观察旁路不加规则**（裁决时撤销）：后端给前端推数据只有 WebSocket 一条路；思考流/日志/弹幕三通道均为"Agent 定义接口、dashboard 实现"的依赖倒置，是干净结构而非问题。

## 替代方案（Alternatives）

### 局部工具代码直连合法（注册表只作 LLM 面）

**拒绝**。与 ADR-012"一切工具注册、调用统一经注册表"冲突；核证还发现"reply 走直连"的前提本身是误读（`_invoke_reply` 内部就是 `registry.invoke`）。双路径只会让"哪个工具走哪条路"成为新的记忆负担。

### 管理面操作白名单化 + 溯源

**撤销（用户裁决）**。"webui 重启就是干这个的"——重启重读配置即一致性兜底，审计链是给不存在的威胁设计的。

### 装配顺序调整（方案 A：仅把 simulator.setup 挪后）

**拒绝（选方案 B 两阶段）**。只挪一处是点修，"装配期不得改运行态"需要结构性保证；两阶段把规则写进组合根形状，任何新组件想在第①段触发运行态都会显得刺眼。代价是改动面更大、需确认无组件的 `start()` 依赖 simulator 已运行。

## 后果（Consequences）

- 两阶段装配成为组合根纪律：新增组件在第①段注册订阅、第②段启动；违反该纪律的代码在组合根里形状刺眼，可被 review 捕获。
- 学说防腐靠文档对齐 + 既有 `tests/architecture/` 断言（分层方向、事件流边界、provider 健康契约）；通道指派红线暂无专属架构测试， doctrine 再腐烂的风险仍在——新增通道类型时应先回看五维框架再动机制。
- 管理面与观察旁路"不设规则"是显式裁决而非遗漏：将来若出现真实的滥用事故，重开议题的起点是本 ADR 的撤销理由，而非从零争论。
