# ADR-051：主播长期记忆 MEMORY.md（纯文本 / 收播合并 / 开播冻结注入 / 正式彩排各一份）

- 状态：已采纳；扩展 ADR-042（在场次回顾与观众画像之外加第三样记忆，ADR-042 的"只有两样"由本篇改为三样）
- 日期：2026-10-29
- 实现提交：可用 `git log --grep` 按 subject 检索——`feat(streamer): 主播长期记忆 MEMORY.md`、`feat(dashboard): 主播记忆页可查看与编辑长期记忆`

## 背景（Context）

ADR-042 把主播记忆收敛为两样：场次回顾（自己做过什么，一场一份）与观众画像（常客是谁）。用下来缺一层：场次回顾只管单场，开播只注入最近一两场；五场前答应观众的事、反复出现的老梗、跨场次推进的长线目标，除非主播一场一场去翻，否则就丢了。活人感的几条判据里，"自我是连续的"（心情延续、记仇、有反复出现的老梗和执念）正卡在这里。

参照两个做法：

- **Hermes Agent**：MEMORY.md 与 USER.md 两个有字数上限的文件（约 2200 / 1375 字符），Agent 经一个工具增改删条目；写满时不自动淘汰，退回让 Agent 合并；会话开始时整份注入并冻结，本次会话的新写入下次才生效，保住提示词前缀缓存。往期对话另存 SQLite 全文检索。
- **OpenClaw**：按天的笔记是流水层，MEMORY.md 是精选层；后台整理流程把每日笔记里有用的东西提炼进 MEMORY.md。文件是唯一事实源，向量索引只是附加检索。

Amaidesu 已经有对应的几层：场次回顾 ≈ 每日笔记，观众画像 ≈ USER.md（按人分），本场备忘录 ≈ 会话里的临时记录；缺的正是 MEMORY.md 那一层。用户的方向是纯文本管理，不用嵌入向量。

## 决策（Decision）

**加一份由主播"自己"整理的长期笔记：纯文本文件，有字数上限，收播时合并、开播时整份冻结注入，正式场与彩排场各一份。**

1. **存储**：数据库同目录的 `memory/MEMORY.md`（正式）与 `memory/MEMORY.rehearsal.md`（彩排），纯文本、UTF-8、LF，人可以直接用编辑器打开改；写入先写临时文件再原子替换。不进 SQLite——它是一整段给人和模型读的文本，没有可查询的结构，价值在于能直接改。按场次类型分文件，与 ADR-050 的两条记忆线一致。
2. **谁来写、什么时候写**：收播整理里排在场次回顾之后，一次 summary 档位调用：旧笔记 + 本场回顾 + 本场备忘录全文快照 → 更新后的整份笔记。本场没写成回顾就不动；启动补写回顾的场次同样补一次。直播进行中不写——现场要记的结论由本场备忘录承担，沿用 ADR-042"直播中不为记忆额外调用模型"。
3. **结构与上限**：按节组织（答应过的事〔标兑现状态〕、老梗与口头禅、长线目标、关于我自己），默认上限 2000 字符（`[agents.streamer.memory].long_memory_max_chars`）。超出时让模型压缩一次，仍超出就保留旧版本不写，不截断成半句。
4. **注入**：开播时按场次类型读出整份，整场不变；进决策参考段最前（"长期记忆-内部参考"，在上场回顾之前）和快嘴的系统提示词。人工在 WebUI 或编辑器里改的内容从下一次开播起生效。
5. **管理入口**：WebUI"主播记忆"页（原观众画像页）顶部的长期记忆面板，正式 / 彩排切换、整份编辑保存；接口 `GET / PUT /api/v1/memory/long-term/{kind}`。

## 替代方案（Alternatives）

### 直播中由主播经工具增删改（Hermes 式 add / replace / remove）

**暂不采用**。每次写入都占决策步数和延迟，模型也容易把临时状态写进长期记忆；现场的结论已有本场备忘录承接，收播时一并沉淀即可。以后若发现收播合并丢细节，再考虑开放"标记一条要长期记住"的写入口。

### 存进 SQLite 一张表

**拒绝**。功能上等价，但失去"打开文件就能改"的直接性；这份记忆没有需要按条件查询的结构。

### 嵌入向量 / 语义检索

**拒绝**。用户方向是纯文本；ADR-042 也已论证按身份与场次序号直取足够。真要按内容搜往期，SQLite 全文检索也不需要向量。

### 不设上限、靠截断

**拒绝**。整份每次开播都注入两层上下文，必须有上限；截断会切掉句子甚至未兑现的承诺，所以超限只压缩、压不下就保留旧版。

## 后果（Consequences）

- 主播开播即带着跨很多场的承诺、老梗和长线目标；彩排里写的东西不会进正式那份。
- 收播整理多一次 summary 调用（回顾 → 长期记忆 → 画像），失败只降级，长期记忆保持旧版本。
- 长期记忆的质量取决于 summary 档位模型对"保留 / 删减"的判断；人可以随时在 WebUI 或编辑器里纠正。
- 人工编辑与收播合并同时发生时后写覆盖先写，编辑尽量避开收播整理的那几十秒。
