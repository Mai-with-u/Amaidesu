# ADR-055：LLM 调用默认一直等，晚了就没用的用途按用途设放弃等待时长（取代 ADR-032 "运行时韧性"一节的硬超时一条）

- 状态：已采纳；部分取代 ADR-032（"运行时韧性"一节里 `hard_timeout_ms` 那一条，其余不变）
- 日期：2026-10-30
- 实现提交：与本篇同笔交付（`git log -- docs/decisions/055-llm-give-up-wait.md`）

## 背景（Context）

ADR-032 规定引擎用 `hard_timeout_ms` 包住一个模型的整次尝试（含重试），到点就切下一个模型。2026-09-25 的提交 39daafa3（`refactor(llm): 移除生成额度和请求硬超时`）把它和 SDK 自带的请求时限一起删了：长回复（游戏 Agent 的长计划、整场回顾）被宿主设的时限从中间掐断，白白浪费一次生成，而这些调用晚一点返回并不要紧。此后所有调用都一直等到模型返回，只保留调用方主动中断与失败重试。

2026-10-29 的全链路彩排暴露了另一面：回复模型（replyer）一次卡了 313 秒才返回，主播这一轮就一直在等这句台词，直播间冷场 5 分钟。慢调用告警只记日志，不切换。直播里的台词和主播的决策是"晚了就没用"的调用：一句台词等了一分钟，它要接的那条弹幕早已过去。

两类调用对时间的态度相反，一个全局开关定不下来；而 profile 本来就是"用途"，正好按用途区分。

## 决策（Decision）

- 每个用途 profile 加 `give_up_ms`（放弃等待时长，毫秒），通用默认 0 = 一直等，长回复不被掐断。
- 设了值的用途，一个模型（连同它的重试）这么久还没返回，引擎就取消这次请求（底层连接一并收回）、按失败切名单里的下一个模型；名单走完仍没有，就返回失败，由调用方按失败降级。
- 只给直播里晚了就没用的两个用途设：replyer 60 秒（台词正常十几秒内出）、planner 120 秒（决策正常半分钟内出，实测最长约 36 秒）；其余用途保持一直等。
- 存量 `model.toml` 由升级钩子给这两个用途补上取值（只补缺的键，用户写过的值原样保留）。
- 计时经构造注入，测试不靠真实时间流逝。

## 替代方案（Alternatives）

- **恢复全局硬超时**：重新引入 39daafa3 要解决的问题，长回复会被掐断。
- **在主播包里给回复调用套时限**：只管得到台词，同一用途的快嘴反应、决策照样会卡；而且拿不到"切名单里下一个模型"的能力。
- **等待时先说一句垫话（"让我想想……"）**：能掩盖几秒的慢，掩盖不了几分钟的卡；垫话本身也要说得像人，另起一套机制。可以以后作为补充，不能替代放弃等待。
- **按首个 token 计时**：能区分"卡住"和"在慢慢写"，但不是所有调用都走流式，客户端也未必报首 token；台词和决策都很短，整段计时已足够区分。

## 后果（Consequences）

- 回复模型卡住时，主播至多冷场一分钟左右：这一轮的台词作废，Planner 拿到失败结果后照常进入下一轮。
- 名单里配了备用模型时，卡住会自动切过去；只配了一个模型时，到点就按失败处理。
- 卡住的请求被取消，费用与请求历史按失败记，不会在后台继续占连接。
- 设得太短会误伤正常但偏慢的调用：取值按实测留了几倍余量，日志里的"放弃等待"告警是调整依据。
