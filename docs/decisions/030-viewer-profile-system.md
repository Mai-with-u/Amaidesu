# ADR-030：观众画像系统与记忆层重构

- 状态：已采纳（2026-09-23 定案，2026-09-24 实现）
- 日期：2026-09-24
- 实现提交：`4e8431e174b8f467f0cfa427081d87718dcc8b07`（画像提取/生成/注入/管理页/双工具）；`4d9190a00058a4a6c5b191498a637d0a08f26aa8`（端到端验收）；`93fd68cdcd122d4b8b110643a2b4f776ed646fdc`（对照定案收齐：注入昵称、画像原料、硬帽、不占位语义）

## 背景（Context）

主播要"认出老观众"，旧记忆系统做不到：

1. **写入**只有两路且都不按人组织：高价值事件（礼物/SC）格式化成中文事实、话题摘要压缩——全部落 `_memory_facts` 扁平表，无 user 归属、无去重、无衰减。普通弹幕不进记忆；观众"表达过什么观点"只有送礼时才留痕。
2. **召回**靠 LIKE + CJK 2-gram（噪声大），query 由话题+弹幕文本拼出——只有弹幕恰好含昵称才带出其历史，"老观众回来了认得出"纯靠运气。
3. **SC 观众掉进两级缝隙**：明细表写了但 `viewers` 统计不写（计数"走语义层"），而语义层不按人组织；按人的画像层 `_memory_profiles` 曾建而不用、当死代码删除——SC 事实只剩全局扁平副本。
4. `_memory_facts` 是冗余副本：话题有 `topics`/`timeline_summary` 权威表、付费有三张明细表，它两头重复且永不收敛。
5. `_` 私有表前缀是伪隔离：物理同库、无隔离机制，"免检"也是伪豁免（`SimpleMemory.initialize` 照样查表存在性）。

## 决策（Decision）

核心一句：**每个观众一份落盘画像文本（LLM 增量压缩），写入路径持续产出按人归属的事实原料，决策前把有画像的观众注入提示词——没形成印象的观众不注入，主播由此认出老观众。**

### 核心模型

- **方案二（档案层 + 画像文本 + LLM 压缩）**。写入路径只产出原料，压缩机制负责精炼；弹幕量级（活跃观众每人每天数十上百条）决定了现场拼接必然爆炸，LLM 压缩是对真实量级的正确响应。

### 写入路径

- **原料分两类**：非结构化（说过什么：弹幕 + SC）→ 提取事实；结构化（干了什么：付费明细三表、身份快照、互动统计）→ **直读，不经提取**。
- **事实提取复用后台 60 秒话题摘要循环**——同一次 LLM 调用顺便提取（成本≈0），不新增循环。输入是 canonical 格式消息批（`昵称: 内容 [id:xxx]`，与 planner 同源）加时间窗内的 SC（SC 不落 live_chat，恰是最有价值的事实源）。
- **归属程序化**：LLM 输出 `[{"message_id", "fact"}]`，用 message_id 反查批内消息得 `(platform, user_id)`——不靠 LLM 报人名，杜绝"记错人"。引用批内不存在的 id 视为幻觉丢弃；`json_repair` 容错解析，失败时整体降级为纯文本摘要，**事实提取失败不拖垮话题摘要**。
- **证据分层**（借鉴 MaiBot 群聊实践）：本人原话是权威源，邻近上下文仅辅助理解；prompt 硬约束"事实必须由本人原话直接支持"，跳过纯情绪短句。
- **门槛**：`viewers.interaction_count` ≥ N（默认 3）才有画像；不够格自然不注入，无需排除逻辑。
- **增量压缩**：`viewer_profiles.last_compressed_at_ms` 是水位，每次只把水位后的新事实 + 旧画像 + 结构化直读喂给 LLM；触发复用压缩 worker（并发=1 保顺序），失败逐人降级。

### 召回路径

- **画像段替换记忆召回段**：planner 参考段内 `memory_recall_section` 退役，新段收集本批弹幕发言人（去重、时间倒序），逐人查画像——**无画像跳过且不占位**（候选遍历到有画像者凑满上限 3 才停），昵称从 `viewers` 实时取（与弹幕侧同源可关联），整段 1600 字硬帽，查询异常整段省略不阻断决策。
- **过渡期召回策略（甲）**：planner 只注入"观众画像 + 当前话题"，历史事实召回暂时缺失，将来接外部记忆系统补上——不预养空壳。

### 存储归属

- **`_memory_facts` 废弃**（两源均有权威表，扁平副本冗余）；**私有表机制一并废除**——`_` 前缀是伪隔离，所有表统一进 `list_expected_tables()` 启动闸门。
- 新表 `viewer_facts`（事实原料）与 `viewer_profiles`（画像文本 + 水位）是业务表，统一纳管。
- **memory 模块保持通用记忆定位**，不窄化为观众画像——画像只是记忆的一种能力；`MemoryProvider` Protocol 保留（接口稳定，未来外部记忆后端再入口的门），当前无实现者。

### 接线

- 工具双开：`query_memory` 查事实（`viewer_facts`），`query_viewer_profile` 查画像（昵称经统计表反查定位）。
- WebUI 记忆管理页改画像管理页：列表 / 人工纠正 / 删除，行展开查看事实原料、单条删除。
- 配置 `[memory]` 段承载画像行为参数（提取开关 / 门槛 / 画像长度 / 注入上限 / 单批事实条数）——写入侧与注入侧共享同一组策略值。

## 替代方案（Alternatives）

### 方案三：现场拼接画像起步，压缩机制留白

**拒绝**。其论据"Amaidesu 写入频率比群聊低两个数量级"错在拿现状的写入筛选策略当成未来的写入需求——"普通弹幕也该成为印象原料"正是本次重构的内容。直播间弹幕量级下现场拼接必然爆炸，LLM 压缩不是过度设计。

### 照搬 MaiBot 的逐轮触发提取

**拒绝**。MaiBot 是回合制群聊（bot 回复触发），直播是一对多流式（大部分弹幕无人回复），逐轮触发失效。但它的三个细节照搬：证据分层、prompt 硬约束、JSON 容错。触发改用"批量 + 复用后台循环"，归属改用消息 id 引用（按 sender 分组会丢批内上下文，被否）。

### 保留 `_memory_facts` 双轨并行

**拒绝**。两源均有权威表，扁平副本永不收敛；画像层所需的人归属、去重、水位它都没有，留着只会让"哪边是真相"变得含糊。

### 画像文本里存昵称

**拒绝**。昵称随改名漂移；画像文本只存稳定认识，昵称在注入时从 `viewers` 实时解析——画像段与弹幕侧的"昵称: 内容"才能对上号。

## 后果（Consequences）

- planner 参考段按本批发言人变化，影响 LLM 前缀缓存命中率——画像段有整段硬帽与人数上限约束体积，上线后需观察缓存指标。
- 事实提取的输入与 planner 同源（canonical + message_id），弹幕落库行的 `message_id`/`platform`/`sender_id` 成为画像归属的依赖字段，缺一即丢（宁可丢不可错归属）。
- `MemoryProvider` 的 `recall`/`ingest` 签名当前无实现者，属"留给未来后端"的接口门——修改该 Protocol 前需先确认没有外部记忆系统在对接。
- 画像质量依赖摘要循环的 LLM（summary profile）；该 profile 不可用时事实与画像静默停摆（有日志），直播主链路不受影响。
