# ADR-082：常驻简报按表快照逐决策窗重渲

- 日期：2026-11-22
- 实现提交：与本 ADR 同批交付，按路径检索：`git log -- docs/decisions/082-brief-re-render-per-decision-window.md`

## 背景（Context）

[ADR-066](066-memory-injection-switch.md) 定下三个读出口时，常驻简报的形态是"系统提示词末尾、开播拼一次、整场不变"，理由写得很直接：拼好整场不重算，前缀缓存才命中。此后陆续落地的几件事与这个形态冲突：

1. **场内纠错要当场生效**。[ADR-077](077-memory-zones-opening-wrapup-ttl-and-in-stream-correction.md) 引入 `streamer_memory_correct` 与承诺当场结单：运营者在直播中发现旧档案或旧承诺记错，当场改完，这场直播剩下的时间她看到的仍是错的那一行。
2. **承诺状态会自己变**。运营者可以在 WebUI 记忆页了结或判误记一条承诺，不必等到下一场开播。
3. **待整理场次在直播进行中整理完**。开播时排进后台的待整理场次可能在直播进行中整理完，简报要带上刚结束那一场，否则她整场都不知道上一场留下了什么。

同时，"整场不变"从来不是前缀缓存的必要条件。前缀缓存吃的是**前缀逐字节相同**，不是"整场只拼一次"。只要渲染结果只依赖表快照、不含时刻等易变值，表没变时每窗重渲出来的字符串与开场拼的那份逐字节相同，缓存照样命中。

## 决策（Decision）

1. **常驻简报每个决策窗重渲一次。** 渲染只依赖表快照，不含时刻、随机数或计数等易变值；表没变时每窗输出与上一窗逐字节相同，Planner 系统提示词的前缀缓存照常命中。表变了（场内更正、运营者判误记、了结、删一行，或上一场整理刚写完）下一窗就反映出来。
2. **重渲的三个时机**：每个决策窗开窗前（先同步各游戏眼下在哪个存档，再重渲）；场内更正写库后立即刷新；开播时按场次类型拼第一份（正式场接正式场、彩排场接彩排场），此后的重渲走同一路径。
3. **"表没变则逐字节相同"是硬约束**，由 `tests/agents/streamer/test_streamer_memory.py` 里的 `test_brief_rerender_is_byte_identical_when_ledger_unchanged` 守护。

## 替代方案（Alternatives）

1. **保持整场不变，靠单独的注入通道递送更正**。被否决。纠正要进的是同一段常驻文本，另开通道会让"她看到的记忆"分裂成两处，渲染与遮名口径也要跟着分叉。
2. **每窗重渲但允许文本里含时刻**（例如渲染时写"距上次提过 3 天"）。被否决。时刻进文本会让每窗都不同，前缀缓存彻底失效——而这正是"每窗重渲"唯一的代价；同时它与"任何面向主播的通路都不出现精确天数、场次数与日期"这条规则冲突。
3. **只在表变动时重渲（事件驱动）**。被否决。表有多条写入路径（整理、审核、场内更正、了结、删行），漏掉一条就静默不更新；每窗无条件重渲的成本只是重算一次字符串。

## 后果（Consequence）

- 直播中的纠错、运营者的了结与误记判定、刚整理完的那一场档案，在下一个决策窗就生效，不必等到下一场开播。
- 每窗多一次字符串重算，成本可忽略；前缀缓存命中不受影响。
- 渲染函数必须保持"只依赖表快照"：任何把时刻、计数或随机性写进文本的改动都会打破缓存。这是硬约束，不是优化建议。
