# ADR-021：全站时间字段毫秒统一（Unix epoch 毫秒 int，原子切换）

- 状态：已采纳
- 日期：2026-09-19
- 实现提交：`1afd7cacdab224863e4a217ddd5772ff0d42b1e0`（refactor: 事件时间戳统一毫秒；至 `d56208ecb3889f25136ea191f14e484acb102c42` 覆盖 llm 域）

## 背景（Context）

仓库约定时间字段统一为毫秒：时刻用 `int` Unix epoch 毫秒，时长/超时命名 `<name>_ms`。但 dashboard 的多个域实际落盘与出网的是秒 `float`，约定与实现漂移。后果直接落在前端：`utils/liveFeed.ts` 被迫维护 `toSeconds` 这类双格式启发式——以"数值大于 1e12 判定为毫秒、否则为秒"来猜测单位，同一字段两种口径并存，每个消费点都要做一次猜单位。启发式对边界值脆弱（早于 2001 年的毫秒时刻、晚于 33658 年的秒时刻均会误判），且每个新域接入都在扩大猜单位的面。

## 决策（Decision）

**全站时间字段统一为 Unix epoch 毫秒 `int`**，覆盖范围包括：

- SQLite 存储列；
- REST 参数与响应；
- WebSocket 线格式（WS 载荷）；
- 进程内内存结构。

采用**原子切换而非兼容窗口**：前后端同仓同进程分发（FastAPI 同源挂载 dist，开发期 Vite 代理到同一后端），前端永远与后端同版部署，不存在"旧前端配新后端"的版本偏差窗口，兼容层的存在没有前提。遗留的秒口径域全部正名（字段名与单位同步改对，不留双写）。

## 替代方案（Alternatives）

### 双格式兼容启发式（>1e12 判单位）

**拒绝**。该方案曾实际上线（`toSeconds`），后被删除——经验证兼容代码本身就是持续成本：每个时间消费点都要过一遍猜单位逻辑，边界值语义含糊，且永远不敢删。同进程分发消除了它唯一的存在理由。

### 字符串 ISO 8601 时间

**拒绝**。人类可读性对人确实友好，但机器侧排序、比较、游标分页都要先解析字符串，存储与索引成本升高；本项目时间字段的主要消费形态是排序与差值计算，int 毫秒是直接形态。

## 后果（Consequences）

- 新域、新端点的时间字段必须遵循毫秒 int 与 `<name>_ms`/时刻毫秒命名，约定重新成为可执行纪律而非摆设。
- 前端时间显示统一以毫秒为入参，`toSeconds` 类启发式及其调用点全部删除。
- 外部消费者若依赖秒口径会被破坏——已查证 dashboard 之外不存在此类消费者（WS 与 REST 均为本仓自带的同仓前端），风险为空。
- 后续若出现独立分发的外部 API 消费者，需另行评估对外契约的版本化；对内契约不变。
