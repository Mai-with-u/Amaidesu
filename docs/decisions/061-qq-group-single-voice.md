# ADR-061：QQ 群里只留 QQ 麦麦一张嘴（主播托话代替直接发群：主播给要点、QQ 麦麦决定怎么说 / 直接发群与水群接管改为可选、默认关）

- 状态：已采纳
- 日期：2026-11-01
- 实现提交：Amaidesu 侧没有代码改动（主播看到的 QQ 工具清单由插件动态提供）；插件侧在 MaiBot-Amaidesu-Adapter 仓库 `74513a46d950e6c3d8e6adc2d16525d9dfb00844`（feat: 群里默认只留 QQ 麦麦一张嘴）

## 背景（Context）

Amaidesu 与 MaiBot 的关系是"一个身份、两个身体"：同一个麦麦，直播间里由 Amaidesu 的主播 Agent 驱动，QQ 群里由 MaiBot 驱动，两边各跑各的决策循环。接通 QQ 的第一步给了主播三件事：读群、直接发群、托 QQ 麦麦说话。直接发群时，同一个群里有两方都能以麦麦的名义说话，插件用"水群接管"避免抢话：主播发群后 10 分钟内把 MaiBot 在该群的发言频率倍率压到 0，每发一句重新计时。

接管只能缓解，留下的问题有两类。

一类是时间上的空档：

- 接管要等主播第一句真正发出去才生效。主播读群、想、调用发群的几十秒里，QQ 麦麦照常聊天，可能两个麦麦对同一条消息各回一句；接管到期后主播再来，又是同样的空档。
- 倍率为 0 时 QQ 麦麦连 @ 都不回，而主播要主动读群才看得到群消息，群友 @ 麦麦可能十分钟没人理。

另一类是"人格分裂"。主播直接发群时，MaiBot 的规划与回复全被跳过：文字由主播的规划模型在调用工具时写好，插件直接用 QQ 号发出，事后才写进 MaiBot 的群上下文。主播写这句话时只看得到读群读到的几十条，没有 MaiBot 对群友的印象，也没有它在这个群学到的说话方式，注意力还在直播上。于是会接错话题、把直播里的事硬搬进群、口吻忽然从 QQ 麦麦变成直播口吻、对熟人像对生人；接管结束后，QQ 麦麦在上下文里看到"自己"刚说过的话，却不知道当时为什么这么说。

这些问题都出自同一个结构：一个会话里有两方都能以麦麦的名义说话，就必须有互斥（接管）和双向同步，而这两样都只能做到近似。

## 决策（Decision）

核心一句：**QQ 群里只有 QQ 麦麦说话。主播想在群里说什么，就托它说：主播负责"说什么、为什么"，QQ 麦麦负责"怎么说、什么时候说、说不说"。直接发群保留为可选，默认关闭。**

### 为什么由 MaiBot 说

一句群消息要说得像同一个麦麦，需要五样东西：群里一直在聊什么、对这些群友的了解、在这个群的说话方式、自己之前说过什么和为什么、自己此刻在干什么。前四样都在 MaiBot 里，而且一直在变；只有第五样在 Amaidesu，量很小，直播近况与共享笔记已经同步过去（ADR-045、ADR-059），剩下的用一句托付就能说清。让谁说，等于决定往哪边搬数据：让 MaiBot 说，搬的是一句托付；让主播说，要把前四样搬过来，每次说话前重搬，说完还得写回 MaiBot。最小必要的机制是搬小的那一份，同时把"两方说话"变成"一方说话"，互斥与同步都不再需要。

这与 Amaidesu 自身的做法对称：直播间里只有主播一张嘴，游戏 Agent 不直接在直播里说话，而是经 `minecraft_report` 把事交给主播；主播委派游戏 Agent 用 `framework_delegate`，只给自然语言指令、不给步骤。QQ 群就是 MaiBot 的"直播间"，托话就是主播对 MaiBot 的委派。主播要求自己"不是任何外部 Bot 的外壳"，直接发群反过来把 QQ 麦麦的身体当成了 Amaidesu 的外壳。

### 托话怎么走

1. **沿用插件的托话工具 `ask_mai`**（Amaidesu 侧名 `qq_ask_mai`）：托付作为一条插件任务写进 MaiBot 该群的上下文，并强制 MaiBot 跑一轮规划。QQ 麦麦带着完整的群聊上下文、记忆、对群友的了解和自己的说话方式决定怎么说；托付留在上下文里，之后它也知道自己为什么说了那句。
2. **工具说明写明分工**：交代要说的事、为什么说（直播这边刚发生了什么，QQ 麦麦看不到，要写上）和必须带上的事实（如直播间链接），不用替它写好原话。结果不确定：它可能看群里的气氛决定不说，主播不要在直播里说"已经发到群里了"；它说了什么，下次读群时能看到，署名就是主播自己。
3. **一定要说到的事**：参数 `must_say` 为真时，插件把托付的优先级标为高，并在托付里写明"一定要在群里说到"。宿主给 QQ 麦麦的规则是自行决定是否回复，所以这只能大大提高说到的概率，不能保证。
4. **间隔**：同一个群两次托付至少隔 `qq.min_ask_interval_ms`（默认 60 秒），免得主播每轮决策都托一次，把 QQ 麦麦刷成复读机。唤醒失败不计入间隔，主播可以马上重试。
5. **读群不变**：主播随时可以读群，在直播里聊群里的事。收成一张嘴的只有"说"。

### 直接发群改为可选

6. 插件配置 `qq.direct_send` 默认关。关闭时主播的工具清单里没有 `send_group`；按旧工具清单发来的发群调用也会被拒绝，并提示改用托话。
7. 水群接管只在打开直接发群时起作用。运行中把直接发群关掉时，插件下一次到期检查（每 5 秒）就把所有接管还原，不等到期。
8. 打开直接发群的场合：要说的内容关键在直播这边，而且要逐字精确、和直播实时同步，例如直播里正和群友连线，每句话都要和画面对上。

## 替代方案（Alternatives）

- **保留直接发群，把空档补上**：主播一读群就先短暂接管；发群前检查主播上次读群之后有没有新消息，有就先退回给主播看；工具说明里提醒别把直播话题搬进群。能缓解第一类问题，但 @ 没人回要等群消息实时采集器，口吻与对群友了解的差距补不上，"两方说话"的结构还在。未采用。
- **把 MaiBot 的群上下文给 Amaidesu，由直播麦写**：要搬的是持续变化的大块状态（完整上下文、聊天摘要、人物信息、学到的说话方式），每次说话前都要重搬，说完还要写回；主播的上下文被 QQ 群挤占，同时应付两拨人，与"注意力留给角色、说话通路要瘦"的方向冲突。未采用。
- **主播写稿，交给 MaiBot 改成它的口吻再发**：MaiBot 插件能力 `maisaka.reply.generate` 能套用 MaiBot 的人格与表达方式生成文字但不发送。但宿主实现传的是空聊天记录、固定按长回复风格写，用途是给插件写长文；拿来改写群聊短句要把群消息塞进素材，属于挪作他用。未采用。
- **直播期间整场接管**：直播期间群里基本没人说话，@ 没人回的问题更严重；主播的注意力在直播上，水群本来只是偶尔为之。未采用。

## 后果（Consequences）

- 抢话、接管期间 @ 没人回、人格分裂、交还后接不上这几类问题从结构上消失；QQ 麦麦一直在线，被 @ 时它从近况注入知道自己正在直播，可以自然地回。
- Amaidesu 不用改代码：主播的 QQ 工具清单由插件按配置动态提供，关掉直接发群后 `qq_send_group` 自然消失。
- 代价：托付不保证被说出来；一次托付要经过 MaiBot 的规划与回复，慢几秒到十几秒；主播不知道托付的结果，只能下次读群时看到；节目上少了"主播亲手发一句"。
- 群里说得好不好完全取决于 MaiBot 的回复模型。曾实测到回复模型不按规划给的方向写，这种问题要改 MaiBot 的模型配置，不在 Amaidesu 侧绕路。
- 已部署的插件升级后即按"一张嘴"运行（新配置项带默认值）；想保留亲手发群的，要显式打开 `qq.direct_send`。
- 以后若需要把"托付最后说了什么"单独回报给主播，插件可借已挂的发送钩子（`send_service.after_build_message`）实现；不让工具阻塞等待结果，否则主播的决策循环会卡十几秒。
