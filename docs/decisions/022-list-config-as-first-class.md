# 022 列表型配置是一等公民：整值编辑与索引回填

状态：已采纳
日期：2026-09-20
实现提交：12a7fb878dfdc65c77bf4df382a54e7412f6c7bc（`git show 12a7fb87`：列表型配置升为一等公民支持整列表编辑）

## 背景

配置 Schema 中的对象列表（`List[BaseModel]`，TOML 落盘为 array-of-tables，如 `model.toml` 的 `[[llm_providers]]`）在设置页无法编辑。根因是 Schema 解析层把列表"降维"：`collect_all_fields` 将元素字段展开为无索引的伪键（`llm_providers.api_key`），导致：

- 展示错乱——多个 provider 的同名挤进一个字段，值语义不明；
- 写回必败——写路径的 Schema 树行走（`_walk_schema`）无法把无索引键定位到数组元素，保存恒 422"未知配置项"。

问题不在某个字段的处理，而在解析方式：列表没有被当作配置树的一等节点类型，只是被错误地摊平。设置页的本质是"配置树的通用 CRUD 视图"，每种节点类型（标量 / 对象 / 列表 / 字典）都应有通用的渲染与提交语义，不需要任何字段特殊处理。

## 决策

**列表是值：整列表作为一个字段的值进行编辑与提交。**

1. **Schema 解析**：`List[BaseModel]` 字段保持为一等字段（`type=array`），元素子字段树完整携带在 `items.fields` 中；`collect_all_fields` 不再展开数组元素的伪键。
2. **展示**：前端数组编辑器对对象项渲染折叠卡片（标题取元素标识字段值，如 `name`），元素内字段递归复用既有字段渲染器；不再退化为 JSON 文本框。
3. **编辑与提交**：元素内任何字段修改、增删元素，统一表现为"该列表字段的值变更"，保存时整列表提交（key 为列表字段本身）。
4. **写回**：整值赋给点分路径后由既有统一管线处理——根 Schema 对整个数组做 Pydantic 校验（含跨字段一致性，如 `llm_models` 对 provider 名单的引用检查），落盘按 array-of-tables 重建。写回器零改动。
5. **敏感字段占位回填**：GET 下发的元素内敏感字段是占位文本（前端不持有真实凭据），整列表提交会将其带回。写路径在 Schema 校验前按索引对齐磁盘现值回填真实值；回填后仍残留占位（典型如新元素未填写密钥）则保持既有的占位写拒绝。

## 替代方案

- **元素级细粒度寻址**（`llm_providers.0.api_key` 逐字段提交）：改字段场景干净，但增删元素需要引入额外指令语义（JSON Patch 方向），写回器与前端状态机都要为"删除第 N 项"发明新表达，复杂度反而更高。
- **配置结构改造**：把 `[[llm_providers]]` 改为按名字索引的字典（`[llm_providers.deepseek]`），寻址自然。但这是数据变换档的配置变更（升 `[meta].version` + 迁移钩子），影响面远超设置页修复，且字典形态对"有序 provider 列表"并无必要。
- **敏感字段移出通用表单**（GitHub 式独立改密表单）：交互最严谨，但引入新的表单类型与交互流，收益配不上当前场景（自用工具，凭据改动低频）。

## 后果

- 任何 `List[BaseModel]` 配置（现存与未来新增）在设置页自动获得渲染、编辑、增删能力，无需字段级代码。
- 整列表提交配合深比较状态机：改动未偏离原始值时自动撤销变更记录，增删与改字段的"脏状态"判定语义一致。
- 占位回填按**索引对齐**，存在已知边界：删除中间元素的同时修改其后元素的敏感字段，可能把凭据回填到错位的元素。选择接受：两种操作同时发生的概率低，且错位只发生在用户自己的 provider 之间，不构成外部攻击面；若未来需要消除，应引入元素稳定标识而非继续打补丁。
- 元素内部的嵌套对象（`List[BaseModel]` 元素再含 `BaseModel` 字段）暂不展开子树（`items.fields` 生成时 `include_nested=False`），此类字段退化为字典编辑器；当前六文件 Schema 中不存在此形态。
