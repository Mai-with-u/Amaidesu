# ADR-024：口型帧级通道——AudioSink 分接 + 共享分析器 + 平台渲染器

- 状态：已采纳（2026-09-20）
- 日期：2026-09-20
- 实现提交：`f049e2a789f8dba6d2e75ab46e03ca889f8452ff`（feat: 口型帧级通道兑现分接与共享分析器）

## 背景（Context）

ADR-007 决策 5 对帧级口型的定论是"**留白，YAGNI 暂不建**"——替代方案里被拒的是"立刻建 AudioSink"（当时零消费者），而非拒绝该能力本身。`LipSyncProcessor` 作为预留实现一直存在，但接线断开：分析器零外部调用者、TTS 的 PCM 只进声卡、VTS `is_speaking` 恒 False。产品判定"要口型"后，兑现留白的条件已成熟：消费者（口型分析）真实存在，且多平台渲染的真实诉求出现（VTS 参数 / Warudo 元音通道 / VRChat viseme）。

## 决策（Decision）

**兑现帧级通道，按"分接 — 分析 — 渲染"三段拆开，共享物只有两件：AudioSink 协议与口型分析器。**

- **复制挂在播放器**：`AudioDeviceManager`（全程序唯一出声出口，覆盖全量/流式两种播法）挂载一个 `AudioSink` 分接——开播/播完**同步**开关会话、每个音频块经 `feed` 递入。同步开关是硬约束：事件广播是事后通知，"开始播"的时机晚于首块音频写盘，拿不到正在播的音频。协议住中性的 `src/modules/audio/`（TTS 侧不依赖 avatar，依赖方向干净）；它就是 ADR-007 所说的帧级接口，未来任何音频消费者（口型 / 电平 / 录制）都走它。
- **一个共享分析器**：`LipSyncAnalyzer`（由 `LipSyncProcessor` 就地改造，`git mv` 保历史）实现 sink 会话形状，把音频分析成平台无关的 `MouthSignal`（嘴张开量 + 元音成分 A/I/U/E/O + 音量，归一化数值，**零平台参数名**）；渲染器注册进分析器，一具分析器扇出多具皮套，不重复计算。
- **映射与写入归各平台渲染器**：VTS 渲染器写 `MouthOpen` 并接管说话期间的表情基线维护；Warudo 渲染器写元音 blendshape 通道（启用时应关闭 Warudo 原生口型）；VRChat 无标准 viseme 通道且参数每 avatar 自定义，不接（能力差异的诚实面）。
- **调参落 `infra.toml [avatar.lipsync]`**：口型分析器是共享基础设施、非 provider，调参不进 provider 命名空间（组件配置随其架构类别走）；VTS 侧历史 lip-sync 键跨文件迁入（升版本 + 钩子 + 迁移测试）。

**工程纪律（不变式）**：

- **fail-soft**：口型是装饰性路径，分析器/渲染器任何异常只记日志，不得影响播放与决策；播放器对 sink 调用全链兜底。
- **非阻塞**：`feed` 只追加缓冲、立即返回（不阻塞播放写盘）；分析与写入在后台循环按真实时间游标推进，全量与流式同一模型。
- **表情与口型分工**：口型只写"嘴"；表情归情绪工具与适配器。说话状态解耦——idle"说话时暂停"改由 `tts.utterance.*` 事件提供，不在口型件里兼任。

## 替代方案（Alternatives）

- **删除 `LipSyncProcessor`**：撤回。它不是死代码而是按学说留白的预留件；产品判定即触发兑现，删除是错误处置。
- **TTS 引擎直接驱动口型（不设通用 sink）**：把消费者知识焊进生产者，下一个音频消费者（录制/电平）就要再焊一次；且引擎间播放路径差异大，重复实现。
- **事件广播开关会话**：`tts.utterance.*` 是终点广播、事后通知，拿不到正在播的音频，时序也不精确——被 D2 明确排除。

## 后果（Consequences）

- 播放路径多一层同步回调（`feed` 只追加缓冲，微秒级），声卡播报不受影响；sink 异常不影响播放（有测试锁定）。
- 配置基线推进（VTS 15 个 lip-sync 键迁 `[avatar.lipsync]`，开关键正名 `enabled`）；存量配置由跨文件钩子搬迁。
- `data-flow.md` 中"帧级通道未建"的两处过时表述随之更新；ADR-007 决策 5 的留白兑现，原决策文本不再需要"待真需求"限定。
- 新增第四种皮套后端时：实现一个 `LipSyncRenderer` 注册进分析器即可，分析零改动。
