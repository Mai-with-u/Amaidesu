# ADR-018：游戏无关边界——框架与主播侧不出现具体游戏名

- 状态：已采纳（2026-09-17）
- 日期：2026-09-17
- 实现提交：`1191613635a1ff58772a2bc7b1643e888de543ba`（refactor: 框架层去掉游戏名特例）、`0a8d9c6d68bed6ac9c951bdddce4c3f64cdf0707`（fix: 委派与提示词去掉 Minecraft 特例）

## 背景（Context）

系统三分：主播 Agent（唯一自我驱动）、游戏 Agent（命令驱动，按 `agents.enabled` 名单启停）、工具。游戏 Agent 可以有多个、可以换（当前有 Minecraft 与文字冒险两个），而"接的是哪款游戏"完全由配置的启用名单决定。

此前框架层与主播侧存在若干处写死的游戏名，各自都曾是"顺手写一下"的最小实现：

- 委派工具把目标注册名写死在参数说明里，主播的命令接线又把目标默认值定为 `minecraft`；
- 仪表盘 game 分类的启用判据列举了具体游戏名；
- 任务基建节拍在 `[tools.tasks]` 缺省时回落到 `[agents.minecraft]` 的字段；
- 身体事件 payload 的 `game` 字段默认 `"minecraft"`；
- 主播提示词里点名"注册名 `minecraft`"。

后果是同一个问题：**框架里出现了"默认游戏"这个并不存在的概念**。换一款游戏时，这些位置会静默地指向一个已经停用的 Agent——不报错、只是行为错位；改一处漏一处，且新人从代码里看不出这些散落点是同一条约束。

## 决策（Decision）

**框架层与主播侧不出现任何具体游戏名；接哪款游戏只由 `agents.enabled` 决定。**

具体落法：

- **可委派对象来自运行时名册**：委派工具的 `agent` 参数说明与取值枚举由 `AgentManager` 当前名册生成（每决策窗重新拉取，随启停变化）。目标可留空，由委派原语解析为"当前唯一启用的游戏 Agent"；候选不唯一即拒绝受理并报出候选、要求点名——不猜目标，避免把活派错游戏。
- **主播侧只说角色、不说名字**：提示词写"当前启用的游戏 Agent（注册名以该工具的参数说明为准）"，命令接线的目标默认留空交给框架解析。
- **分类判据按名册而非名单**：仪表盘 game 分类 = 名册里除框架自己的主播 Agent 之外的成员启用。
- **框架只读自己的配置段**：任务节拍只认 `[tools.tasks]`，不回落任何游戏 Agent 的字段。
- **跨模块数据由发布方自述**：身体事件的 `game` 字段必填，不给默认值——默认值会把"忘了填"伪装成"就是这款游戏"。
- **游戏名允许出现的位置**：游戏 Agent 包内（如 `src/agents/minecraft/` 里 Mod 的接口契约字面量）、装配登记表（注册名 → 类/配置 Schema 的映射）、以及各游戏自己发布的数据与事件。

## 替代方案（Alternatives）

- **把游戏名写进框架默认值**（原状）。否决：等于让框架假设只有一款游戏，换游戏就得改框架；且错位是静默的，只在运行期表现为"派给了一个停用的 Agent"。
- **在框架里按注册名分支特判**（`if name == "minecraft"`）。否决：把游戏知识搬进框架，游戏数量一多就退化成注册表；分支本身也是"这里有个默认游戏"的另一种写法。
- **让主播提示词点名游戏**。否决：换游戏必须改提示词，而提示词是给 LLM 的行为约束，不是游戏选择面；名字写进提示词还会诱导模型在别的游戏里说错名字。
- **给游戏 Agent 定分类层**（`[agents.game]` 公共段 + 类型判别字段）。已在 v2 架构中否决：Agent 之间无分类层，每个 Agent 自己拥有全部字段；游戏 Agent 的共性（命令驱动、接到命令才跑）由基类承担，不需要配置层再表达一次。

## 后果（Consequences）

收益：换游戏只改配置启用名单，框架与主播零改动；错位从"静默派错"变成"拒绝受理并说明候选"，启动与运行期都不再依赖某个游戏在场。

代价与需持续关注：

- **新增一款游戏仍要改装配登记表**：`src/modules/agents/factory.py`（注册名 → Agent 类）、`src/modules/config/registry.py`（注册名 → 配置 Schema）、`AgentType` 字面量、以及 `llm_profiles` 的封闭用途集合。这不是漏改，是"注册名必须有人认识"的登记代价；若将来登记表膨胀到难以维护，再讨论按约定发现（包内导出 Agent 类与 ConfigSchema）取代显式登记。
- **采集器的启停是独立名单**：采集器生命周期挂装配期、不随 Agent 起停，所以换游戏除改 `agents.enabled` 外，还要把对应的游戏采集器从 `collectors.toml` 的 `enabled` 里去掉。这是"待机时该流是否还在"这个问题的有意分工，不随本决策改变。
- **留空目标需要名册唯一**：多款游戏同时启用时，留空会被拒绝。需要同时驱动多款游戏时应显式点名，或由上层决定默认目标——名字由使用方给出，不由框架假定。
