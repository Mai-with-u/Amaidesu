# ADR-076：委派改为一件在做、其余待办，换活必须结单（废除急件暂放恢复 / 按短编号结单 / 主播决策与快嘴共读同一账本）

- 状态：已采纳；扩展 [ADR-013](013-async-task-infrastructure-and-delegation.md) 的状态词表与委派调度、细化 [ADR-034](034-agent-intervention-primitives.md) 的递话与取消边界，并废除急件暂放（`suspended`）原位恢复分支
- 日期：2026-11-12
- 实现提交：与本 ADR 同批交付（推送前按 dev 变基，hash 以推送后为准），按路径检索：`git log -- docs/decisions/076-delegation-one-in-hand-and-settle-on-switch.md`

## 背景（Context）

主播通过委派工具把游戏内目标交给游戏 Agent 执行。早期在"同一执行者一张在途单"之上叠加了"先进先出队列 + 急件插队暂放（`suspended`）与恢复 + 补充要求（`framework_prompt`）"，实机运行暴露出三处结构性断裂：

1. **换活走补充要求，导致账面单据与实际行动分叉**：当在途单实际已经做完、但游戏 Agent 没有主动调交付工具结单时，主播决策环节缺少"把在途单按已完成结掉并换下一件"的出口，只能用补充要求把新目标塞进旧单。结果几十分钟内决策参考段里的"手头在做的事"与快嘴通道（游戏事件触发的即时短句通道）读到的目标一直是早就做完的旧单原话，主播反复播报旧单没做完；排在队列后面的单子从未开工，却被误当成已经做完。
2. **急件暂放原位恢复路径失灵且易死锁**：急件插队把原在途单标成 `suspended`，等急件结束后只把账面改回 `running` 并投递一条普通通知，但执行侧的循环早已收工，普通通知叫不醒执行循环，原单与整条队列一起卡死；暂放成功后若新单被执行者拒收，原单也无法带进度回滚；主播本地工作台只留一格在途槽，暂放单被新单直接覆盖丢失。
3. **没有内部任务号就撤不掉单，且多出口各自记账**：内部任务号（`deleg_N`）为防模型照念对主播隐藏，旧取消工具却要求传任务号或只能盲撤在途单，排在队列里的作废单撤不掉；工具面与后台运营接口各自实例化受理器，主播工作台又在本地另存一份队列副本，三处状态互不同步。此外，玩家在游戏公屏发出的路点与坐标没有像观众弹幕那样作为来源原话随委派附带，导致游戏侧拿不到坐标。

## 决策（Decision）

核心一句：**每个执行者任何时刻至多一件"在做"，其余全部留在"待办"；换活必须当场把在做那件结清（做完了 / 先搁下 / 不做了）；搁下的件回到待办最前并记下进度，轮到时按新任务重新送达；任务账本是决策环节、快嘴通道与后台面板共用的唯一事实源。**

1. **状态词表与单一看板（`TaskLedger` + `delegation_board`）**：
   - 移除 `suspended` 状态与原位恢复路径。已送达未终态的状态只有 `accepted`、`running`、`waiting_for_decision`（合称**在做**，每个执行者至多一件）；排队等待的状态为 `queued`（合称**待办**）。
   - 终态新增 `closed_by_initiator`（发起方认定做完了结单），与执行者主动交付的 `succeeded` 在账面与事件载荷上严格区分：没有执行侧交付凭据而由发起方收尾的单子，下播记忆核对不把它当作执行侧证实完成的证据，快嘴通道也不拿它报喜。
   - 待办分两类：从未送达过的渲染为"还没开工"；做了一半先搁下的在账本条目上记下搁下时刻与执行者收手时回报的进度摘要，排在待办最前，渲染为"搁下了，做到：……"。轮到搁下件时，按全新委派调 `receive_delegation` 重新送达，指令由原委派原话拼上"当时做到：……"组成。
2. **换活必须结单与拒收原子回滚（`DelegationCore`）**：
   - 组合根装配唯一的 `DelegationCore` 单例，同时供主播工具面与后台运营 REST 接口调用。
   - 目标执行者已有【在做】时再调 `framework_delegate`，由 `when_busy` 明示：`queue`（默认）排入待办队尾；`replace` 换做新件（可传新 `instruction`，也可传 `item="待办N"` 把待办里已有的一件提上来做），且必须同时传 `current` 交代在做那件怎么结：`done`（记 `closed_by_initiator`）、`shelve`（回待办最前保留进度）或 `drop`（记 `cancelled` 作废）。
   - 换活按"收手 → 试送新件 → 结旧落新"顺序执行：先调执行者的异步收手接口 `release_delegation` 停掉当前在跑的游戏目标并拿到一句进度摘要（收手本身不提前改写委派终态）；再向执行者送达新件；若新件被执行者拒收，立即把原件连同刚拿到的进度摘要重新送回执行者，账面保持原件在做，不丢单也不卡队列。
3. **本场稳定短编号与独立结单出口（`framework_task_settle`）**：
   - 每件委派在场次内分配稳定短编号：当前已送达的叫 `在做`，待办里的按本场首次入队序号叫 `待办1`、`待办2`……，内部任务号继续对模型隐藏。
   - 用 `framework_task_settle(item, outcome)` 取代旧的按任务号取消工具，支持对 `在做` 或任意 `待办N` 执行 `done` / `shelve` / `drop`。撤掉某件待办只移除该待办，不触碰正在跑的在做件；结掉或搁下在做件后，待办队首自动送达。
4. **补充要求边界与两条机械兜底**：
   - `framework_prompt` 只给正在做的同一件事补要求（`kind="requirement"`，公屏回话走独立的直发工具 `minecraft_chat_send`，不再经递话让游戏 Agent 代打；底层保留 `kind="chat"` 仅作通用框架兼容）：要做的事或完成标准变了必须走 `framework_delegate` 或 `framework_task_settle`。
   - 机械兜底一：执行侧每次收到非聊天类补充要求时自动附带一句检查提醒——若原委派其实已经做完，先调完成工具交付原单再停手，不把另一件事塞进旧单。
   - 机械兜底二：主播参考段的【我手头在游戏里做的事】同时并列展示短编号、委派原话、已做时长与"游戏那边此刻实际在做"，原话与实际动作一旦脱节当场可见。
   - 游戏侧用递增的收手纪元号（`_release_epoch`）隔离批次：在途推理或工具返回跨越了一次收手后立即中止收尾，防止旧批次把新送达的单子误记进展或冲掉状态。
5. **看门狗看实际活动**：
   - 在途看门狗从"只盯 `accepted` 久未转 `running`"扩为盯全部【在做】单的实际活动，并挂低频定时检查（不依赖事件触发才跑）：当该执行者名下没有任何正在跑的子目标，且距上次目标或工具活动超过阈值仍未交付时，附带短编号向发起方发一次升级提醒（结单 / 补充换做法 / 先搁下）。
6. **主播侧同源读取、公屏原话随单附带与近期目标成败流**：
   - 主播工作台删除本地排队列表，每次渲染决策参考段与生成快嘴现场卡前都从同一份账本看板同步，消除决策环节与快嘴通道的目标分裂。
   - 决策环节派单或发补充要求时，系统把本窗观众弹幕与近期游戏公屏玩家发言（含路点、坐标、地点名、物品名原文）一并去重附在 `[来源对话]` 段送达执行侧。
   - 任务账本在移除终态条目时保留近期游戏子目标成败结果的有界缓冲，主播侧每窗直接查询账本并在【游戏那边此刻】生成跨委派保留的"近期目标成败（成了 / 做了一半 / 没成 / 取消了）"紧凑清单（结果摘要优先于意图前缀，整块除速览外仍严守 600 token 上限），配合守则约束完成类说法与被指出卡住时的对账认账。

## 替代方案（Alternatives）

### 修补原有的 `suspended` 暂放与通知唤醒路径

**拒绝**。`suspended` 要求执行者同时维护两套上下文并在急件结束后无缝接回旧循环，而游戏世界的位置、背包、昼夜与周围实体在急件期间早已变化，旧循环里的中间推理和观察编号已经失效。把搁下件退回待办、轮到时带上"当时做到哪"按全新委派重读现场再做，状态机少一整个分支，且天然契合游戏世界已经改变的事实。

### 让游戏侧或框架根据子目标自动猜测委派已完成

**拒绝**。一件委派往往包含多个子目标（如先取材、再合成、最后摆放到位），单个子目标成功不等于整单完成；反过来有些单子做到观众满意即可收尾。由执行者明确调完成工具交付，或由主播决策环节对照现场显式调 `done` 结单（记 `closed_by_initiator`），权责清楚且不把半成品误报为完工。

### 把内部任务号 `deleg_N` 直接暴露给决策模型管理队列

**拒绝**。直播实测多次证明内部机器编号一旦进入决策上下文，容易泄漏进交接稿被主播照念给观众听。用自然中文短编号（`在做`、`待办1`）既满足精确点名任意在途或待办单，又即使被顺口提到也符合日常口语。

## 后果（Consequences）

- **收益**：彻底消除急件恢复死锁、单据与实际动作分叉、快嘴复读旧目标、未开工待办被误报完成以及无任务号撤不掉作废单五类线上故障；工具面、快嘴与后台面板读同一份账本真相。
- **代价与后续观察指标**：
  - 换活拆单与搁下重送达会让游戏 Agent 按新单重读一次开局现场，单场游戏侧输入 token 会随换单频次小幅增加。
  - 发起方获得主动 `done` 结单出口后，若未仔细核对现场可能提前误结单；下一场复盘需重点盯三个配套指标：**结单后 10 分钟内又重派同一件事的次数（误结单率）**、**搁下后到下播仍未被重新送达的件数**，以及**每场"在做"为空的总时长**。
