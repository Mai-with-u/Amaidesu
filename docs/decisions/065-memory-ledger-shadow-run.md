## 背景（Context）

现在的跨场次记忆是三份自由文本：每场一份回顾（`session_recaps`）、一份长期笔记（`MEMORY.md`，"答应过的事""长线目标""老梗"等分节），加每位常客一段印象（`viewer_profiles`）。三份都由模型在收播时整段改写，读的时候也整段塞进 Planner 的提示词。

这套写法有三个结构性问题：

1. **"她答应过的事"没法可靠地了结**。它是一行自由文本，靠模型下次合并时自己判断有没有做完；做完了不删、说放弃不改、重复的记两遍，都看不出来。运营者发现记错时也只能整份笔记重写，没有"这一条判误记，以后别再记回来"的表达。
2. **读的成本随场次增长**。长期笔记是累积文本，越写越长，开播整份注入；场次回顾一写起来就是几百字，注入几场就上千 token，而这些字里大部分与眼前这一批弹幕无关。
3. **没有可核对的证据面**。模型写的"我答应过老王下次玩恐怖游戏"没有原话可查，运营者无法判断是它编的还是真说过；写错了也删不掉那一句，只能整段重写。

这套旧形态由三篇决策逐步加厚：ADR-042 把记忆收成场次回顾与观众画像两样，各按场次时间序与观众身份直取，退役了按人抽事实的通用记忆层；ADR-051 在上面加一份纯文本长期笔记 `MEMORY.md`，收播时整份合并、开播时冻结注入，正式与彩排各一份；ADR-058 再把长期笔记做成"每行一条 + 行尾标签"，模型只给条目操作、代码逐条执行，没人再提的条目按场次淡出，按对象与游戏分发注入，并保留写入留底可撤回。三篇共同的假设是：记忆的载体可以是一段人可编辑的自由文本，模型负责维护它。实际运行下来，行级状态靠行尾标签硬扛、写入靠模型自觉、读出靠整段注入，账目始终没法与"她真的说过哪句"对上。本系列把记忆改成两条带原话引用的账（承诺与场次档案），由代码对台词逐字核对、按线索分发，因此这三篇旧决策连同它们的载体一起退役。

## 决策（Decision）

核心一句：**把跨场次记忆改成两条可核对的账——承诺账本（`commitments`）与场次档案（`archive_lines`）——由每个正式场的下播整理写，条目自带她说的原话片段；本阶段先只写不读，旧的三份记忆照常注入。**

1. **两张表就是全部新记忆**。承诺一行 = 一件她当众答应过、还没了结的事（动作标题、原话片段、对某位观众、挂哪个游戏、状态）；场次档案每场至多 8 行（标题加原话片段）。两张表都长期保留，对象观众被删除时对 ta 的承诺随删除函数一并删掉。
2. **写在下播整理，分三次调用，每次只做一种判断**：场次档案、找新承诺、了结旧承诺（本场之前没有未了结承诺就不调第三次）。不随场长增加调用次数，一场最多三次模型调用，比现在最多七次少。
3. **判据是代码，不是模型自律**。原话必须是所引那一行台词的逐字子串（超长丢弃）；挂的游戏必须是本场玩过的（否则置空）；说"对某位观众"的，那一行必须真的在回应一条真实观众的弹幕（对不上就不登记，进未登记清单）；与未了结的旧承诺是同一件事、或那句台词已经引用了某条承诺，都不新建；了结只改未了结的行，模型改不动运营者判过的结论。
4. **判误记留墓碑**。运营者判误记的行转成 `void` 而不删除：之后每次"找新承诺"都能认出同一件事，不会重新登记回来；要彻底清掉另有"删除"。
5. **失败不丢场，也不无限重试**。任何一次调用失败、输出读不懂、输入超出模型窗口，这一场整场不提交（一个事务写完，半场写进去会重复登记），重试次数加一并把原因写进整理报告；第三次失败后不再自动补跑，等运营者在 WebUI 点"重新整理"。一场失败不挡后面的场。
6. **先影子运行**。本阶段账本只写不读：Planner 仍用旧的场次回顾、长期记忆与画像；账本在 WebUI 里能查、能改、能看整理报告。攒够真实场次并过了评测门槛再切换注入，切换与清理旧存储另开提交。
7. **整理报告给人看**。校验没通过的条目连同原话进未登记清单，在 WebUI 里逐条显示"模型想登记什么、为什么没登记"，运营者认为是真的就手建。

## 替代方案（Alternatives）

### 继续用自由文本，只把提示词写得更严

**拒绝**。问题不在措辞而结构：自由文本没有行级状态，说完的事没法标记了结，记错的那一条删不掉，原话也没处核对。提示词再严，模型仍会把客套话记成承诺、把放弃的说成还没做。

### 直接一次切换，不跑影子阶段

**拒绝**。新账本依赖提示词质量：难负例（玩笑、推辞、转述、做不到的事）误登记率与红队样本的误登记条数没有历史数据，直接切换意味着拿真实直播试。先只写不读，可以在不影响直播的前提下拿真实场次量召回与误登记，再决定要不要切。

### 由模型自由写整段 JSON 台账，代码只做格式校验

**拒绝**。承诺是否成立、对谁说的、挂在哪个游戏，全靠代码对着台词行逐条核；只校验格式的话，模型编一句没说过的话也能进账，等到它下次照着这句编出来的话行动时，观众听到的就是她答应了没答应过的事。

### 把账本直接做成 Planner 的注入源，旧存储立刻停写

**拒绝**。切换前没有真实数据可验证，旧的三份记忆一旦停写，回滚就没有内容可退；而且删表、删文件是不可逆动作，应当与可逆的切换分开做。

## 后果（Consequence）

- 每个正式场多一到三次 summary 档位调用（无未了结承诺两场次调用、有则三次）；比现在的收播整理少，且不随场长增加。
- 两份记忆并行写一段时间：存储与模型调用增加，但旧注入路径完全不变，直播表现与现在一致，可随时停掉新整理而不影响任何现有能力。
- 需要新的 WebUI 面：账本查看、了结、判误记、删除、手建、整理状态与未登记清单、删单行档案。运营者在切换前还要把旧笔记里值得留的条目手建过来。
- 承诺的可靠性从此有代码守着：原话可核对、了结只由她明确的话或运营者决定、判误记不会被重新登记。代价是"模型看懂了但代码判不过"的条目会进未登记清单，需要人偶尔扫一眼。
- 删除函数、身份合并、场次删除都要认得这两张表（已接好）：删观众顺手删对 ta 的承诺，合并把承诺改挂到合并后的观众，删场次删该场档案行但不删承诺（承诺自带原话）。
- 存储升一版（`commitments`、`archive_lines` 两张表，`live_sessions` 加整理进度三列）；存量场次一律标成已整理，不在升级后集中补跑历史场次——代价是升级前各场说过的承诺不进新账，需要运营者手建。
