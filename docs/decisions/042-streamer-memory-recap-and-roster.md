# ADR-042：主播记忆改为场次回顾 + 常客名册（退役事实提取与通用记忆层）

- 状态：已采纳
- 日期：2026-10-15
- 实现提交：`c339e2f387b51da2fc13da11d238185edcb708df`（feat(storage): 新增场次回顾表并退役观众事实表）+ `5506c5b72be65ae74522598dc93268d63e746671`（feat(streamer): 收播整理场次回顾与常客名册）+ `e79617025f32a48a4bd10521902e0e22a461dc84`（refactor(memory): 删除通用记忆层与记忆工具开关）

## 背景（Context）

旧记忆系统照搬了 MaiBot 的人物记忆管线：后台 60 秒循环从最近 20 条弹幕里让 LLM 抽"关于某观众的事实"落 `viewer_facts`，再按观众增量压缩成 `viewer_profiles` 画像，决策前把本批发言人的画像注入 Planner，另开 `query_memory`（事实 LIKE 检索）与 `query_viewer_profile` 两个工具，`src/modules/memory/` 以"通用记忆设施"自居并保留一个 `MemoryProvider`（`recall` / `ingest`）协议。

这套模型是**参与者视角**：MaiBot 是群聊里的一员，面对有限的一群人、长期多轮对话，核心问题是"这个人跟我说过什么"，按人组织事实、做语义检索是对的。主播是**一对多广播**，记忆问题换了主语。从"主播有什么不能从现场重新推出来、必须自己记住"出发，有三类：

1. **自己的经历（跨场次）**：上场做到哪、答应过观众什么、玩过什么梗。旧系统完全没有：`timeline_summary` / `topics` 只有写面，前情提要只活在本场，开播即失忆。
2. **对常驻观众的认识**：旧系统唯一覆盖的一类。但直播里绝大多数发言是"666""来了"，能认人的信号大半是结构化的（付费、牌子、来了几场），已经直读；每 60 秒抠 5 条"事实"那一层是群聊语境的产物，产出稀薄。
3. **当场的工作记忆**：时间线 + 前情提要（ADR-040）已经处理好，不是问题。

此外还有三处结构性别扭：

- `query_memory` 是对事实文本的 LIKE 子串匹配，Planner 守则又要求"1~3 步内收敛"，模型既不知道该拿什么关键词查，查到的也是零散第三人称短句；`viewer_facts` 实际只是画像的中间原料。
- `MemoryProvider` 协议零实现者，`backend` 只剩一个可选值，属于"预养空壳"。
- `modules/memory` 号称通用，但每一行都是观众事实与画像；真正的编排（提取提示词、画像生成、付费原料）全在 `agents/streamer/background.py`。按组件判据，这就是主播 Agent 的业务逻辑。

## 决策（Decision）

核心一句：**主播的记忆只有两样，各按自己的键索引——场次回顾按场次时间序，常客名册按观众身份；两样都在收播时整理，开播与决策时按键取用，不做自由文本检索。**

### 场次回顾（`session_recaps`，新表）

- 一场一行，`live_session_id` 唯一，记录开播 / 下播时刻与回顾正文。
- **收播写**：`live.ended` 后主播 Agent 在后台用 summary 档位模型总结本场。原料全部按场次主键从库表取：主播自己说过的话（`live_chat` assistant 行，承诺与梗都在嘴里）、话题摘要轨迹（`timeline_summary`）、游戏里程碑（`game_events`）、本场最活跃的观众与付费三表。空场次（无明细行）不写。
- **启动补写**：进程异常退出没跑到收播钩子的场次，下次启动补写最近一场（只看已结账且无回顾的）。
- **开播注入**：`live.started` 时读出最近 `recap_inject_count`（默认 1）场回顾（排除本场），作为参考段最前面的"上场回顾-内部参考"整场固定不变——整场不变的背景放最前，不破坏前缀缓存。
- **工具**：`memory_recall_session(n_back)` 取往前第 n 场（1 = 上一场，排除进行中的本场）。

### 常客名册（`viewer_profiles`，沿用表结构）

- 身份键 `(platform, user_id)`（ADR-029）；印象文本不存昵称（随改名漂移），注入与工具查询时经 `viewers` 实时解析。
- **收播更新**：候选 = 本场弹幕最多的观众，且 `viewers.interaction_count` 达 `roster_min_interactions`（默认 3）；每场最多 `roster_batch_max`（默认 5）人。原料 = 旧印象 + 该观众本场在原料水位之后说过的**原话** + 付费与身份直读（累计付费、最近明细、付费时的牌子 / 舰队快照）。一次 LLM 调用融合，写回并推进水位；失败逐人降级（印象不动、水位不推）。
- **有印象才注入**：本批发言人逐人查印象，没有就跳过不占位（沿用旧规则）。
- **工具**：`memory_recall_viewer(nickname | user_id)`。

### 退役

- `viewer_facts` 表（存储 v15 迁移 DROP）、60 秒循环里的事实提取（摘要循环回到一句话话题摘要的纯文本契约）、付费消息直落事实。
- `query_memory` / `query_viewer_profile` 工具与 `[tools.memory]` 配置段（tools.toml v2.0.45 钩子删除）。
- `src/modules/memory/` 整包（含 `MemoryProvider` 协议与 `SimpleMemory`）。存储装配改由 `src/modules/storage/bootstrap.py` 的 `build_database` 承担。

### 落位

- 生成、注入与工具逻辑归 `src/agents/streamer/memory/`（主播 Agent 的业务逻辑）；两张表的仓储 `ViewerProfileRepo` / `SessionRecapRepo` 在 `src/modules/storage/repos/`，与其他表域同级。
- 记忆工具注册名单只含 `streamer`，随主播 Agent 启停，没有独立开关；工具页归入随 Agent 启用的 `memory` 分类。
- 行为参数在 `[agents.streamer.memory]`（纯新增字段，漂移写回自动补默认值）。

## 替代方案（Alternatives）

### 保留事实层，换语义检索后端

**拒绝**。问题不在检索精度，而在记的东西不对：直播里按人抽事实产出稀薄，主播真正缺的跨场次经历根本不在这条管线里。加 embedding 只会把一个空转的检索做得更贵。

### 场次回顾按章持久化（把本场前情提要落库，开播时拼接）

**暂不采纳**。前情提要是为本场上下文预算服务的，篇幅、粒度与"下次开播要记得什么"不同；收播时用整场原料单独总结一次更贴目的，成本也只有一次调用。若以后发现收播总结丢细节，再考虑把章节作为回顾的原料之一。

### 常客印象继续在 60 秒循环里增量更新

**拒绝**。逐分钟更新让 summary 档位持续空转，且直播中途的印象变化对本场决策几乎没有价值——本场对话本身就在上下文里。收播时整理一次，原料完整、成本可控。

### 保留 `MemoryProvider` 协议作为外部记忆后端的入口

**拒绝**。零实现者的接口门违背"不预养空壳"；真要接外部记忆系统时，按那时的真实需求设计接口。

## 后果（Consequences）

- 主播开播即带上一场的回顾，能接上"上次答应的事"；跨场次连续性首次有了载体。
- 摘要循环的 LLM 调用回到纯话题摘要，输出更短；记忆整理集中在收播后台，两次调用（回顾 + 名册批量）。
- 常客印象的更新粒度从"分钟"变为"场次"：本场新形成的认识要到下场才进注入段（本场靠对话上下文本身）。
- 观众事实的人工逐条清理入口消失，名册页只剩印象的查看、纠正与删除。
- `session_recaps` 随场次删除级联清理；回顾正文由 LLM 生成，质量依赖 summary 档位模型，失败只降级不阻断直播主链路。
