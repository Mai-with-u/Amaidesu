# ADR-040：上下文分层与检查点（按窗口比例定预算 / 只追加 / 按章压缩 / 图只挂尾部）

- 状态：已采纳
- 日期：2026-10-14
- 实现提交：`f990ff6a7d471b38719fe4c05aaee007abf5b0bc`（feat(context): 新增上下文分层原语与窗口查询）+ `dc1896c22a678d76feaee3c3673581489b233968`（perf(vision): 截图只挂下一次请求尾部）+ `9a6ba7affd4972dbca87835447f6cbdec2d0aa0d`（perf(minecraft): 上下文预算改 token 并按段追加摘要）+ `c1c93875f9532ca0334939960005f3b1992e2f76`（fix(context): 前缀自检与计量按对象缓存结构哈希）+ `a1b01380619569947abb16c537b08305b71e43fd`（feat(streamer): 对话历史改由只追加时间线投影）+ `b6b2cc62313f5e07cb6ab760fb0686a8c7292be6`（refactor(llm): 退役 profile 历史预算与旧压缩器）+ `3cf3c97afaf8118e6fe56ce4cbdb667eda850970`（feat(streamer): 游戏里程碑与委派进入时间线）

## 背景（Context）

三个 Agent 各有一套上下文策略，单位、配置位置与缓存纪律互不相同：

- 主播 planner / replyer 按 `[llm_profiles.*].history_token_budget`（默认 8000 token，模型窗口 1M）逐窗从最老处规则抽取压缩。边界每窗前移、摘要头带变化的条数，一旦触发就让紧跟 system 的前缀逐窗失效；抽取只截前 1200 字，留下开播最早的内容、丢掉刚压的一段；planner 与 replyer 各压一遍。
- MC 按 `max_context_chars`（默认 16 万字符，实测约 55k token）触发阻塞的 LLM 摘要。09-25 与 10-05 两场每约 95–100 秒整理一次，10-05 合计 38.7 分钟角色站着等摘要；每次整理又把上一份摘要连同新记录重写，细节层层丢失。
- 截图以引用留在历史里，引擎对之后不足两轮的引用注水、过窗就地换成文字：同一张图付两次视觉编码，MC 的历史中段被改写，之后的前缀缓存全部失效。

决定每次请求成本与质量的四种力是：信息需要、服务端前缀缓存（越靠前的字节变化代价越大）、同步摘要带来的延迟、长上下文注意力衰减。原有实现没有一处统一回应它们。

## 决策（Decision）

**一次请求按易变程度分四层，越稳定越靠前；稳定层只追加，改写只发生在低频成批的检查点；预算按模型窗口比例换算，由消费方 Agent 定策略；易逝内容（图片）不进可持久层。**

- **四层布局**：L0 系统提示词 + 工具声明；L1 检查点摘要（按章/段只追加）+ 不经摘要的固定事实；L2 上次检查点以来的原始记录（只追加）；L3 每次请求现拼的尾部（情境、相对时间、"新"标记、临时图片），用完即弃。
- **框架原语与 Agent 分工**：`src/modules/context/` 只提供与具体 Agent 无关的机制——按窗口比例换算预算与三条水位线（预算 / 提前整理线 / 整理后回落线）、带缓存的 token 计量、按组切分（工具调用与回执同进退）、后台检查点准备、前缀稳定性自检、尾部临时图片。每层放什么、摘要怎么写留在各 Agent 包内，框架不出现游戏名。
- **预算归属**：窗口是模型属性（`[[llm_models]].context_window`），比例与上限是 Agent 策略（`[agents.streamer.context]`、`[agents.minecraft.context]`）。有效预算 = min(窗口 × 比例, 上限)；窗口未配置按 128k 保守换算。`history_token_budget` 退役。
- **检查点**：越过提前整理线就在后台准备下一章/段摘要，涨到预算时直接替换，决策热路径不等摘要；一次压到回落线，两次检查点之间前缀不变。摘要只覆盖上次以来的原始记录，旧章/段原样保留；MC 旧段总量超过预算两成时才一并并入新段，主播侧摘要迟迟不来、涨到预算两倍时才同步用占位说明兜底。
- **主播时间线**：planner 与 replyer 共用 `StreamerTimeline` 投影——`live_chat`（仍是对话事实源，ADR-015 不变）与未落库对话轮、游戏里程碑、"我在哪个游戏里开始做什么"按主播第一次看到的先后只追加；游戏记录行首写绝对时刻，相对时间只在参考段。场次变化时清空重来。
- **图片生命周期**：工具回执写进历史的始终是文字观察，图句柄只挂在紧随其后的那一次请求尾部（一条 user 消息），用完即弃；引擎只认最后一条 assistant 之后的图片引用。本条取代 ADR-037 中"工具消息携带图像"与"图生命周期 = 单个工具回合（两轮可见）"两项；能力协商与按需 VLM 不变。
- **缓存纪律可测量**：Agent 每次请求前把稳定层交给前缀自检，检查点与开新任务之外的改写记告警。

## 替代方案（Alternatives）

- **保留 profile 级 token 预算，只把默认值调大**：止血有效，但逐窗挪边界破坏缓存、抽取式摘要保旧丢新这两个结构问题仍在；预算也仍挂在模型用途上，与"消费方定策略"不符。
- **主播侧也用同步 LLM 摘要**：一次摘要 20–150 秒，直播决策窗承受不起；后台提前准备 + 到预算直接替换才不阻塞。
- **每次整理重写整份摘要（MC 原做法）**：实现简单，但摘要的摘要层层丢细节，且每次整理都改写整个 L1；按段追加只在旧段过多时合并一次。
- **按时间戳重排整条历史（而非首次看到的先后）**：迟到落库的记录会插进已发过的前缀中段，缓存失效；首次看到即定序只影响同一窗内新条目的相对先后。
- **图片保留两轮再换文字（原做法）**：多付一次编码费，且改写历史中段；模型看图那一步的文字说明已足以承载画面信息。
- **把游戏里程碑只留在参考段**：15 分钟后不再回放，换章时也写不进前情提要；进时间线后成本只是少量文本。

## 后果（Consequences）

收益：

- 默认预算从 8k / 约 55k 提到窗口比例（主播窗口四分之一、上限 128k；MC 窗口一半、上限 200k），10-07 量级的直播整场不触发主播检查点，MC 整理频率按实测会从每分半钟一次降到个位数。
- 两次检查点之间请求前缀逐字不变，图片不再改写历史；前缀自检让回归可见。
- planner / replyer 只算一份历史；游戏进展与主播自己的委派留在整场时间线里，前情提要可以概括它们。

代价与需持续关注：

- token 计量用 tiktoken cl100k 估算，对中文比 DeepSeek / MiniMax 偏多，预算偏保守；真实成本以 API usage 为准。
- 主播时间线与章节、MC 历史均在内存，进程重启后从 `live_chat` 重建对话，但前情提要与游戏记录会丢失；从 `game_events` 回灌留待后续。
- 主播委派的状态仍由 `game.report` 驱动：账本里主播委派的发起方记为调用场景名（`planner-react`）而非 Agent 名，BaseAgent 的任务唤醒对主播不生效；MC 也只在注入任务基建时才写账本。改为读账本前需先修正发起方命名。
- 配置迁移：`agents.toml` 与 `model.toml` 升 2.0.44（MC 字符预算换算、profile 历史预算删除）。
