# ADR-070：MC 上下文由模型在后台主动折叠（同前缀整理请求 / 原文进块库可取回 / 到预算线先收起不等摘要）

- 状态：已采纳；扩展 [ADR-040](040-context-layering-and-checkpoints.md) 的工作层整理（只用于 Minecraft Agent）——集中整理与按段追加摘要不变，退为第二道；ADR-040 里"涨到预算时直接替换、决策热路径不等摘要"这一条，MC 侧改由本篇的"先收起"兑现
- 日期：2026-11-05

## 背景（Context）

ADR-040 之后，MC Agent 的历史超过预算（窗口的一半，最多 20 万 token）就集中整理一次：另调一次摘要模型，把旧调用组压成一段摘要。实测这条路有三个问题：

- **角色会站着等**。每一步开始前历史一旦超预算，就同步等摘要写完，一次 20–150 秒。让出等待时虽然会在后台提前整理，但醒来时没做完、又已超预算，照样要等。一个长任务不让出等待、一路做到预算线，就一定会撞上。
- **摘要模型只能猜**。它按位置从最老处压，不知道哪些回执已经用完、哪些编号和坐标后面还要用；摘要请求的系统说明也与行动步不同，几十万字的历史整段按原价重新计费。
- **压掉的就回不来**。摘要漏掉的坐标、报错原文只能重新查一遍游戏。

billion-context 项目给出了另一种思路：让刚读过这些记录的模型自己挑出已经用完的区间、自己写摘要，原文留着可以取回。它面向编程助手、做成代理层，有三级蒸馏、原地还原等一整套机制。本篇只借它的思路，按本项目的约束用 Python 重写，没有复用它的代码和提示词。

## 决策（Decision）

**MC 的工作层由模型在后台主动折叠；原文进块库可取回；集中整理退为第二道；到预算线时先把旧记录收起来，不让角色等摘要。**

- **编号**：每条新追加的 user / tool 消息开头写上 `[m0012]`，模型用编号指定区间。编号只写在还没发出过的消息上，已发出的前缀不动；编号在 Agent 的整个生命周期里只增不减。
- **后台整理请求**：历史过了折叠线（默认预算的 40%），且距上次请模型又涨了预算的一成时，宿主另发一次请求：系统说明、工具声明、历史都与行动步完全相同，只在末尾多一条"宿主整理请求"，列出可折区间和各自体积。前缀相同，输入几乎全部命中缓存，只多付摘要的输出；身体同时照常行动。
- **折叠只碰旧区间，按编号套用**：模型调 `minecraft_context_fold` 给出若干区间与摘要。行动期间历史只在尾部追加，所以基于稍早那份历史算出的折叠，下一步开始前按编号重新定位就能套上。区间按"调用 + 回执"整组扩展；系统说明、任务事实、集中整理的摘要段、开任务的主播原话和最近几组都不能折；区间太小、摘要没比原文短一半的不执行。整理请求里模型调的游戏动作一律丢弃。行动中调用折叠工具不执行，回执让它继续推进任务。
- **取回是读一次，不还原到原处**：`minecraft_context_recall` 按块号读整块原文，或按关键词只取命中的片段，结果作为一次工具回执出现在尾部。billion-context 是把原文还原回历史中段，本篇没有照搬，因为那会改写已发出的前缀，与 ADR-040 的"只追加"相冲突。
- **到预算线先收起**：超预算、又没有现成摘要时，从最老的可折记录起，把单条较大的正文换成一行"原文已收起 b5，可取回"的占位，不调模型、瞬间降到回落线。收起后仍超预算才走同步整理；后台整理已在跑就先等它，不并起第二份改写。提前整理也从"只在让出等待时"放宽到"每步行动前都可在后台起"，醒来时不再等它或取消它。
- **两种后台改写互斥**：后台折叠与集中整理任一方在后台改写历史时，另一方不发起、写好的折叠也先不套用，避免彼此记下的位置对乱。开新任务、对话重开时，后台在跑的折叠与集中整理当场作废——集中整理写完会就地改写历史，晚一步就会把旧任务的摘要套到新任务上。
- **框架与 Agent 分工**：编号、折叠、块库、取回、收起和请模型的节奏判定放在 `src/modules/context/fold.py`，不出现游戏名；整理请求怎么写、摘要规矩、工具和何时请模型留在 `src/agents/minecraft/`。
- **开关**：`[agents.minecraft.context].active_fold` 默认开；关掉时不编号、不声明这两个工具，行为回到原来只靠集中整理。

## 替代方案（Alternatives）

- **让模型在行动步里自己折叠**（billion-context 的做法）：实现最简单，但写摘要的那一步角色站着不动，正是要解决的问题。
- **只改集中整理，不让模型参与**：可以把提前整理做得更积极，但摘要模型仍只能按位置猜，摘要请求也仍是一次不同前缀、按原价计费的大请求。
- **整理请求不带工具声明、要模型输出 JSON**：工具声明与行动步不同，前缀缓存就失效；JSON 正文的解析也比工具参数脆弱。
- **取回时把原文还原回历史原处**：模型看到的历史更完整，但每次取回都改写一次中段前缀，还要处理还原后再次折叠的往返。
- **照搬三级蒸馏**：本项目 MC 任务以单个任务为界、开新任务即清空，历史规模用不到第三级；旧块可以被新区间吞并，先只做一层。
- **主播 Agent 也用**：主播的历史是直播时间线的投影，不是她自己的工具调用记录；平常一整场连一次换章都触发不了，而且直播中她的注意力应该留给角色，不该分给整理上下文。

## 后果（Consequences）

收益：

- 角色不再因为整理上下文而站着等：折叠和集中整理都在后台，预算线上的兜底是瞬间完成的收起。
- 历史长期压在预算的四成上下，每步请求更小，长上下文的注意力衰减也更轻；集中整理只在折叠跟不上时出手。
- 折叠和收起都可逆，摘要漏掉的细节可以读回，不必重新查游戏。

代价与需持续关注：

- 每次后台整理要模型写一段摘要，多付输出 token；与行动步同时发出，同一时刻会有两条请求在跑。
- 折叠或收起会改写一次历史中段，之后那次请求要重算这一段之后的前缀；节奏判定（过线且再涨一成）用来避免频繁改写。
- 模型可能折得太狠（有取回兜底），也可能一直说"无需整理"（有集中整理和收起兜底）。实际折叠频率、省下的 token 与取回次数要在真实直播里看日志确认，默认比例是估算值。
- 收起产生的占位会一直留到被折叠或集中整理压掉；大条记录密集时，模型可能需要多次取回。
- 块库与编号都在内存里，进程重启即丢，与 ADR-040 中 MC 历史的现状一致。
