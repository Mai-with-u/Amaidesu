# ADR-058：主播记忆条目化、会淡出、按对象注入（部分取代 ADR-051 / ADR-042）

- 状态：已采纳；部分取代 [ADR-051](051-streamer-long-term-memory-file.md) 的"谁来写""结构与上限""注入"三条（存储位置、正式彩排各一份、管理入口不变），以及 [ADR-042](042-streamer-memory-recap-and-roster.md) 场次回顾的原料取法与观众画像的候选取法
- 日期：2026-10-30
- 实现提交：可用 `git log --grep` 按 subject 检索——`fix(streamer): 修复决策层备忘录恒为空因构造了两份`、`fix(streamer): 修复关应用后补整理丢备忘录因只存内存`、`fix(streamer): 修复回顾只看结尾致长场前半段丢失 + 原料加纠错`、`perf(streamer): 长期笔记与上场回顾挪进系统提示词`、`feat(storage): 长期记忆写入留底并核对版本`、`feat(streamer): 长期笔记条目格式与三种视图`、`feat(streamer): 长期笔记按条目合并并按场次淡出`、`feat(streamer): 收播合并长期笔记改为条目操作`、`feat(streamer): 长期笔记按对象与游戏注入 + 约定规则`、`feat(streamer): 收播合并认出人改过的行并记为人工`、`feat(dashboard): 长期记忆可看改动记录并撤回`、`fix(streamer): 修复画像只覆盖话最多几人因按条数取前几`、`fix(streamer): 修复长期笔记因多数后续场次而误搁置`、`feat(streamer): 长期笔记淡出按游戏场次与节区分`

## 背景（Context）

ADR-042 把主播记忆收成场次回顾与观众画像，ADR-051 加了长期笔记 MEMORY.md：收播时让模型把"旧笔记 + 本场回顾 + 备忘录"整份重写一遍，开播时整份冻结注入决策层与快嘴。按"一条记忆要有用，得在发生时记下来、留到要用时、要用时出现在眼前、内容是真的"逐条对照，这套做法在每一环都有缺口：

- **记不下来**。回顾原料按时间倒序只取最近 80 句主播发言、60 条话题摘要、40 条游戏事件，三小时的直播只看得到最后一段；原料超长时从尾部截断，排在最后的备忘录（模型自己沉淀的结论）最先被截。备忘录只活在进程内存里，直播中直接关掉应用、下次启动补整理时它已经没了。另有一处现成缺陷：主播 Agent 构造了两份备忘录对象，决策层读到的那份一直是空的。
- **留不住，也去不掉**。长期笔记每场被整份重写：没提到的条目靠模型自觉保留，人改过的内容会被改回去，改坏了没有旧版本可回。反过来，它又没有出口：做不成的约定永远挂着，压缩提示词还要求"不丢掉未兑现承诺"；主播看到笔记又提了一次，回顾记下"又提了"，合并时据此"不止一次被提起"，越记越牢——过气的梗、即兴编的"关于我自己"都会进这个循环。
- **出现得不是时候**。整份笔记每个决策窗都注入：答应某位观众的事，对方不在场时也对着全场挂着；快嘴提示词与冷场素材还鼓励她主动提起答应过的事。笔记与上场回顾虽然"整场不变"，却放在参考段里，参考段接在不断增长的对话历史之后，前缀缓存一次也吃不上。
- **未必是真的**。回顾的规则是"只写记录里出现过的"，可主播即兴说的话也在记录里；写进"关于我自己"之后，就以"你一直记着的事"的身份进了快嘴的系统提示词。观众自称的身份与关系同样会被画像当成事实。
- 画像候选取本场弹幕数前十五、凑满五个就停，每场都是那几位话最多的；只送礼不说话的观众从来进不了候选。

参照了 MaiBot 的 A_memorix（AGPL-3.0，只借思路不借代码）：关系强度按半衰期衰减，新证据回满、"被用到"只小幅加强且有冷却；跌破阈值先冻结不删除，有新证据可复活；原始记录不过期，推出来的结论才过期；事实账本不允许按时间悄悄覆盖，冲突要显式取代，每次状态变化留痕可撤回；画像按来源分可信度，设"不确定"区；只在相关时把记忆拉出来。它的向量检索、关系图、按小时衰减不适合一对多、断续开播、按身份直取的主播场景，也与纯文本的方向不符。

## 决策（Decision）

核心一句：**长期笔记仍是一份人能直接读、直接改的纯文本，但改成"每行一条 + 行尾标签"；收播时模型只给对条目的操作，代码逐条执行，没人再提的条目按场次淡出；注入按对象与游戏分发；每次写入留底可撤回。**

### 记得下来

1. **回顾原料覆盖全场**：发言、话题、游戏三类先取全场，再按时间均匀取样（首尾都在）；整体超长时先把发言隔行抽稀，抽到下限仍超才从尾部截断。备忘录排在场次头之后、不参与截断。新增"观众指出主播说错、记错的地方"一段（命中"记错""说错""不对"等说法的弹幕，连同主播前一句），给长期笔记改正用。回顾与画像超长时停在完整句子之后截短。
2. **备忘录落盘**：存储升到 v21，场次行加 `notebook_text`。备忘录工具每次写入都把全文落进进行中的场次行，回顾与长期笔记按场次主键读回；已结账的场次不接受迟到的写入。决策层、表达层、工具与收播清空共用同一份备忘录。

### 条目格式

3. 笔记分节：答应过的事、老梗与口头禅、长线目标、关于我自己（这四节注入），不确定（还没坐实，不注入），搁置（已淡出，不注入）。每行一条，行尾标签记代码要用的状态：约定的结局（未兑现 / 已兑现 / 放弃）、`对 昵称#观众编号`、`游戏 名字`、`始于 #场次` / `最近 #场次`（最近一次有新证据的场次）、`人工`、搁置来由。不认识的标签原样保留，人自己加的节与说明文字原样保留。整份没有标签的旧笔记按模型条目读，"（未兑现）"读成状态。

### 合并与淡出

4. **模型只给操作**：收播合并时给模型编号清单、人设、接入的游戏、本场观众名单、回顾与整理原料（与回顾同一份），模型只回 `add / seen / edit / done / drop / move / remove` 操作的 JSON，代码逐条执行，没动到的行一字不变。新增与已有相同按"续上"处理；观众编号不在名单里、游戏没接入就不挂对象；输出读不出操作时保留旧版本、不记合并时刻。
5. **人工条目只读**：没带标签的行、带 `人工` 的行、人自己加的节都是人工条目，模型对它的操作不执行，只记进改动清单。收播合并写下的全文另存为基线，下一次合并先拿当前文件和基线比：人新增或改过正文的行（WebUI 与编辑器都算）记成人工。
6. **默认会淡出**：续上（`seen`）只认观众在弹幕里再提或游戏里真的发生了相关的事，主播自己又念一遍不算。模型条目连续 `long_memory_stale_sessions`（默认 3）场同类型、写过回顾的场次都没有新证据，就挪进搁置区；已兑现或放弃的约定留一场让主播知道结果，之后也搁置。场次只数到正在合并的这一场为止，补合并旧场次时不把之后的场次算进去。口径按节区分：只跟某个游戏有关的长线目标与老梗只数玩过那个游戏的场次（看这场有没有那个游戏的游戏事件），连播几场杂谈不让游戏里的目标跟着过期；约定不管玩没玩照常数，做不成的宁可早点放下；"关于我自己"不按场次淡出——她是谁不靠观众复述，主播自己再提又不算证据，按场次数只会把人设慢慢磨掉。注入的四节合计超过 `long_memory_max_chars` 时，先搁置最久没被提起的模型条目（"关于我自己"排在最后）；人工条目永不搁置。搁置区的条目有人再提可以挪回；搁置区只留最近 30 条。
7. **记录的门槛写进合并提示词**：约定只记主播明确答应、而且做得到（接入的游戏里能做、直播安排上能做）的事；观众的请求、玩笑、客套不算约定；"关于我自己"只收与人设一致的喜好、习惯与立场，不收即兴编的经历；观众自称的身份关系只进"不确定"；不记"正在直播"这类只对这一场成立的话。

### 注入

8. **按对象与游戏分发**：决策层的系统提示词末尾放全场条目，且只放开着的游戏的；答应某位观众的事跟着 ta 的人物画像行走，ta 发言时才出现（没画像也给）；快嘴只拿全场条目。笔记在开播时解析一次，整场不变。
9. **整场不变的放系统提示词**：长期笔记与上场回顾从参考段挪到 Planner 系统提示词末尾，与人设一起吃前缀缓存；参考段只留随环节与本批变化的段。
10. **笔记是参考不是待办**：Planner 守则加"做不到的不答应"（越界与游戏里办不到的直接婉拒，答应了做不成就说明并在备忘录记放弃）与"笔记用得上时再用、不对着全场念叨"；快嘴的笔记说明改为"用得上时再用，不必主动提起"。回顾提示词区分主播答应的与观众只是请求的；画像提示词把观众自称的身份写成"他自称……"。

### 留底

11. 每次写入（收播整理、页面保存、恢复旧版本）把旧全文存成快照，来由、场次与逐条改动追加到改动记录，只留最近 50 条。写入带读出时的版本号，合并期间有人在 WebUI 保存，就在新版本上重做同一批操作。主播记忆页可看改动记录、只读查看改之前的全文、撤回某次改动（撤回本身也留底）。

### 画像候选

12. 候选改为本场发言人（前五十）加本场付过费的观众，达门槛、且上次整理之后这场至少说了两句或付过费才算；按"没建档的先来，其次印象最久没更新的"排序取每场上限。

## 替代方案（Alternatives）

### 保留整份重写，只在提示词里强调"别丢东西"

**拒绝**。问题在机制不在措辞：重写就意味着每一行每一场都要被模型重新决定一次，几十场之后磨损、改写、人改过的内容被改回去都会发生；也给不出"哪一行是谁写的、哪一场记的"，淡出、按人注入、只读都无从谈起。

### 结构化存储（SQLite 一张约定表）

**暂不采用**。功能上更规整，但失去"打开文件就能改"，也与 ADR-051 的纯文本方向相悖。行尾标签让代码拿得到状态，人照样能读能改，没有表也够用。

### 直播中由主播经工具实时增删笔记条目

**暂不采用**（沿用 ADR-051）。现场结论已有备忘录承接，且备忘录现在落盘，收播时沉淀即可；实时写会占决策步数，也更容易把临时状态写进长期笔记。

### 按小时衰减（A_memorix 的做法）

**拒绝**。直播是断续的，一周可能播三场、也可能停播半个月，按墙钟衰减会让停播期间的笔记无端过期；按"写过回顾的同类场次"计数才对得上"几场没人提"。

### 语义检索后按相关度注入

**拒绝**。与纯文本方向不符；主播场景下"相关"主要就是"这个人在场""这个游戏开着"，按键筛选足够，且不需要直播中额外调模型。

### 人在 WebUI 保存时就把改动行标成人工

**拒绝**。那要让仪表盘懂笔记格式，而且用编辑器直接改文件的情况照样漏掉；改为收播合并时对照上一次合并写下的基线识别，两种改法都认得出。

## 后果（Consequences）

- 做不成、没人再提的约定与梗会自己淡出，不再一场场挂在提示词里；主播自己念叨不会让一件事记得更牢。
- 答应某位观众的事只在 ta 在场时出现，全场注入只剩对全场的事；决策层每个决策窗少付约两千五百字的未缓存输入。
- 人写的条目受保护，模型改错了能在页面上撤回；合并记录写明每一条改了什么、没采纳什么。
- 收播整理的原料变大（全场取样、观众纠错、观众名单），一次合并的输入比原先长；模型仍是一次调用。
- 旧笔记第一次合并时整份按模型条目读入，之后带上标签；文件里出现 `〔…〕` 标签是正常格式，WebUI 面板写明了含义。
- 记忆的质量仍取决于 summary 档位模型是否守规矩（门槛、续上只认别人提起）；规矩写在提示词里，执行由代码兜底的只有结构性的部分（只读、淡出、篇幅、对象核对）。
- 以后与 MaiBot 两边都用时（"一个麦麦"），条目格式与"操作 + 留底 + 版本号"正好是两个身体共写一份笔记所需的基础；按"身份那一层的正本跟着常驻的身体走"的思路，正本会放在 MaiBot 一侧、Amaidesu 留缓存，届时另起 ADR。只用 Amaidesu 时不受影响。
