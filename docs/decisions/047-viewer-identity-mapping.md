# ADR-047：观众身份映射（账号 ID 与开放平台 ID 同行 / 同平台按昵称关联 / 超出时限转人工确认）

- 状态：已采纳（2026-10-25；取代 [ADR-029](029-viewer-identity-key-and-currency-unit.md) 的"身份键"一节，货币口径与付费明细部分不变）
- 日期：2026-10-25
- 实现提交：分批实现中，`git log --grep=ADR-047` 可检索各批提交

## 背景（Context）

ADR-029 把观众身份定为 `(platform, user_id)`：同一平台内，一个 `user_id` 就是一个人。这条规则默认每个平台只有一种用户 ID，B 站接入多种数据源之后，这个前提不成立了：

| 数据源 | 拿到的用户 ID | 说明 |
|---|---|---|
| 官方开放平台（`bili_danmaku_official`） | `open_id`，UUID 形式 | 开放平台文档里 `uid` 字段标为"已废弃，固定为 0"，拿不到账号 uid |
| LAPLACE Event Bridge（`bili_danmaku_laplace`） | 账号 `uid`，纯数字 | 来源是开放平台时 uid 恒为 0，事件里也不带 `open_id` |
| 旧版轮询（`bili_danmaku`） | 账号 `uid`，纯数字 | 未登录请求目前拿不到弹幕 |

三者都写 `platform="bilibili"`，于是同一个观众换了数据源就会分成两行：发言计数、付费统计、观众画像、同步给 MaiBot 的人物都跟着分裂。单看一行的 `user_id` 也分不出是哪种 ID。开放平台没有提供 uid 和 open_id 的对照，按 ID 本身无法把两者对上。

还有一处不确定：开放平台文档对 `open_id` 只写了"用户唯一标识"，另设一个"同一开发者下唯一"的 `union_id`（需单独申请开通）。按微信、抖音开放平台的同名惯例，`open_id` 很可能按应用划分，即换一个开放平台应用，同一观众的 `open_id` 也会变。

能把两种 ID 关联起来的依据是昵称：B 站昵称在同一时刻全站唯一，改名要花硬币，观众不会频繁改。但昵称会易主——老观众改名后，旧名字可以被别人注册——所以不能无条件信任。

## 决策（Decision）

核心一句：**观众表一行一个人（按平台），同一行里分别记账号 ID 和开放平台 ID；新出现的 ID 在同平台内按昵称精确匹配老观众，昵称在时限（默认 90 天）内出现过才自动关联，超出时限或候选不唯一就先建新观众并挂一条待确认的合并建议，由 WebUI 人工处理。观众改名时只更新当前昵称，曾用名另表记录、不参与匹配；明细里的名字保留当时的样子。**

### 观众表

`viewers` 的一行代表某个平台上的一位观众，`viewers.id` 是内部观众 ID，弹幕、礼物、画像等一律引用它。外部身份放在同一行的几列里：

| 列 | 含义 |
|---|---|
| `platform` | 平台标识，同 ADR-029（`bilibili` / `console` 等） |
| `account_id` | 平台账号 ID：B 站即 uid，账号永久不变、全平台公开 |
| `open_id` | 开放平台发给某个应用的用户 ID：B 站即开放平台事件里的 `open_id` |
| `open_app_id` | 发出这个 `open_id` 的开放平台应用 ID；`open_id` 为空时也为空 |
| `user_name` | 当前昵称 |
| `name_seen_ms` | 最近一次以当前昵称出现的时刻 |
| `simulated` | 是否模拟观众（模拟器生成） |
| `link_status` | `confirmed`（已确认）/ `pending`（待人工确认） |
| `link_candidate_id` | 待确认时建议并入的老观众 `viewers.id` |

原有统计列（发言、送礼、被回复、互动、付费）保持不变。唯一约束：`(platform, account_id)` 在 `account_id` 非空时唯一；`(platform, open_app_id, open_id)` 在 `open_id` 非空时唯一。

`open_id` 这个名字沿用开放平台的通用叫法（B 站、抖音、微信都用它指"平台发给某个应用的用户 ID"），以后接别的平台不用换名；`account_id` 和它对照，强调是账号本身的 ID。不用 `uid` 作列名，是因为 B 站开放平台里的 `uid` 字段恰好已废弃、恒为 0，容易混淆。

### 事件载荷

`RoomMessageUser` 增加两个字段，由采集器在装配期作为常量写入，和 `platform` 的做法一致：

- `id_kind`：`account` 或 `open`，说明 `id` 是哪种 ID。官方开放平台采集器写 `open`，其余采集器写 `account`。
- `open_app_id`：`id_kind=open` 时为开放平台应用 ID（官方采集器取自配置的 `app_id`），否则为空。

### 解析与匹配

解析由记账器（`StorageLedger`）在写入时完成，只对会更新观众统计的消息（弹幕、礼物、醒目留言、上舰）执行；进房事件不建观众。主播 Planner、观众画像整理、记忆工具这些读方，按 `platform` + 外部 ID 查观众，查不到就当新观众。

一条消息到达时：

1. **按 ID 命中**：同平台、同种 ID 列等于来值的行存在，就是这个人。每次命中都刷新 `name_seen_ms`；昵称变了则按下文"改名"处理。
2. **按昵称找候选**：ID 未命中时，在同平台、同 `simulated` 的观众里找 `user_name` 与来值完全相同、且对应 ID 列"空着"的行。"空着"指：来的是账号 ID，候选 `account_id` 为空；来的是开放平台 ID，候选 `open_id` 为空，或候选的 `open_app_id` 非空且与来值不同（换了开放平台应用）。对应列已经有另一个值的同名观众不是候选：同一种 ID 不同值就是另一个账号，说明昵称已经易主。存量行的 `open_app_id` 可能为空（见"存量迁移"），此时无法判断是不是同一个应用，按"已有另一个值"处理，不作候选。
3. **决定关联方式**：
   - 没有候选：新建观众，`link_status=confirmed`。
   - 恰好一个候选，且当前时刻减去它的 `name_seen_ms` 不超过时限：把来值写进候选的对应 ID 列（换应用时覆盖旧的 `open_id` 与 `open_app_id`），视为同一人。
   - 唯一候选超出时限，或候选不止一个：新建观众，`link_status=pending`，`link_candidate_id` 指向 `name_seen_ms` 最近的候选。消息照常处理，不等人工。
4. **占位昵称不参与匹配**：采集器拿不到昵称时填的占位名（如 `unknown`、`未知用户`，名单在代码里集中登记）、空昵称、带打码星号的昵称，一律跳过第 2 步，直接按"没有候选"处理。

时限按"这个昵称多久没出现过"计算，不按建档时间：两年前建档、昨天还在用这个名字的老观众应当自动关联；要防的是改名后旧名字被别人拿走，而这只和昵称最后出现的时间有关。时限做成配置项 `storage.toml` 的 `name_match_window_days`，默认 90。

### 改名

按 ID 认出观众、发现昵称和 `user_name` 不同时，把 `user_name` 换成新昵称，同时更新昵称记录。

**匹配只用当前昵称。** 上面第 2 步只比对 `viewers.user_name`，曾用名不会让一位观众成为候选。例：A 原名"甲"，改名"乙"且被我们看到；之后 B 注册了"甲"并从新数据源进来。只看当前昵称时没有候选，B 被新建，这是对的；若曾用名也参与，A 会成为候选，B 可能被并到 A 身上。曾用名对匹配也没有增益：A 改名时若没被我们看到，新昵称本来就不在任何记录里。

**明细里的名字不改写。** `live_chat.sender_name` 以及礼物、醒目留言、上舰明细的 `user_name` 记的是观众当时用的名字，属于历史事实；场次回放、对话记录、场次回顾的素材都按当时的名字呈现。

**昵称记录表 `viewer_names`**：每位观众用过的每个昵称一行（含当前昵称），列为 `viewer_id`、`user_name`、`first_seen_ms`、`last_seen_ms`，`(viewer_id, user_name)` 唯一。只在三个时刻写入：新建观众时记下初始昵称；改名时把旧昵称的 `last_seen_ms` 定为改名前的 `name_seen_ms`，并记下新昵称（改回用过的旧名则沿用原行）；合并时把两边的记录并到一起。当前昵称的最近出现时刻以 `viewers.name_seen_ms` 为准，不逐条消息写这张表。它的用处：

- **主播认人**：画像正文本来不存昵称，改名不会弄坏画像；但场次回顾是按当时的名字写的（"甲送了舰长"），主播不知道"乙就是以前的甲"就对不上号。注入画像时带上曾用名，写成"乙（以前叫甲）"。
- **按昵称查人**：`memory_recall_viewer` 先按当前昵称查；没命中再查曾用名，多位观众用过同一个名字时取 `last_seen_ms` 最近的一位，结果里注明对方现在叫什么。
- **WebUI**：观众详情页列出曾用名；待确认页同时展示候选的曾用名，帮助人工判断。

不从明细表反推曾用名：删除场次会连明细一起删掉，曾用名会随之丢失，这与 `viewers` 计数"历史累计、不随明细回滚"的口径不一致。

### 人工确认与合并

WebUI 提供"待确认观众"列表，处理方式参照 MaiBot 表达方式审核：

- **同意**：把待确认观众并入建议的候选。
- **改选**：搜索并选择另一个已有观众，并入它。
- **保持新建**：清除待确认标记，作为独立观众保留。

待确认期间，主播把这位观众当作新观众（读方查到的是新建的那一行，没有画像）。认错人对角色的伤害大于没认出来。

观众详情页另外支持手动把两个观众合并。合并（新观众并入老观众）的规则：

- 新观众有、老观众空着的 ID 列搬到老观众上；两边同一种 ID 列都有值且不相等（同一应用下）时拒绝合并——那是两个不同账号。
- 统计计数相加，`last_active_ms` 取较大值，昵称取 `name_seen_ms` 较新的一方，两边的昵称记录合并。
- 明细表里指向新观众的行改指老观众；画像以老观众为准，老观众没有画像时沿用新观众的。
- 删除新观众行。合并本身没有一键撤销，自动关联只在"时限内唯一候选"时发生，其余都交给人工；关联错了用下面的"取消关联"修。

**取消关联**：观众详情页可以把某一个 ID（`account_id` 或 `open_id`）从观众身上拆出去，用于修正自动关联或合并的错误。前提是这位观众还有别的 ID——只剩一个 ID 时没有可拆的。拆的步骤：

- 从原观众身上清掉这个 ID，用它新建一位观众。
- 明细表里平台、原始外部 ID 及其种类与之相同的行，改指新观众；新观众的昵称、`name_seen_ms` 和昵称记录取自这些明细。
- 新观众的计数按改指的明细重算，原观众减去同样的数。已删除场次的明细拆不出来，那部分计数留在原观众身上。
- 画像正文没法按人拆分，留在原观众身上；新观众从零开始。

### 存量迁移

存储结构版本从 17 升到 18：

- `viewers` 重建为上述结构，`name_seen_ms` 取原来的 `last_active_ms`。`platform=bilibili` 下纯数字的 `user_id` 写入 `account_id`；UUID 形式的写入 `open_id`，`open_app_id` 留空。`open_app_id` 为空的行在第一次被同一个 `open_id` 命中时补上当前应用 ID（迁移在存储层，拿不到采集器配置）。
- 旧版采集器修复前写下的行（`platform` 为空）：纯数字 `user_id` 按 B 站账号 ID 处理，与已有同 `account_id` 的行合并；`bili_` 加昵称这类无真实 ID 的行，保留为两种 ID 列都为空的 B 站观众，可作为昵称候选，同样受时限和人工确认约束。
- `live_chat`、`gifts`、`super_chats`、`guards` 增加 `viewer_id` 与 `id_kind` 两列并回填（`id_kind` 按 ID 形式判断：纯数字为 `account`，UUID 形式为 `open`）；原有的 `sender_id` / `user_id` 保留，作为当时收到的原始外部 ID。取消关联靠原始外部 ID 与 `id_kind` 找回属于某个 ID 的明细。
- 新建 `viewer_names`，从现存明细里按观众汇总用过的昵称及其最早、最晚出现时刻回填；只出现在已删除场次里的旧昵称找不回来。
- `viewer_profiles` 改为以 `viewer_id` 为唯一键。

## 替代方案（Alternatives）

### 每个外部 ID 一行的独立身份表

即 `viewer_identities(viewer_id, platform, id_kind, 应用范围, external_id)`，一个观众可以挂任意多个外部 ID。

**暂不采用**。它能容纳更多 ID 种类（如 `union_id`）、同时保留多个应用的 `open_id`、合并同一人的多个账号。但现有平台每种 ID 至多一个有效值，同行几列已经够用，"对应 ID 列是否空着"的匹配规则和 WebUI 展示都更直接。代价是换开放平台应用时旧 `open_id` 被覆盖，以及同一人的多个账号无法合并成一个观众。以后真要接第三种 ID，再加一列或改为本方案。

### 两个数据源同时连接，按同一条弹幕配对

同时开官方源和 LAPLACE 源，同一条弹幕两边各收一次，按文本、昵称、时间配对出 uid 与 `open_id` 的对应关系。

**拒绝**。需要同时维持两条连接，副源还不能发事件（否则主播收到两遍），实际直播不会这样开。昵称匹配加人工确认已经够用。

### 维持现状，只约定同一房间不换数据源

**拒绝**。官方源和 LAPLACE 源各有限制，换源是现实需求，约定挡不住分裂，分裂后也没有修复手段。

### 时限按建档时间计算

**拒绝**。老观众建档越早反而越容易被打进待确认，与"防昵称易主"的目的无关。

### 不设时限自动关联，或一律人工确认

**拒绝**。不设时限会把拿了旧昵称的新人认成老观众；一律人工则每次换数据源都会把所有回访观众塞进待确认队列。时限内唯一候选自动关联、其余人工，兼顾两头。

### 曾用名也参与昵称匹配

**拒绝**。昵称易主后，曾用名指向的是原主，用它匹配恰好会把拿到旧名的新人认成原主；而原主改名没被看到的情况，曾用名里也没有新名字可配。曾用名只用于展示和按名字查人。

### 改名时回写明细表里的名字

**拒绝**。明细记的是当时发生的事，场次回顾也是按当时的名字写的；把它们改成新名字会让回放和回顾对不上。认人靠昵称记录表补上新旧名字的对应。

### 从明细表推导曾用名，不另建表

**拒绝**。删除场次会连明细一起删，曾用名随之丢失；单独一张小表只在改名、新建、合并时写入，代价很小。

### 在事件链上解析，给载荷写入内部观众 ID

仿照场次归属拦截器，在事件分发链上解析身份并把 `viewer_id` 写进载荷，下游直接使用。

**拒绝**。解析可能新建观众，等于在事件链上写库；而且没开场次时消息不落库，事件链上建观众会打破这一约定。改由记账器负责写，读方按外部 ID 查询。

## 后果（Consequences）

- ADR-029 中"昵称不进任何身份判断"改为：**昵称不能当 ID 用，只用于在同一平台内把两个真实 ID 关联到同一位观众**。缺 ID 的消息仍然丢弃，不用昵称顶替。
- 事件契约变化：`RoomMessageUser` 增加 `id_kind`、`open_app_id`；各采集器（含模拟器、控制台）需写入。
- 读方全部改为"外部 ID → 观众"再取数据：Planner 画像注入、常客画像整理、`memory_recall_viewer`（`user_id` 参数改为内部观众 ID）、WebUI 观众接口（`/viewers/{user_id}?platform=` 改为 `/viewers/{viewer_id}`）。
- 同步给 MaiBot 的观众 ID 改用内部观众 ID，MaiBot 那边已有的人物会在切换时断开一次；合并会让被并入的观众 ID 消失，MaiBot 侧对应人物不再更新。
- 新观众的第一条消息：记账器和 Planner 并行消费同一事件，Planner 可能在关联完成前查询，这一条按新观众处理，后续消息正常。
- 新增配置 `storage.toml` 的 `name_match_window_days`（纯新增字段，不需要升级钩子）；新增 WebUI 待确认页、观众合并与取消关联操作；新增昵称记录表 `viewer_names`，画像注入与 `memory_recall_viewer` 带出曾用名。
- 仍有一种情况会自动关联错：观众改名时没被我们看到，旧名被别人拿走，这个人又恰好在时限内从另一种 ID 进来。这种情况很少见，出现后用取消关联修正；拆不回的只有已删除场次的计数和画像正文。
- 模拟观众与真实观众分开匹配，同名也不会互相关联。
- 跨平台关联不在本决策范围：不同平台的观众始终是不同行，不自动匹配。将来需要时另加"同一个人"的关联记录，统计仍按平台分开（各平台货币不同，见 ADR-029），画像可按关联合并读取；本方案的表结构不妨碍这样扩展。
