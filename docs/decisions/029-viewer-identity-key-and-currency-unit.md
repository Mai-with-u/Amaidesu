# ADR-029：观众身份复合键与平台虚拟货币口径

- 状态：已采纳（2026-09-23 定案，2026-09-24 实现）
- 日期：2026-09-24
- 实现提交：`525b86bf3c3c9ff42b538e0ac621145e6d4425f7`（v10 迁移：付费明细补全、身份复合键、付费统计）；`93fd68cdcd122d4b8b110643a2b4f776ed646fdc`（对照定案的偏差修复：user_id 缺失告警、付费口径过滤、换算常量收敛）

## 背景（Context）

实现观众画像的前提是把"观众"当作一等实体，但存储与事件层存在三块地基缺陷：

1. **单平台假设**：`viewers.user_id` 裸键 UNIQUE，`live_chat`/`gifts`/`super_chats` 无 platform 列；console 调试输入的用户与真实观众在同一个 user_id 命名空间里互相污染。`live_sessions` 虽有 platform 列但装配未传值，恒为 `'unknown'`——又一处"有列无值"。
2. **金额三套单位并存**：B 站礼物/上舰官方单位是金瓜子（1 元 = 1000 金瓜子），SC 官方单位是人民币元，`super_chats.amount` 存元浮点、`gifts` 表连金额列都没有。元与金瓜子的换算散落各处，是"×1000 静默 bug"的高危地形。
3. **付费事实大量丢失**：礼物金额、连击、盲盒、粉丝牌、舰队等级在采集层已解析但契约与存储全丢；上舰只落一行 live_chat 文本；SC 观众在 `viewers` 统计空白（只写明细表、计数走语义层，而语义层不按人组织——两级缝隙）。

官方单位口径（B 站直播开放平台文档三方交叉确证）：`SEND_GIFT.price`/`GUARD.price` 是金瓜子，`SUPER_CHAT.rmb` 是人民币元；免费礼物按银瓜子计价，无金钱价值。

## 决策（Decision）

核心一句：**观众身份键 = `(platform, user_id)` 复合键；付费金额统一平台最小虚拟货币单位、取标价口径；付费事件不可复刻，存原始 JSON 兜底。**

### 身份键

- 不同平台账号视为不同的人。platform 是本项目自定的稳定键：平台名（`bilibili` / `douyin` / …）+ 调试保留字 `console`，由采集器作为**装配期常量**统一注入（先例：`LiveSessionManager` 构造参数），不是发布方逐条手填的配置项。
- 保留字只剩 `console`：控制台输入没有 simulated 标记，身份隔离只能靠 platform。模拟器数据归 `bilibili`（platform=bilibili + simulated=1），真假过滤靠 `simulated` 贯穿列——两者正交，模拟器要的正是走真实 B 站链路做端到端验证。
- 昵称不进任何身份判断：会漂移，权威在 `viewers.user_name`，需要"昵称找人"时实时反查。

### 金额口径

- **存储单位 = 平台最小虚拟货币单位**（B 站金瓜子）。SC 的元 ×1000 换算入库，整数无损。平台内单位一致，跨表聚合直接 `SUM`，无汇总层换算。
- **不跨平台聚合**：身份键已按平台隔离，聚合天然单平台，无需统一现实货币。
- **取值口径 = 标价**（`total_price`），实付另记 `paid_price`。贡献按标价算——送"舰长"就是 138 元贡献，无论打折；以实付为准会让打折/免费礼物在贡献认知上被区别对待。
- `currency` 带平台前缀（`bilibili_gold_coin` / `bilibili_silver_coin`）：自描述 + 防跨平台重名 + 同平台多币种（金/银瓜子）。
- 银瓜子（免费礼物）照常落库，付费统计与付费汇总按 currency 过滤；现实货币换算只在展示层执行，换算率收敛在代码常量 `CURRENCY_TO_CNY`（`src/modules/types/currency.py`）。

### 付费明细与原始保全

- 上舰建购买事件表 `guards`（每次开通/续费一条），周期存平台原值（`guard_num`/`guard_unit`，含 `"*3天"` 怪值原样保留），到期判断留应用层——不存会漂移的状态表。
- 每条付费消息存**当时的身份快照**（`guard_level`/`fans_medal_*`）——观众身份信息对画像价值高，且只在这些消息里有。
- **按数据可复现性决定是否存原始**：付费事件不可复刻（真实直播一次性事件，官方怪值无法预先测试）→ 存 `raw_data` 完整原始 JSON，解析可修复后重放补数；普通弹幕可复刻且关键信息已结构化 → 不存 raw。
- **user_id 缺失即告警并丢弃**：兜底 `"unknown"` 会让多个无 id 用户退化成同一行、身份互相混淆，宁缺毋滥。

## 替代方案（Alternatives）

### md5(platform + user_id) 派生 person_id（MaiBot 式）

**拒绝**。MaiBot 的哈希派生源于其多平台适配器生态需要统一 person_id；本项目无此需求，`(platform, user_id)` 直接作业务键即可，不引入无查询收益的哈希层。

### 保留单键 user_id，platform 仅作过滤条件

**拒绝**。这是把 platform 当 tenant_id 的概念错误——它是身份键的组成部分（键查找天然含它）。单键的现状才是真污染：调试 uid 与真实观众混一处。

### 各表存平台原始单位（SC 存元、礼物存金瓜子）

**拒绝**。"平台内统一到最小虚拟货币单位"正是本决策的本意——原始单位并存会让每处跨表 SUM 都带换算分支，1 元 = 1000 金瓜子的换算散落满仓必然出现漏乘。

### 以实付金额为贡献口径

**拒绝**。观众对"我送了多少"的认知按标价；打折场景实付口径系统性低估贡献，且 `paid_price` 已单独保留，信息不丢。

## 后果（Consequences）

- v10 迁移一次性重建 `viewers`（复合键唯一约束）并改造三明细表；存量行 platform 回填 `bilibili`（历史数据均产自 B 站链路，console 调试行无法区分、一并归入）。
- 消费方纪律：统计查询必须 `simulated=0` 过滤假数据，付费口径必须按 currency 过滤银瓜子与空币种——两个正交维度缺一不可。
- `paid_amount` 是派生值（可从明细重算），未来接美元平台时单位可调整，不构成锁死。
- B 站礼物连击的推送模式（每条都推 vs 只推终结）未实测，数量规则暂维持 `max(gift_num, combo_count)`；`combo_id` 已结构化、`raw_data` 已落库，实测后可按连击归并修正，不需要再改契约。
